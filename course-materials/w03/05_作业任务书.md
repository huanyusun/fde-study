# W03 作业：让运营 Agent 按青禾口径查数

>
> 适用：W03；工程与工具契约 `w03-0.1.0`；数据 `qinghe-w03-20260923`。截止与提交入口按班期或个人课程进度通知。

## 1. 本周输入与必做任务

带入 W02 业务模型和访谈核查记录，保留原版。课程方提供标准运营 Agent、梧桐书店独立完整样例、青禾 Markdown 资料及 4 张 CSV 表、W03 客户访谈和两个辅助工具框架。小样本为 20 个账户、48 笔订单、3 家门店、22 张卡；规模数据为 3 万账户、30 万订单、24 家门店、38,891 张卡。统计覆盖 2024-09-01 至 2026-09-01（结束日不包含），参考日 2026-09-01。

本周完成 38 项指标，包含 32 项通用报表指标和 6 项付费会员月度指标；目标目录见客户材料。开发两项内容：**指标构建 Skill／转换逻辑**和**测试用例与确定性结果判定代码**。默认框架的这两块未实现，不开发无法完成任务。提示词和 Skill 是真实开发；仅改目录、贴最终 YAML 或把实际结果复制成期望不算完成。

无须开发自然语言查数引擎、文件解析器或辅助工具网页。构建 Skill 使用你配置的大模型 API，判定程序可用任意后端语言。允许自建，但按同样业务范围和证据要求验收。W02 提取方法若不够，可在 W03 继续迭代，不增加第三个必须重写的工具。

## 2. 从领取到提交：完整 12 步

1. **承接 W02，明确任务。** 保存自己的原版及来源，建立 W03 工作副本；缺少起点可用材料包 [W2 checkpoint](W02_checkpoint/README.md)（W02 参考答案）中的参考业务模型，并注明采用了哪些部分。不能把参考稿当作本人访谈成果，照抄不算完成 W02。
2. **跑通独立样例。** 按工程 README 安装新环境，加载梧桐库，在原聊天入口完成一次问数，检查意图、SQL、结果和解释。确认标准 Agent 已具备什么。
3. **阅读材料，发现缺口。** 对照 38 项目标、旧模型、字典和小样本，区分业务规则、统计选择、字段或数据覆盖问题，说明影响和核查对象。规模 CSV 不整体送进模型。
4. **继续访谈。** 王经理为本周必访，可以先了解他对阶段交付、验收依据和双方责任的要求，不必等 SOW 初稿完成再约他。其他角色按缺口选择，补充必要的定义、条件、实例和责任。材料中已经说明的规则无须逐项重问；保留本人记录及未解决项。
5. **更新本体业务模型。** 使用原 W02 提取流程结合新增访谈、核查、修订并保存 W03 版。检查产品范围、账户与多卡、有效期端点、等级与资格是否真的更新。未更新就继续调整提取目标、提示词或 Skill；保存差异和来源。报表特有的时间选择、分子分母放进指标定义。
6. **开发指标构建 Skill。** 从业务模型、当期资料与字典生成候选定义、字段映射、依赖和来源，处理冲突与缺项。缺事实要未决，不能凭常识补全。保留实际模型输入输出与方法版本。
7. **核查候选与核定依据。** 对照原文和角色答复，确定采用版本、统计范围、未知和暂不支持项。形成自己的指标核定记录；可引用生成目录而不重复抄表。材料已明确的 32 项无需每项重问；重点补齐影响关键指标的缺口。
8. **形成指标库并接入 Agent。** 输出原生语义定义、必要客户模型、中文目录及来源；编译并加载小样本，继续在原聊天入口问青禾的数。真实执行，不只展示生成的 SQL。
9. **开发测试与判定模块。** 编写自然语言问题、独立期望和来源，开发确定性比较逻辑。课程框架调用标准问数内核并提供实际结果，你的程序负责比较，不另建问数引擎。
10. **小样本逐例核对。** 独立手算或另写审核程序确定期望，覆盖全部 38 项及关键业务边界；同时看意图、数值、分组、单位和解释。注入错误结果证明判定不是恒真。
11. **规模数据和多种问法回归。** 使用规模集，验证时间、支持维度及更多问法；独立期望与该数据版本对应。分清事实、模型、构建、产品、期望和判定的错误来源，修正后回归并保留失败记录及耗时。
12. **讨论、修订并提交 SOW。** 结合调查和验证形成草稿，写明本期、后续、排除项、依赖、职责、里程碑和验收依据。按条件筛选会员这类此时还没有开发的能力，不必在本周写出具体的条件清单，但要约定：它支持哪些条件，在这项能力交付时以书面的范围确认为准；超出确认范围的要求，按变更处理。把草稿的相关段落、代表性查询与校验的证据摘要，以及要核实的具体问题，粘贴到与王经理的普通访谈中，请他从财务和合同核查的职责出发提出意见；必要时再问其他角色。根据实际反馈修订同一份 SOW，保留修改依据、分歧和未决项，再随作业提交。计算正确、角色意见、合同批准和业务收益分别记录。

工程命令、配置与文件接口见解压包的 `docs/w03/README.md` 和 `contract.md`。访谈普通会话沿用每角色 2 次、每次 12 条学员消息的限制；了解要求、讨论草稿和反馈修改可以在同一会话中继续，不固定为两场访谈。页面接收聊天文字，没有 SOW 文件上传入口；按具体问题粘贴相关段落和必要证据，不能只发送本地文件路径。无需新建回访入口或另交一份汇报材料，也不要求取得王经理对整份 SOW 的批准。额度与开放状态由服务显示；不需要为了完成任务耗尽额度。

## 作业路线

这一节手把手走标准框架路线：用 `tools/w03.py` 构建和测试，判定程序用 Python，照着做能走完从领取到提交。走自建线的同学，第 1、3、4、7、12 步照做，其余步骤按第 3 节提供映射和可复跑入口。要求以本任务书正文为准，其他用法见工程 `docs/w03/README.md`。业务判断由你自己做，示例里的内容都是占位。

**在哪运行**：除第 1 步解压外，所有命令都在**工程目录**运行，就是解压出来的 `fde-agent-w03`。终端提示符不在这个目录时先 `cd` 进去。

**Windows**：先在 PowerShell 执行 `setx PYTHONUTF8 1`，关闭并重新打开所有 PowerShell 窗口；建环境用 `py -3.11 -m venv .venv`，其余命令把 `.venv/bin/python` 换成 `.venv\Scripts\python.exe`。文件操作和打包命令不同的地方，下面单独给了 PowerShell 写法。

更新业务模型走 `w02_workflow.py`，工作流已经包含提取，不用照工程里的 `docs/w02_extraction/README.md`、`docs/w02_walkthrough/README.md` 操作。

**整体顺序**：承接 W02 → 跑通梧桐样例 → 读材料找缺口 → 继续访谈 → 更新业务模型 → 开发构建 Skill → 核查候选 → 定稿并接入 Agent → 开发测试与判定 → 小样本核对 → 规模回归 → 修订 SOW 并提交

### 第 2 步：安装环境，跑通梧桐样例

**做什么**：新建 Python 3.11 环境，配置模型，加载梧桐样例，在聊天页问一次数。

本周依赖和 W02 不同，要新建环境。本机没有 `python3.11` 命令时，换成 3.11 解释器的完整路径（用 uv 的话是 `uv python find 3.11` 的输出）。

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip --isolated install -r requirements-w03.txt
```

配置模型。三个值换成自己的，`FDE_MODEL_URL` 写 Chat Completions 的完整地址，模型要支持原生工具调用。环境变量只在当前终端有效，每开一个新终端都要再设一次。

macOS／Linux：

```sh
export FDE_MODEL_URL='https://你的服务地址/v1/chat/completions'
export FDE_MODEL_NAME='你的模型名'
export FDE_MODEL_KEY='你的密钥'
```

Windows PowerShell：

```powershell
$env:FDE_MODEL_URL="https://你的服务地址/v1/chat/completions"
$env:FDE_MODEL_NAME="你的模型名"
$env:FDE_MODEL_KEY="你的密钥"
```

检查环境：

```sh
.venv/bin/python tools/w03.py doctor
```

成功时的样子（`python` 版本第三位可以不同）：

```json
{
  "python": "3.11.13",
  "missing_dependencies": [],
  "model_configured": true,
  "network_call_performed": false
}
```

加载样例并启动聊天：

```sh
.venv/bin/python tools/w03.py load --library examples/w03/library --data examples/w03/data --project .runtime/wutong-v1 --activate-home .runtime/product
.venv/bin/python tools/product.py start --home .runtime/product
```

`load` 成功时返回 `project` 和 `activated_home` 两个路径。`start` 成功时终端显示下面两行，然后一直占着这个终端，这是正常的：

```text
Sample tag API: http://127.0.0.1:某个端口
Product UI: http://127.0.0.1:8765
```

浏览器打开 `http://127.0.0.1:8765`，问“2026 年 8 月梧桐书店扣退后收入是多少？”。然后打开 `.runtime/product/metric-runs/` 里最新的目录，看 `result.json` 的 `intent`、`sql`、`rows`、`answer`。看完回到运行 `start` 的终端，按 Ctrl-C 停止。

- **算完成**：回答是 130 元，`rows` 里是 13000 分；能说清标准 Agent 已具备什么。
- **容易卡**：`doctor` 只查配置是否存在，不验证网络。工程根目录的 `README.md` 只是入口，安装和命令在 `docs/w03/README.md`。梧桐库只用于样例，不能回答青禾的问题。

### 第 4 步：继续访谈

**做什么**：这一步不跑命令。带着缺口访谈，保存原始记录。

1. 打开原访谈服务，选 W03。王经理必访，其他角色按第 3 步的缺口选。
2. 一次问一件事，沿上一轮回答追问。不知道怎样开口，可以看[访谈参考](08_访谈参考.md)（选看）。
3. 会议结束后点「导出提取用记录」，把下载的文件放到工程的 `artifacts/w02/sources/`，文件名形如 `W3-interview-会议编号-transcript.json`。
4. 在 `docs/w03/interview_notes.md` 加一节“本周访谈”，按下面的格式记：

| 角色 | 导出文件 | 要核实什么 | 问到了什么 | 未解决项 |
| --- | --- | --- | --- | --- |
| 角色名 | 文件名 | 对应缺口 | 要点，可引用原始导出 | 还缺什么、下一步找谁 |

用文本编辑器打开导出文件，开头应该有这三项：

```json
"contract_version": "w02-0.1.0-draft",
"week": 3,
"role_id": "角色编号"
```

- **算完成**：有王经理的本人记录，缺口有了答复或记成未解决项。
- **容易卡**：不要选「导出完整公开记录」（文件名以 `-public.json` 结尾），W03 的这种文件不能转换，要回网页重新导出。第 12 步还要和王经理讨论 SOW 草稿，留出次数。

### 第 5 步：更新本体业务模型

**做什么**：用 W02 工具把新访谈提取、核查，写进 W03 模型。

```sh
.venv/bin/python tools/w02_workflow.py init
```

`init` 不覆盖已有文件，返回的 `created` 列出新建了哪些文件。然后改两个文件，里面的路径都相对工程目录。

`customer/w02/workflow.json` 改三个字段，其他不动：

| 字段 | 填什么 |
| --- | --- |
| `goal` | 本周要核实的缺口 |
| `business_model` | `docs/w03/business_model.md` |
| `notes` | `docs/w03/interview_notes.md` |

```json
"goal": "占位：本周要核实的几类缺口",
"business_model": "docs/w03/business_model.md",
"notes": "docs/w03/interview_notes.md",
```

`customer/w02/extraction.json` 改三个字段：

| 字段 | 填什么 |
| --- | --- |
| `sources` | 第 4 步每个导出文件的路径 |
| `focus_questions` | 本周要提取的问题，来自缺口清单 |
| `profile` | 和模型匹配的配置，通用接口用 `compatible`，其他见 `docs/model-configuration.md` |

```json
"sources": ["artifacts/w02/sources/W3-interview-会议编号A-transcript.json", "artifacts/w02/sources/W3-interview-会议编号B-transcript.json"],
"focus_questions": ["占位：要提取的问题一", "占位：要提取的问题二"],
"profile": "compatible",
```

检查配置，这一步不调模型：

```sh
.venv/bin/python tools/w02_workflow.py inspect
```

成功时的样子，`materials` 等于 `sources` 的文件数：

```json
{
  "goal": "占位：本周要核实的几类缺口",
  "materials": 2,
  "batches": 1,
  "skill": "customer/w02/skills/extract-business/SKILL.md",
  "profile": "compatible"
}
```

启动提取。这条命令要等几分钟，等它自己返回，中途不要按 Ctrl-C：

```sh
.venv/bin/python tools/w02_workflow.py start
```

返回 `"status": "awaiting_review"` 后生成报告：

```sh
.venv/bin/python tools/w02_workflow.py report
```

用浏览器打开返回的 `report.html`，在「逐项核查」里对照原文。然后写反馈并继续：

```sh
.venv/bin/python tools/w02_workflow.py review --feedback '候选编号 采用；候选编号 修订为……，因为……；候选编号 暂不采用，因为……'
.venv/bin/python tools/w02_workflow.py resume
```

`resume` 返回 `awaiting_review` 就重复上面两段，返回 `awaiting_apply` 就往下走。先看草稿：

```sh
.venv/bin/python tools/w02_workflow.py report
```

在报告「模型修改」里核对旧模型和草稿。要改就：

```sh
.venv/bin/python tools/w02_workflow.py revise --feedback '哪一处要改，依据是什么'
.venv/bin/python tools/w02_workflow.py resume
```

确认后保存：

```sh
.venv/bin/python tools/w02_workflow.py apply
```

返回 `"status": "completed"` 后，写 `docs/w03/model_changes.md`，模板四节这样写：

| 模板的节 | 写什么 | 写到什么程度 | 从哪里取 |
| --- | --- | --- | --- |
| W02 起点及采用情况 | 起点是自己的 W02 还是参考稿，采用了哪些部分 | 用了参考稿要点到具体部分 | 第 1 步 |
| 本周更新、依据及解决的未知 | 改了什么、依据是什么、解决了哪个未知 | 每处写修改前、修改后、来源 | 报告「模型修改」、访谈导出 |
| 仍待确认 | 还没定的问题 | 写清缺什么、向谁核实 | 缺口清单、访谈未解决项 |
| 提取方法迭代与实际运行 | 改过目标、提示词或 Skill 吗，跑了哪几轮，结果怎样 | 写运行目录，失败的也写 | `artifacts/w02/runs/`、`artifacts/w02/workflows/` |

修改记录的占位写法：


## 4. 公开判定标准

技术门槛和交付门槛都要达标，平均分不能抵消核心缺项。

- 38 项完整可执行，且业务定义与确认来源一致。重点验证一账户多卡不重复、资格与等级区别、有效期和提前终止端点、月底资格与当月订单归属。其余通用指标也需验证退款、取消、首购观察期及粒度。
- 明确时段才查；含糊问题适当澄清；越界、未知维度值和未定义指标不假装算出零；月度范围按当期确认；零分母与缺数据有区别。
- 测试检查指标、时间、筛选、分组、数值、单位和空值，不比较 SQL 文本长得是否相同。分组以键匹配，允许无意义的行列重排；有意义的漏行、重复或数值错误必须发现。
- 对解释另留人工核查记录：是否正确识别当前客户，是否准确说明实际应用的时间、筛选和业务口径，是否把已知信息误说成未知。数值通过不能代替解释通过；不要求另建 LLM 裁判，也不按解释文字逐字比较。
- 至少展示这些错误能被判定拒绝：错指标、错日期、错筛选、错分组／漏组、元分混淆、比例误作百分数、null 改零、篡改数值，以及 error 被伪装成 ok。错误注入不调用另一套 LLM 判答案。
- 规模数据有真实执行与独立核对，至少覆盖通用订单、金额、首购、复购和付费会员月报；更多问法保留实际记录。没有统一“响应必须几秒”的虚构目标，记录环境、耗时与失败即可。
- W03 模型有实质更新和依据；构建与判定确有开发；有本人向王经理了解要求、带草稿与证据讨论的记录，以及据反馈修订或保留未决项的依据；不按访谈场数或是否得到“同意”判定完成。SOW 不把角色意见写成合同批准，不以合成数据承诺业务增长。

公开 `check` 只作结构与自报预检；程序成功、语义正确和客户确认分开判定。助教会用独立问题与错误结果复查，不按代码行数、语言或所选模型品牌评分。

## 5. 卡住以后

环境问题先重跑独立样例，按报错区分 API、依赖、构建和查询问题。缺业务事实继续访谈；如遗漏或回答不稳定造成阻断，课程方按需要直接分发与访谈事实一致的补充材料：MD 供阅读，同源 JSON 加入原提取工具的 sources。来源须标为课程方补充，不冒充自己的访谈，不以补充材料充抵必访记录。W02 提取遗漏可以继续改方法后更新模型，不需要重交 W02。

W03 的 checkpoint 随 W04 材料包提供可运行参考状态，须另存、注明采用部分并补齐本人开发与核查证据，不能用覆盖方式消除失败记录。本周未通过不阻断下周材料开放；核心缺项需在答辩前补齐。作业期间遇到服务失败，保留会话和请求编号，先刷新原记录，不反复创建会话。

## 报错对照表

出错时先按这四步排查，再查下表：

1. **看原文**：完整读错误码和位置，不要只看到“失败”就重跑。
2. **分层**：判断问题在哪一层：自己的命令和配置、网络和模型服务，还是业务内容。
3. **缩小范围**：用最小的一步验证，比如只跑不调模型的检查命令，或看这次运行留下的记录。
4. **留证据再求助**：记下运行的命令、错误码和试过的办法。半小时还没解决，就带着这些发到群里。

| 错误码或现象 | 原因 | 下一步 |
| --- | --- | --- |
| `UnicodeDecodeError: 'gbk' codec can't decode` | Windows 没开 UTF-8 模式 | 执行 `setx PYTHONUTF8 1`，重开所有 PowerShell 窗口 |
| `MODEL_NOT_CONFIGURED` | 三个模型环境变量缺项，或换了终端 | 在当前终端重新设置，`doctor` 看 `model_configured` |
| `MODEL_POLICY_INVALID` | `FDE_MODEL_TIMEOUT` 等参数不合规；`w03.py` 下超过 240 就会报 | `w03.py` 的 `FDE_MODEL_TIMEOUT` 不超过 240 |
| `MODEL_TIMEOUT` | 模型单次调用超时；`w03.py` 默认 180 秒，W02 工具默认 90 秒 | 确认进程已结束，设 `FDE_MODEL_TIMEOUT=240`（W02 工具可设 180），重新运行；构建换新输出目录 |
| `MODEL_NETWORK_ERROR`、`MODEL_HTTP_401` 这类 | 网络不通，或模型服务拒绝请求 | 核对网络、地址、模型名和密钥，重新运行 |
| `MODEL_OUTPUT_TRUNCATED` | 输出被截断 | `build` 用 `--metrics` 分批，再 `merge`；W02 工具先看 `*.attempts.json` 的 `finish_reason`，是 `length` 就设 `FDE_MODEL_MAX_TOKENS=32768` 并调 `batch_chars`，批次多要注意一次推进 600 秒的上限 |
| `build` 报 `Expecting value` 这类，`trace.json` 的 `error` 是 `JSONDecodeError` | 模型没有只返回 JSON，常见是返回了 YAML | 在 Skill 第四段写明只返回一个 JSON 对象，换新目录重建 |

| `WORKSPACE_ALREADY_INITIALIZED` | `customer/w03` 已存在，`init` 重复运行 | 不用再 `init`，直接往下做 |
| `OUTPUT_ALREADY_EXISTS` | `build`、`merge` 或 `test` 的输出目录已存在 | 换新目录；`merge` 到定稿库时先把旧库改名 |
