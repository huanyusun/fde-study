| 输入 | 本轮怎样使用 |

| `migration_records.csv` | `pos_source_id`、`crm_source_id` 指定双端来源账户；本版状态包括 `success`、`failed`、`revoked`、`unknown` |
| `account_review_records.csv` | `left_source_id`、`right_source_id` 和 `conclusion` 表达指定账户的同人／非同人结论；本版有 `same`、`different`，有效状态为 `current` |
| `operational_verification.csv` | `kind` 为 `employee` 或 `abnormal_identity`，`conclusion`、`status` 表达核验结论及状态；`scope` 为 `member` 或 `account`，不能混用 |
| `contact_scope_confirmation.csv` | 指向原条目的 `original_file`、`original_row`、`original_quote`；`channel_scope` 可为 `all`、`telephone`、`sms`、`unknown`，`status` 有 `current`、`pending` |
| `business_basis.csv` | `document_id`、`source_accounts`、`checked_at`、`checked_material`、`issuer` 描述课程模拟核查依据；`source_accounts` 以竖线分隔。不是统一会员答案表 |
| `coverage.json` | 订单覆盖、开户核查覆盖、员工／异常核验覆盖、参考日和限制；覆盖声明只适用于所列来源及哈希对应文件 |
| `knowledge/catalog.json` 与同目录 Markdown | 课程方提供的知识目录和原文，含层级、版本、有效范围及条件，由真实 LlamaIndex 本地关键词索引读取；不要求自建向量检索平台 |

业务记录通常带 `record_id`、`valid_from`、`valid_until`、依据位置与范围；有效区间含起点、不含终点。`basis_file`、`basis_row`、`basis_document_id` 必须能指向适用于当前账户的依据，不能只看状态字符串。CSV 来源行号指去掉表头后的第 1 条记录起算；更正记录只有明确有效的 `replaces_record_id` 才能替代旧记录。

以上枚举描述本版实际文件，不意味着“没出现的异常就可以静默放过”。未知状态、缺失依据和有效记录冲突应保留明确结果。

本版 `coverage.json` 声明已经核对两来源的开户／迁移留档，并单列未确认登记人的例外；它是判断独立开户来源的一项业务依据。无边来源不能脱离该覆盖、原文件哈希及例外记录单独判断。员工／异常核验同样按本批覆盖解释，不把“本批未发现排除”说成永久正常。

### 知识检索的层级与上下文

`retrieve_knowledge` 的 `level` 按本版 `knowledge/catalog.json` 选择：

| `level` | 登记文档 | 主要内容 |
| --- | --- | --- |
| `definition`（定义层） | `03_身份关联与数据使用说明.md`（`identity`） | 来源账户与统一会员的含义、身份关联依据、数据覆盖与关联后的使用边界 |
| `domain`（业务领域层） | `04_运营对象核验说明.md`（`operations`） | 员工／异常身份核验、运营排除范围，以及推荐与经营统计的区分 |
| `usage`（使用层） | `05_联系限制与建议说明.md`（`contact`） | 分渠道联系限制、待核处理、有依据建议及执行授权边界 |

层级会筛选文档。例如查联系限制却填 `domain`，取不到登记在 `usage` 的联系说明。不确定层级时可以不传 `level`；不传时不按层级筛选，仍受关键词匹配、有效期、适用条件及返回条数限制，不保证返回全部文档。

`context` 是判断知识是否适用的会员上下文，可用的键为 `channel`、`identity`、`tier`。先调用 `get_member`，从返回的 `recommendation_context` 取值传入，不自行编写或猜测。本周三份登记文档的 `conditions` 均为 `{}`，未登记结构化条件，传不传 `context` 不影响这三份文档的返回；建议校验仍会把引用片段的条件与 `get_member` 返回的 `recommendation_context` 核对。知识适用不替代程序的联系限制判断。

### 圈选支持的条件

`member_cohort` 按条件筛选会员，沉睡召回的主条件只是其中一种组合。客户侧约定的条件范围见[新需求说明第五节](客户材料/02_W05新需求说明.md#五按条件筛选会员本轮的条件范围)；下表是对应的请求字段，完整定义和例子见工程包 `docs/w05/README.md`。

| 条件 | 字段 | 说明 |
| --- | --- | --- |
| 指标条件 | `metric_filters` | 1～3 条，同时满足。指标取自己指标库里能按会员计算的指标，金额按分填写；同一指标可以各给一条下限和上限。没有两期对比时必填，有两期对比时可以不填 |
| 指标窗口 | `start`、`end` | 必填，含起始、不含结束；有两期对比时就是本期 |
| 最近有效购买间隔 | `dormant_days`、`active_within_days` | 都可以不填。前者表示距参考日至少满 N 天，后者表示不足 N 天；两个都填表示一个区间；都不填就不按购买间隔筛选 |
| 注册门店 | `store_id`、`store_ids` | `store_id` 填一家门店，或 `null` 表示全公司；`store_ids` 填 1～50 家门店，任一门店有注册关系即在范围内，同一人只列一次。两个字段不能同时填 |
| 会员等级 | `tiers` | 可以不填。填一个或多个等级，表示属于其中任一等级；取值用数据里的等级原值，不在数据里的值返回 `TIER_VALUE_NOT_IN_DATA`，不当作零命中 |
| 注册日期 | `registered_from`、`registered_before` | 都可以不填，可以只填一边；含起始、不含结束。注册日期取来源 CRM 已知入会日期的最早值 |
| 两期对比 | `comparison` | 可以不填。`metric` 为对比的指标，`baseline_start`／`baseline_end` 为基期，基期须在本期之前、不重叠；`direction` 为 `decrease` 或 `increase`；`min_ratio` 为变化幅度下限，按基期值的比例填写，下降不少于 50% 填 `0.5`；`min_baseline_value` 可选，为基期值下限，按指标原单位填写 |
| 联系渠道 | `channel` | `telephone`／`sms`／`all`，或 `null` 只做条件分析 |

**等级或注册日期未知的会员不会被丢掉**。 等级在各来源不一致或没有记录时为未知，POS 独有会员的注册日期为未知。其余条件都满足、所要求的属性未知的已核实会员，列在结果的 `attribute_pending_members` 里，不计入条件命中，也不当作不满足条件；其中没有被运营排除、所查渠道没有被阻断的，同时并入 `unknown_members` 待核，结果为 `partial`，最终回答不能是 `completed`。

**两期对比只在基期有该指标记录的会员中进行**。 本期没有记录时按 0 计，所以降到零的会员会入选；基期值不大于 0 时比例没有定义，不入选，人数在 `comparison_condition` 里给出；本期才第一次购买的会员不在对比范围内。两期对比只接受可加总的指标，例如净消费、有效订单数，比率类和月度类指标返回 `COMPARISON_METRIC_NOT_SUPPORTED`。同时填了指标条件时，指标条件作用于本期。

**只设上限的条件只覆盖窗口内有记录的会员**。 没有两期对比时，圈选只在指标窗口内有相应记录的会员中筛选。像「净消费不足 1,000 元」这种条件，窗口内没有任何订单的会员不在结果里；这时结果的 `candidate_scope.zero_value_members_omitted` 为 `true`，结果说明也会写明，引用名单时要带上这句范围，不能说成「全部消费不足 1,000 元的会员」。要找很久没有购买的会员，用最近有效购买间隔条件。

本版不支持的条件：会员卡相关的条件（卡种、购卡金额、生效或到期日期）；条件之间的「或」；除两期对比外，一个请求里使用多个窗口；只支持完整自然月的月度类指标；超过 3 条指标条件；不带任何指标条件、只按等级或门店等属性列会员；与当前准备批次不同的参考日。用户提出这类条件时，Agent 应把原话填进 `unsupported_conditions`，圈选返回 `unsupported`／`CONDITION_NOT_SUPPORTED`，不给名单，最终回答不能是 `completed`，要向用户说明缺口。申报以后，其余条件字段可以留空，例如没有任何指标条件也可以；但 `reference_date`、`start`、`end` 三个日期仍然必填，格式本身不对的字段（例如空的等级列表）仍按参数错误返回。不能丢掉这些条件后按剩下的条件照常圈选。最小的申报请求如下：

```json
{"name":"member_cohort","args":{"reference_date":"2026-09-01","start":"2025-09-01","end":"2026-09-01","unsupported_conditions":["只筛选悦享年卡会员"]}}
```

返回结果里的 `recency_condition`、`attribute_conditions`、`store_scope`、`comparison_condition` 回显本次实际使用的条件；核对 Agent 的回答时逐项对照用户提出的条件，确认没有漏掉的。

## 三、三个客户函数的接口

三个函数都写在工程的 `customer/w05/solution.py`。以下仅说明返回契约，不提供青禾匹配和限制的实现答案。框架入口是 `platform/fde_product/w05/prepare.py`，调用契约在 `contracts/w05/`，可执行对象定义源是客户 YAML；业务规则以本轮书面说明为准，运行签名以 `20261014.2` 为准，三个客户函数的签名与 `20261012.1` 相同。

### `identity_evidence(accounts, materials)`

`accounts` 是来源账户列表，每项有 `source_id`、`system`、`source_file`、`source_row`、`registered_store` 和原始 `raw`；`source_id` 已加 `CRM:`／`POS:` 前缀。`materials` 包含 `manifest`、`coverage`、`reference_date` 以及按文件名索引的公开业务记录列表。

返回字典必须有：

- `rule_version`：本次客户规则版本，后续准备结果、绑定和报告一致；
- `evidence`：每条含 `left`、`right`、`relation`、`evidence_id`、`source_file`、`source_row`、`rule_version`；`relation` 为 `same`／`different`／`unresolved`，受 `IdentityEvidence.schema.json` 检查；
- `verified_singletons`：有公开核查依据支持独立开户的来源 ID 列表，不是所有孤立点列表；
- `findings`：未采信、失效、导出外引用、缺失及冲突等发现，保留可定位来源和原因。

框架从这些返回值形成来源映射，不能在材料中读取最终统一会员 ID。`findings` 保存客户函数报告的发现，传递矛盾／未决状态还应检查 `state/mapping.json`；不能假定所有框架图冲突均自动追加到 `identity_findings.json`。

### `member_attributes(member_id, source_records)`

`source_records` 是当前组件涉及的来源账户，结构与 `accounts` 中单项相同。该函数也会收到未决来源的独立财务桶；框架不会把一个未决组件合并成已核实会员，而是逐来源保留财务记录及映射原因。不得仅因函数被调用就认定其是自然人；`identity_status` 由框架根据映射写入。

当前完整属性接口采用 `display_name`、`names`、`masked_mobiles`、`tier`、`conflicts`、`source_ids`、`registered_stores`、`sources`。`display_name` 为字符串或 `null`；姓名未知或多来源冲突时可以为空，不能要求选择第一条。候选显示名若给出须有依据；多个姓名和掩码手机保留数组；等级不能确定时为 `null`；`conflicts` 为冲突说明对象；来源数组需能定位原文件、记录及字段。注册门店为去重后的关系集合，缺少时为空集合，不新增一个猜测值。

### `contact_constraints(member_id, source_records, materials, channel)`

返回当前组件的限制和核验结果，供直接入口及 Agent 共用。准备阶段 `channel` 为 `None`，需要同时产生电话和短信的状态，不能默认电话。

当前共享模块读取以下字段：

| 字段 | 类型及含义 |
| --- | --- |
| `member_id`、`status` | 当前对象 ID；核查正常或仍有未知，按 `ok`／`unknown` 表达 |
| `channels` | `telephone`、`sms` 各为 `blocked`／`unknown`／`no_known_restriction` |
| `restriction_evidence` | 限制原文及来源数组，基础字段参见 `Restriction.schema.json` |
| `member_excluded` | 是否存在生效的会员范围运营排除，布尔值 |
| `account_exclusions`、`all_source_accounts_excluded` | 被排除的来源账户 ID 数组（依据另列于 `confirmed_exclusions`），以及是否所有来源账户都被排除；不要把单个账户排除自动扩大为会员结论 |
| `confirmed_exclusions`、`pending_verifications` | 已确认排除和待核事项分别列出，均保留依据 |
| `verification_coverage_complete` | 本轮要求的核查是否被有效覆盖，布尔值；不能无依据填 `true` |
| `actual_contact_authorized` | 本轮恒为 `false`；没有执行联系授权 |

可使用课程方的公开记录读取及依据核查辅助函数；它们不替你决定证据优先级、范围、属性冲突和客户限制规则。

## 四、生成物怎样承接

`prepare` 输出 `cleaned/`、`library/`、`project/`、`state/`、`knowledge-index/`、`objects/` 和 `reconciliation.json`。`project/` 是实际 dbt／DuckDB／MetricFlow 项目，`state/` 保留来源关系和限制；`objects/` 保存由 YAML 生成的 ORM、JSON Schema、对象库和生成记录。金额使用原指标引擎，会员对象查询使用同一准备批次的对象库；不是把指标计算迁入 LinkML。

核对当前指标说明时，查看 `library/metrics.yml` 的描述、`catalog.json` 的当前约束／定义、`scope.json` 的覆盖与业务模型路径，以及生成后 `project/` 中的对应内容。`catalog.json` 的历史 `sources` 可以继续保留，但须与当前定义区分。报告标题和模型引用也要同步，不能仅更新一条全局备注。修改自己的输入库后重新准备、绑定，不直接改生成文件来绕过版本检查。

本周 `buyer_count` 按已核实统一会员与未决来源独立财务桶统计。核对自己输入库中该指标的 `catalog.json` 显示名为“购买财务实体数”，`metrics.yml` 的该项 `description` 明确这一粒度和自然人数待核边界；已有准确说明沿用，不重复堆叠。保留指标 ID、公式、筛选条件、窗口和历史来源原文，准备后再核对生成库的实际说明。只调整本场景受影响的语义，不将其他指标统一改名。

自 `.12` 起，`member_relations.cards` 保留原 `raw` 及账户、文件、行号，同时增加 `semantics`：`purchase_amount` 为购卡金额，`unit=CNY`，原单位为元、来源字段为 `pay_amt`；`effective_date`、`expiry_date`、`stop_date` 分别来自 `st_dt`、`ed_dt`、`stop_dt`。各项含 `known`／`missing`／`invalid` 状态，缺失和非法值不推断为有效日期。`financial_status` 反映 W04 实际接受／隔离结果；关系接口展示原卡不表示卡款进入订单净消费，也不据卡种推定有效期或当前可用状态。

`get_member.recommendation_decision` 列出详情实际安全条件；`recommendation_context` 只供知识适用，等级不参与该安全判断。详情安全条件不等于完整圈选资格，完整条件使用 `member_cohort`。`follow_up_requirements` 按实际未知字段指出补证对象及责任角色，注册门店未知不能推翻已核实身份。

本版沿用 `.13` 对当前会员事实的 `summary` 和圈选 `suggestion` 使用结构化结果生成的固定说明。模型继续选择工具、取得证据和适用知识；固定说明分别表达候选、待核、阻断、分页及注册关系未知范围。`coverage_complete` 只表示最近有效购买判断窗口覆盖；圈选未核查财务隔离记录，空名单或未决身份来源空集都不能推出没有隔离记录。补证事项仅取实际 `follow_up_requirements`，不将角色一般分工增加为当前待办。此能力由课程工程提供，不增加客户函数或学员开发任务。

运营 Agent 最终返回 `status=completed` 且 `validation_code=GROUNDED`，表示已调用工具的结果完整、引用合法，已提交的建议通过逐条校验；`GROUNDED` 单独表示校验通过，不等于任务完成。

本版起，最后一次圈选的名单不为空时，最终结果还要有两个字段：`task_scope` 写明本轮是否要建议（`recommendations_requested`）和对任务的一句理解（`statement`）；`non_recommendations` 列出不给建议的会员，每条有 `member_id`、理由 `reason_code`、当轮证据 `evidence_ids` 和说明 `explanation`。要建议时，本页名单里每个人要么有一条建议，要么有一条不建议记录，漏一人返回 `CANDIDATE_NOT_DISPOSED`，结果为 `incomplete`。理由有五种：`program_blocked`（程序禁止或运营排除，可以完成）、`facts_pending`（事实待核）、`no_applicable_knowledge`（本轮检索没有适用知识）、`evidence_missing`（还缺工具证据），这三种只能 `incomplete`；`not_requested` 只用于本轮不要建议。本轮不要建议时，`non_recommendations` 留空即可，不必逐人列出。名单为空、圈选被拒或没有圈选时不需要这两个字段，写了也不判错。

程序仍然不检查 `task_scope` 是否忠实于原题：题目要建议、模型却声明不要，程序发现不了；`explanation` 的文字也不校验。用户提出的条件如果既没有被应用、也没有填进 `unsupported_conditions`，程序同样发现不了。提交前须对照原题逐项核对，包括题目里的每一个条件。

回答没通过程序校验时，`status` 为 `incomplete`，`result.summary` 换成程序按当轮工具结果生成的固定摘要（没有固定摘要的，换成一句说明校验没通过的固定文字），模型原来的回答保留在 `result.model_claim`，`validation_code` 写明原因。排查时看 `model_claim` 和 `validation_code`。

运营 Agent 的 `critical_facts` 须对应当轮工具返回，`validation_scope` 明确程序已检查和未检查的范围。`validation_passed`／`GROUNDED` 不检查全部自由文字事实，也不表示业务验收；仍须将最终说明中的金额、日期、限制及依据与源记录核对。以上均由公共工程提供，不增加学员函数。

未决来源为了保存财务记录可以对应独立桶，不能算成已核实自然人。涉及人数及人数分母的当前指标可能返回 `partial`；应说明影响，不能改成 `completed` 来通过验证。注册门店、等级的代表属性也不能替代全部来源关系。

直接 `query` 的 `status=ok` 表示计算执行成功；还要读取返回的覆盖和身份语义说明。运营 Agent 的 `query_metrics` 会按这些业务边界表达 `partial`，最终答复可能为 `incomplete`。不能只凭底层执行成功就宣称精确自然人数已经确定，也不要求将不同层的状态字段机械改成相同值。

本版摘要按实际 `conflicts` 区分姓名／等级来源冲突、真实缺失和正常值；不能通过填入虚构代表值消除冲突。W05 当前粒度下，单项、未分组的 `buyer_count` 查询首句直接说明购买财务实体数，其他指标和分组仍须核对实际粒度。固定摘要不替代客户函数返回的正确事实。

`export` 自动导出的 `ontology.yaml` 是更广的对象关系说明，并附客户 YAML 的路径和摘要；它不是执行源。唯一对象定义源是 `customer/w05/member.linkml.yaml`，生成 ORM 与对象库不手改，修改 YAML、客户代码或输入后须新建 prepared 和 home。

导出使用本材料的[四字段模板](模板/export.json)：`prepared`、`mvp_report`、`customer_code`、`binding`。除原主数据、对账、ontology 和报告四份文件外，导出还复制客户 `solution.py`、`member.linkml.yaml`、依赖锁，以及 `artifacts/w05/model-build.json`、`model-binding.json`。指标库、状态快照、完整 Markdown 模型和原始证据仍须补齐。重新绑定后重新导出，不能把旧 `model-binding.json` 搬来匹配新运行。

当前 checker 检查模型源、生成批次与绑定，以及原结构、版本、金额和可运行性；同时要求 `precision_acceptance` 保留 `pending` 开头，报告 `pending` 包含 `precise_person_total`。这是本周业务边界，不要求删除待定标识；已核实范围仍必须准确核对。

已知使用观察：当前会员说明包含较多来源和内部字段，阅读体验仍待真人反馈。
