## 一、本周做什么

在自己的 W04 客户版本上，完成两块开发：

1. **ID-Mapping 与 ETL 接续**：依据迁移和账户核查记录建立身份关系，生成统一会员及来源映射，让新旧订单实际按映射进入查询；保留冲突、未决和对账证据。
2. **会员业务能力开发**：实现客户属性、关系及联系限制的规则适配，让运营 Agent 可以圈选会员，再取得信息、关联记录和建议依据，并与直接入口得到一致结果。

两块工作共同服务以下任务：

> 按指定门店、本轮消费与沉睡条件筛选会员，查看会员信息和关联记录，说明入选理由、联系限制和待核事项，并给出有依据的运营建议。

## 三、从阅读到提交：8 个步骤

### 1. 阅读材料，列出实际缺口

先读 demo 纪要、新需求和三份依据说明，再检查数据中的记录、覆盖和来源。将 W04 完整模型接续到 `docs/w05/business_model.md`，按新证据核对身份、门店、限制、指标粒度和能力边界。

材料已经明确的规则直接引用，不重新访谈确认一遍。有影响实现的缺口再定向沟通：老周核查身份依据、导出范围及记录状态；小林核查具体限制及运营例外；其他角色按实际职责选访。**不按访谈次数、角色数量评分**，不要求访遍五位角色。材料、数据计算、真实访谈和自己的推断分别标注来源；没有完成的沟通如实保留待核。

访谈不保证能消除每条记录的未知。若角色仍不能提供可定位依据，保留待核、影响和后续补证对象即可；C 组本来就要求验证待核结果，不能为得到确定答案而改变原记录或重复追问。

业务访谈 Agent 的个人账号、入口、窗口与配额由课程通知提供。只有实际完成的交流才能登记为访谈；入口不可用时如实报告，不能编写客户已确认的对话。

### 2. 填写对象定义，实现身份依据与客户属性

依据第一步的 Markdown 模型，在 `customer/w05/member.linkml.yaml` 填写 `Member`、`SourceAccount`、`Store` 的 `slots` 列表并删除 TODO 注释。模板提供字段定义、类型和多值关系，先核对含义再引用；手工填写路径和独立练习在工程 `docs/w05/手工模型说明.md`。Markdown 继续保存完整含义、依据和未决问题，YAML 提供本场景可执行的对象结构，两者应一致。业务判断继续写在以下客户函数里，不把规则只写进 YAML 描述。

完成 `identity_evidence(accounts, materials)` 和 `member_attributes(member_id, source_records)`，使用公开记录判断哪些关联可采信，哪些是不同人、未决或冲突；保留记录编号、来源位置和规则版本。框架负责根据你提供的有效依据建立映射。

不能仅凭姓名、脱敏手机号或设备相同合并。没有关联边的账户是否可以视为独立会员，也要核对开户核查覆盖和例外，不能一律当作自然人。失效、撤销、导出外引用和有效依据冲突各自保留原因。

会员属性保留多来源和冲突，注册门店与购买门店分别表达。POS 没有提供注册门店时保持未知，不能反填购买门店。

属性呈现还要承接前序已核定的规范化和缺失值规则。原始字段留存不等于把缺失标记当成真实姓名、手机号或属性冲突；在来源中保留原值，在业务属性中正确表达缺失。

### 3. 实现限制规则，准备统一数据并对账

完成 `contact_constraints(member_id, source_records, materials, channel)`。核对员工／异常核验的效力和账户／会员范围，将 CRM、工作账及补充确认记录中的限制作用于已核实身份；未知不等于允许联系，明确禁止不被空白或较新记录自动解除。

填写[准备请求模板](模板/prepare.json)，使用工程的 `tools/w05.py prepare` 生成新的准备目录。框架会接续 W04 清洗结果、加入 POS、消费身份映射、构建查询库和知识索引，同时读取 YAML 生成对象映射代码、校验实例并装载对象库；三个函数或 YAML 的 TODO 未完成时会明确失败。

核对源账户、已核实会员、未决账户分别落在哪里，逐来源核对订单的接受、隔离、去重及金额守恒。至少追溯一组跨系统账户和其订单、一条不应采信的依据；不能仅比较两个总数。修正后在新目录重跑，保留第一次结果和差异。

### 4. 核对模型、指标与共享入口

检查准备目录中实际生效的 `library/`、`project/`、`state/` 和 `objects/`。核对 YAML 的属性与多值关系确实进入生成结构和对象查询，而不只是保存了一个文件。原指标 ID 及未受影响计算定义保持；统一身份、代表属性、多门店关系和未决财务桶的实际语义必须与业务模型一致。把修订原因和来源记入本周同一份报告，未修改部分也说明核对范围，不按修改条数评分。

计算正确还要核对模型读到的说明：指标描述、目录中的当前约束、覆盖说明和业务模型路径应指向本轮状态，不能继续把已接入的 POS 说成未导出，或把统一实体说成旧 CRM 账户。历史原文保留来源与适用阶段；当前可执行定义和当前模型不能仍指向旧版。文件位置见[输入与工程说明](06_输入与工程说明.md#四生成物怎样承接)。

本周 `buyer_count` 统计已核实统一会员与未决来源独立财务桶。核对输入库中该项 `catalog.json` 显示名为“购买财务实体数”，`metrics.yml` 的 `description` 说明这一粒度及自然人数待核；已有准确定义沿用，ID、公式、窗口和历史来源保留。修改后重新准备，检查有效库，不能只改报告标题。

填写[绑定请求](模板/bind.json)，用 `tools/w05.py bind` 绑定新的运行目录，再按工程说明执行 `tools/product.py init`。直接入口和运营 Agent 都使用该绑定。对象定义、代码、数据、规则或知识改变后，重新准备、绑定新 home 并初始化，不能用旧缓存证明新版本通过。课程方发布新版工程时，按输入说明「已做过 `.13` 时怎样接续」一节处理：只有说明写明可以沿用准备目录、并且自己的准备输入都没有改时才沿用。

课程方提供的直接入口是 `tools/w05.py service-call`；不要求开发 Web 页面。四个业务工具为 `member_cohort`、`get_member`、`member_relations`、`retrieve_knowledge`，旧指标仍走 `query_metrics`。`retrieve_knowledge` 的层级与上下文怎样取值，见[输入与工程说明](06_输入与工程说明.md#知识检索的层级与上下文)。

| `artifacts/w05/mvp_v1_report.json` 与其引用的 `evidence/` 文件 | 第二块：实际任务、独立预期、直接入口与模型原输出、变更、回归、沟通及耗时；路径相对提交目录填写 |
| `artifacts/w05/precheck.json`、复现请求文件（放在提交目录的 `requests/`） | 公开自检原结果及你实际使用的准备、绑定、导出参数；不含密钥和不可取得的教师目录 |

准备目录中的数据库可由输入和代码重建，不必上传虚拟环境或缓存。原始课程数据不重复作为作业上传；按发放版本及哈希定位。提交前去掉私有凭据，路径改为可解释、可重定位的自己的工作目录，不能依赖教师机器。状态快照和旧绑定含本机路径，不能直接复制后声称已复跑；在新工作目录用提交代码、有效库及可取得的同版输入重新准备、绑定和初始化，原快照保留用于对照。具体路径操作见工程包 `docs/w05/README.md`。

### 8. 自检、复核并提交

使用当前提交、准备目录和绑定运行 `tools/w05_check.py`，输出到新的文件，再把结果放入提交目录。示例：

```sh
python tools/w05_check.py --submission YOUR_SUBMISSION --prepared YOUR_PREPARED --binding YOUR_HOME/member-binding.json --output YOUR_NEW_CHECK.json
```

`YOUR_*` 替换为自己的实际路径。自检通过后，仍须逐项检查 A～E 的真实回答、身份依据和业务边界。程序判定完成不等于题目要求全部完成，提交前对照原题核对是否有漏做。缺项在报告中标明。提交时只把这个提交目录打成一个 zip，解压后应直接看到 `customer/`、`artifacts/`、`docs/` 等文件夹，按班期通知的方式提交；不打包整个工程目录、准备目录、`.venv` 或 `.runtime`，也不要把工程候选包原样提交当作作业。

## 四、两个门槛都要满足

**技术门槛**：身份规则正确且被 ETL 和运行查询消费；源记录和金额对得上；客户 YAML 被生成与查询消费，共享模块被直接入口和 Agent 使用；正常、空、禁止、待核结果正确；实际变更及回归有证据。

**交付门槛**：业务模型、指标和实现一致；每个结论能区分材料、计算、访谈、推断与待核；能解释身份误判、范围影响、为何只提供建议及尚未满足的条件。不因角色多、报告长或模型品牌不同加减分。

checker 主要检查文件、版本、映射内部一致性、金额守恒和可运行性，不是客户验收。对身份规则的有效性、人数含义、建议及自由文本的正确性还要核对原始依据。未使用的字段、输出措辞或文件顺序不要求与教师实现完全一致。

核对最终回答时，要检查字段含义和判断依据，而不只检查数字有没有出现。来源有不同值的姓名／等级应明确冲突及当前选择状态，真实未提供才按缺失表达；不要把冲突文案拼进客户属性来修公共摘要。金额、日期和状态不能互换，上下文属性也不一定是筛选条件。若客户实现和工具数据正确，但课程公共模块仍生成错误解释，保留同题输入、工具结果和原答，交课程方修复；不要求学员重写通用模型审核或修改 checker。

## 五、人数、名单和金额怎样判定

1. **可确定的必须算准确**：同一输入版本、同一业务依据下，已核实身份的来源分组、来源覆盖、订单归属和金额应能精确核对。不能将全部账户丢入待核来回避实现，也不能只凑齐人数而错误合并。
2. **未决对象明确单列**：未决来源账户是账户数，不是自然人数。为保持订单和金额而设立的财务桶，也不能当成已核实的人；说明未决项对哪些人数及分母有影响。
3. **指定条件结果按实际证据核对**：名单、注册门店关系、渠道状态及对应指标值应与输入一致；不同 ID 编码按来源账户集合比较。未指定渠道时不报单一“可联系人数”。
4. **全公司精确自然人数继续补证**：本周要求交付已核实范围、未决来源、受影响的人数／分母及下一步核查对象，不要求消除全部未决身份。客户口头约数不能作程序常量；保留 `precise_person_total` 不单独判作业失败，把未证实总数写成已验收则不达标。员工或异常账户被排除运营推荐，不等于其自然人身份已经查清，也不等于相应经营记录可被删除。
5. **金额单独对账**：运营排除不删除源订单或扣减既有经营金额；按来源说明接受、隔离、去重和退款处理。出现差异必须定位到记录及规则，不能自行设置容差放过。

在现有报告的 `scope_and_evidence.unresolved_impacts` 中说明未决对象、所缺依据、受影响结论、核查对象和补证后要重算的内容即可，不增加独立报告。交易人数、复购率等要分别说明统计对象、时间窗口、购买／退款口径与覆盖；已核实范围的结果不能冒称全公司结果。保留源数据的财务核算、会员身份核实和运营推荐范围分别判断，不能用其中一个结果代替另外两个。

## 六、卡住时怎样继续

| 情况 | 先核查什么 |
| --- | --- |
| `C3_BASE_REQUIRED` 或源／清洗哈希不一致 | W04 c3 数据和自己的清洗 manifest 是否匹配；不要改哈希伪造一致 |
| TODO 未实现、缺少字段 | 核对三个函数及 YAML 的类字段列表；`MODEL_TODO_FILL_CUSTOMER_SOURCE` 指向未填模型，按[输入说明](06_输入与工程说明.md)及工程手工说明定位 |
| 模型校验或导出绑定错误 | 核对字段类型、必填性、关系目标；导出填写客户代码和当前绑定，修改后新建 prepared／home 并重新导出，不手改生成物 |
| 输出目录已存在或绑定过期 | 换新的准备、运行和自检路径；核对代码／数据版本，不覆盖旧证据 |
| 出现空名单、待核或部分结果 | 先核对条件、覆盖、来源关系和限制；不要为了非空修改主条件或订单 |
| 模型格式、引用或解释失败 | 保留当轮原输出和工具证据，先分清内容错误与输出契约问题，再做有针对性的修改 |
| 访谈窗口未开放、模型调用不可用 | 保留实际错误和待补项，继续不依赖该入口的工作；不能用手写回答代替真实运行 |

未通过不阻断下一周材料解锁，核心缺项须在答辩前补齐。使用后续 checkpoint 时保留原提交并说明采用范围，不能把参考结果登记为自己已完成的开发。

## 报错对照表

出错时先按这四步排查，再查下表：

1. **看原文**：完整读错误码和位置，不要只看到“失败”就重跑。
2. **分层**：判断问题在哪一层：自己的命令和配置、网络和模型服务，还是业务内容。
3. **缩小范围**：用最小的一步验证，比如只跑不调模型的检查命令，或看这次运行留下的记录。
4. **留证据再求助**：记下运行的命令、错误码和试过的办法。半小时还没解决，就带着这些发到群里。

报错一般在终端最后一行，或者结果 JSON 的 `code`、`status` 字段。Agent 的模型错误写在 `result.summary` 里。

| 错误码或现象 | 原因 | 下一步 |
| --- | --- | --- |
| `UnicodeDecodeError: 'gbk' codec can't decode` | Windows 没开 UTF-8 模式 | 执行 `setx PYTHONUTF8 1`，重开 PowerShell |
| `FileNotFoundError`，路径以 `manifest.json` 结尾 | `prepare.json` 的 `raw` 或 `w04_cleaned` 路径不对 | 核对路径，`raw` 指向解压后的数据目录 |
| `FileNotFoundError`，发生在 `service-call` | 准备目录或 home 被移动、文件被删 | 用现有准备目录重新 `bind` 到新 home；文件缺失就重新 `prepare` |
| `NEW_OUTPUT_REQUIRED`、`NEW_CHECK_OUTPUT_REQUIRED` | 输出路径已存在 | 换新编号，旧目录保留 |
| `MODEL_TODO_FILL_CUSTOMER_SOURCE` | YAML 还有 `TODO` | 填完三个 `slots`，删掉三处 TODO 注释 |
| `MODEL_SOURCE_MISSING` | `solution.py` 同目录没有 `member.linkml.yaml` | 核对 `code` 路径，YAML 和它放一起 |
| `MODEL_REQUIRED_CLASS:类名` | 删掉了核心类 | 恢复 `Member`、`SourceAccount`、`Store` |
| `CalledProcessError`，命令含 `gen-sqla` | YAML 引用了没有定义的字段名 | 核对 `slots` 里的名字 |
| `INSTANCE_INVALID:类:行:字段:说明` | 某行数据不符合字段定义，常见是必需的字段没进 `slots`，或类型不对 | 按错误里的类和字段定位，修 YAML 或函数返回值，不手改生成文件 |
| `MISSING_REFERENCE:ID` | 关系指向不存在的账户或门店 | 核对函数返回的账户 ID、门店 ID |
| `REGISTRATION_PROVENANCE_MISMATCH` | 会员的 `registered_stores` 与来源账户的注册门店不一致 | 改 `member_attributes`，不用购买门店填 |
| `SOURCE_MUST_HAVE_ONE_FINANCIAL_OWNER` | 一个来源账户没有归属，或归属了多次 | 核对函数返回的 `source_ids` |
| `CUSTOMER_IDENTITY_RULES_REQUIRED`、`CUSTOMER_MEMBER_ADAPTER_REQUIRED`、`CUSTOMER_CONTACT_RULES_REQUIRED` | 对应函数还是 TODO | 按第 2、3 步完成函数 |
| `KeyError: 'verified_singletons'` 这类 | 函数返回值缺字段 | 对照第 2、3 步的返回结构补齐 |
| `literal_error`，提到 `relation` | `relation` 不是 `same`、`different`、`unresolved` | 改取值 |
| `EVIDENCE_SOURCE_NOT_FOUND`、`SINGLETON_SOURCE_NOT_FOUND` | 账户 ID 不存在，常见是漏了 `CRM:`、`POS:` 前缀 | 用 `accounts` 里的 `source_id` |
| `DUPLICATE_EVIDENCE_ID` | `evidence_id` 重复 | 每条依据一个编号 |
| `IDENTITY_SELF_EDGE` | 一条依据的两端是同一个账户 | 去掉这条，或核对字段 |
| `MAPPING_VERSION_REQUIRED` | `rule_version` 为空 | 填规则版本 |
| `C3_BASE_REQUIRED` | 清洗结果不是 W04 c3 版本，或 `w04_cleaned` 填成了原始 CSV 目录 | 换成 c3 的清洗输出目录 |
| `W04_SOURCE_VERSION_MISMATCH`、`W04_CLEANED_HASH_MISMATCH` | 清洗结果与源数据或 manifest 对不上 | 用未改动的清洗结果，或重新生成；不改哈希 |
| `PUBLIC_SOURCE_HASH_MISMATCH:文件名` | 数据文件被改动 | 重新解压数据 ZIP |
| `CUSTOMER_CODE_CHANGED_REPREPARE_REQUIRED`、`MODEL_SOURCE_CHANGED_REPREPARE_REQUIRED` | 准备之后改了代码或 YAML | 重新 `prepare` 到新目录，再 `bind` 到新 home |
| `EXISTING_BINDING_PRESERVED_USE_NEW_HOME` | 这个 home 已经绑定过 | 换新 home |
| `MEMBER_DEPENDENCY_VERSION_CHANGED_REBIND_REQUIRED` | 绑定后依赖文件变了 | 改的是代码、YAML 或准备输入就重新 `prepare`；否则重新 `bind` 到新 home。都要 `init` |
| `MEMBER_TOOL_CONTRACT_FAILED` | 请求不合格式：字段类型不对（`store_id` 要字符串，`value` 要数字）、没有 `metric_filters`、窗口不对、`store_id` 和 `store_ids` 同时填 | 对照[圈选支持的条件](06_输入与工程说明.md#圈选支持的条件)改请求 |
| `KeyError: 'name'` | 请求文件缺 `name` 或 `args` | 用模板的结构 |
| `STORE_NOT_FOUND` | 门店 ID 不在门店表 | 核对门店 ID |
| `TIER_VALUE_NOT_IN_DATA` | 等级取值不在数据里 | 用返回的 `known_tiers` |
| `REPREPARE_POLICY_FOR_REFERENCE_DATE` | 参考日与准备批次不同 | 用 `2026-09-01` |
| `CONDITION_NOT_SUPPORTED` | 请求里申报了不支持的条件 | 这是预期行为，不给名单，向用户说明缺口 |
| `COMPARISON_METRIC_NOT_SUPPORTED` | 两期对比用了比率类或月度类指标 | 换可加总的指标 |
| `status: unsupported`，`reason` 是“指标未定义” | `metric` 不在当前指标库 | 核对指标 ID |
| `status: not_found`，有 `member_id` | 统一 ID 不存在，常见是模板占位没换 | 从 `state/mapping.json` 取实际 ID |
| `MODEL_NOT_CONFIGURED` | 3 个模型环境变量没有都设置 | 在当前终端重新执行第 0 步的设置 |
| `MODEL_URL_INVALID` | 地址不是 https，或带了账号、参数 | 用服务提供的完整 https 调用地址 |
| `MODEL_HTTP_401` 这类 | 模型服务拒绝请求 | 核对地址、模型名、密钥 |
| `MODEL_NETWORK_ERROR` | 调模型时网络断了 | 确认网络和模型服务，重新提问，保留这次失败记录 |
| `MODEL_TIMEOUT`、`MODEL_TURN_TIMEOUT` | 单次调用超时，或一轮超过 600 秒 | 单次慢就设 `FDE_MODEL_TIMEOUT=180`；问题过大就拆开问 |
| `MODEL_OUTPUT_TRUNCATED` | 输出被截断 | 调大 `FDE_MODEL_MAX_TOKENS` 后重试 |
| `CALL_LIMIT` | 一轮调用次数到上限 | 缩小问题，保留记录 |
| `SESSION_INTERRUPTED` | 上一轮运行中被中断 | 这个会话不能续，去掉 `--session` 新开，A 组两问都要在新会话重做 |
| `CANDIDATE_NOT_DISPOSED` | 本轮要建议，名单里有人既没有建议也没有不建议记录 | 看 Agent 是否逐人查了详情、关联记录和知识；问题写清要逐人给建议，同题回归 |
| `TASK_SCOPE_REQUIRED` | 有圈选名单，结果缺 `task_scope` | 输出格式问题，保留原输出，重新提问；多次出现换模型 |
| `NON_RECOMMENDATION_REASON_UNSUPPORTED`、`NON_RECOMMENDATION_REQUIRES_INCOMPLETE` | 不建议的理由没有当轮证据支持，或待核类理由却声称完成 | 保留原输出，核对引用的详情是否真有禁止或待核；不要改结果凑通过 |
| `validation_passed` 为 `false`，`status` 是 `incomplete` | 最终回答没过程序校验，`validation_code` 写了原因；`summary` 换成程序的固定摘要，模型原答在 `model_claim` | 保留原输出和工具结果，分清内容错误和输出约束问题，再同题回归 |
| `MODEL_EXPORT_REQUIRES_CUSTOMER_CODE_AND_CURRENT_BINDING` | `export.json` 缺字段 | 填齐 4 个字段 |
| `EXPORT_BINDING_PREPARED_MISMATCH` | `prepared` 和 `binding` 不是同一批 | 用同一批准备目录和绑定 |
| `block2_report_version_agreement` 为 `false` | 报告的版本与准备结果不同 | 按第 6 步改 `data_version`、`rules_version` |
| `block2_original_evidence_and_changes` 为 `false` | 证据列表或 `change_log` 为空，或文件不在提交目录 | 补内容，路径相对提交目录 |
| `block2_acceptance_boundary` 为 `false` | `formal_acceptance` 不是 `false`，或 `pending` 没有 `precise_person_total` | 恢复模板值 |
| `model_current_relative_binding` 为 `false` | 提交不是用当前绑定导出的 | 重新导出到新目录 |
| `REQUEST_TEACHER_ABSOLUTE_PATH:文件` | `requests/` 里有 `/Users/`、`/home/` 开头的路径 | 改成相对路径 |

改了代码、YAML 或准备输入后，都从 `prepare` 重走：新准备目录、新 home、`init`、重新导出、重新自检。
