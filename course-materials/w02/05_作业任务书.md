# W02 作业：形成有依据的业务模型，并让 Agent 使用

> v0.22｜2026-11-01。按独立试做补无 W1 复制命令和边界、截断与超时恢复、核查常见偏差，要求不变。v0.21｜2026-11-01。按试做补无 W1 路径、pip 警告说明和模型连接检查，要求不变。v0.20｜2026-11-01。作业路线细化到照着能做完，补上改进提取方法和补全文档两步，要求不变。v0.19｜2026-11-01。作业路线第 2 步加选看的访谈参考入口，要求不变。v0.18｜2026-11-01。加“作业路线”和“报错对照表”，要求不变。v0.17｜2026-10-20。两份人工整理的文档，加程序与运行记录。配套工程包为 `w02-agent-0.5.4`；安装与操作见材料使用说明。正式提交渠道和开放时间以班期通知为准。

## 本周要完成什么

从 W1 的问题和旧项目材料出发，通过多角色访谈取得信息，用 AI 帮助提取，再由自己核查和建模。最后把业务模型说明提供给 Agent，检查它是否正确使用这些业务认识。

本周学习顺序是：V04 学本体基础与人工建模，V05 学信息提取、核查与业务模型完善，V06 学接入 Agent 与效果验证，V08 串起完整作业路径。

业务模型采用自然语言、小表格或草图组织，不要求填写 `ontology.yaml`，也不要求单独提交一张图。JSON 用于保存程序提取的候选信息；学员需要读懂和核查结果，不必从头编写通用调用程序或手工维护状态枚举、哈希和运行编号。

## 作业路线

照着这一节从头做到尾，就能走完从领取到提交的全部操作。这里走“修改课程工具”路线；开发自己 Skill 的同学，第 3～7 步按自己的方法做，并保留同等的输入、请求和回答记录，其余步骤照做。业务判断要自己做，这一节只告诉你在哪里做、做到什么程度。要求以本任务书正文为准。

下面的命令都在工程目录运行。Windows 把 `.venv/bin/python` 换成 `.venv\Scripts\python.exe`。

**整体顺序**：准备环境 → 访谈并导出 → 填写配置 → 启动提取 → 分组核查 → 确认业务模型 → 改进提取方法 → 同题对照 → 补全两份文档 → 自查提交

提取走 `w02_workflow.py`，确认业务模型后接 `w02_knowledge.py`。工作流已经包含提取，不用再跑 `w02_interviews.py`，也不用照 `docs/w02_extraction/README.md` 操作；那份文档只在改提示词、转换导错的访谈记录时查阅。

### 第 1 步：准备环境

W1 的工程和提交快照保留不动。把 `fde-student-w02-0.5.4.zip` 解压到一个新目录，这个目录就是本周的工作目录。打开终端，进入这个目录：

```sh
cd /你解压的路径/fde-agent-w02
python3 -m venv .venv
.venv/bin/python -m pip --isolated install -r requirements.txt
```

需要 Python 3.11 以上。Windows 用 `python -m venv .venv`；中文 Windows 先按工程 README 设置 `PYTHONUTF8`。

配置自己的模型。下面的值换成你自己的，模型要支持原生工具调用：

```sh
export FDE_MODEL_URL="https://你的服务地址/v1/chat/completions"
export FDE_MODEL_NAME="你的模型名"
export FDE_MODEL_KEY="你的密钥"
```

Windows PowerShell：

```powershell
$env:FDE_MODEL_URL="https://你的服务地址/v1/chat/completions"
$env:FDE_MODEL_NAME="你的模型名"
$env:FDE_MODEL_KEY="你的密钥"
```

把 W1 的 fit-gap 复制过来，预检要用。已完成 W1 的，用下面的命令：

```sh
mkdir -p artifacts/w01
cp /你的W1工程路径/artifacts/w01/product_fit_gap.json artifacts/w01/
```

没有完成 W1 的，把材料包的 `W01_checkpoint` 复制过来作为起点：

```sh
mkdir -p artifacts/w01 docs/w01
cp /你的材料包路径/W01_checkpoint/artifacts/w01/product_fit_gap.json artifacts/w01/
cp /你的材料包路径/W01_checkpoint/artifacts/w01/product_fit_gap.xlsx artifacts/w01/
cp /你的材料包路径/W01_checkpoint/docs/w01/project_assessment.md docs/w01/
```

在访谈与核查记录里写明采用了哪些部分。W1 的沈总访谈、立项判断和三份运行证据不用在开始 W02 前补完，不阻断本周，但要在结营答辩前补齐；本周提交里写明哪些还没补。

- **算完成**：安装退出时没有报错，`artifacts/w01/product_fit_gap.json` 已存在。pip 提示缓存目录不可写只是警告，安装成功就可以继续。
- **容易卡**：环境变量只在当前终端有效，新开终端要重新设置。工程 README 前半部分讲的是 W1 产品，本周不用重做 W1 的验证。密钥不要写进任何文件。

### 第 2 步：访谈并导出记录

先回看 W1 的待核实问题，写下这次要弄清什么。必访老周、小林、陈姐，王经理选访。不知道怎样开口，可以看[访谈参考](08_访谈参考.md)（选看）。

每场访谈结束后，在访谈网页选中这场会议，点“导出提取用记录”，保存到工作目录的 `artifacts/w02/sources/`，文件名用自己认得出的，比如 `lao-zhou.json`、`xiao-lin.json`、`chen-jie.json`。

- **算完成**：三位必访都有导出文件。至少有一组针对同一业务问题、会影响判断的不同说法，这组会在第 9 步写进分歧。
- **容易卡**：不要选“完整公开记录”。提问次数有限，一次问一件事，先想好再问。

### 第 3 步：初始化并填写配置

```sh
.venv/bin/python tools/w02_workflow.py init
```

这会生成 `customer/w02/` 下的配置，以及 `docs/w02/` 下的两份文档模板。已有文件不会被覆盖。

打开 `customer/w02/workflow.json`，只改 `goal`，写本轮要核实什么：

```json
"goal": "弄清……的定义和范围，以及……在实际工作中怎样做。"
```

打开 `customer/w02/extraction.json`，改三处：

```json
"sources": ["artifacts/w02/sources/lao-zhou.json", "artifacts/w02/sources/xiao-lin.json", "artifacts/w02/sources/chen-jie.json"],
"focus_questions": ["需要保留哪些定义和条件？", "每位角色实际怎样做？", "哪些说法不同，哪些还没有依据？"],
"profile": "compatible"
```

`focus_questions` 换成你自己的问题。`profile` 默认用 `compatible`；端点支持 `response_format` 可用 `json-object`；DeepSeek 接口可用 `deepseek-json`。

再打开 `customer/w02/extraction_prompt.txt`，补上你对这批材料的处理要求，比如保留角色和条件、分开提问和陈述。这是本周方法开发的起点。

然后检查配置，这一步不调模型：

```sh
.venv/bin/python tools/w02_workflow.py inspect
```

- **算完成**：返回 `goal`、`materials`、`batches`、`skill`、`profile`，`materials` 等于你的文件数。
- **容易卡**：`sources` 留空会报 `SCHEMA_INVALID`。三位必访要写在同一个 `sources` 里一起跑，不要一人跑一轮再替换：同题对照和预检只认一次提取，缺人会报 `REQUIRED_ROLES_MISSING`。

### 第 4 步：启动提取

```sh
.venv/bin/python tools/w02_workflow.py start
```

这条命令要等几分钟，等它自己返回，中途不要按 Ctrl-C。

- **算完成**：返回 `"status": "awaiting_review"`，`pending` 里是这一组候选。
- **容易卡**：返回 `failed` 时看 `error`，查文末报错对照表。随时可以用 `tools/w02_workflow.py status` 看当前状态。

**输出被截断和超时要一起看。** `batch_chars` 是每批的材料字符数，不是模型输出的 token 数；调小它可以减少截断，但批次会变多，提取总时长也更容易超过一次推进的 600 秒。

1. 打开这次运行的 `*.attempts.json`，看 `finish_reason`、用量和耗时。
2. `finish_reason` 是 `length`，先提高输出上限，再把 `batch_chars` 调到中等。课程方用一个国内模型试做时，下面这组才跑通，换了模型要按自己的结果调整：

```sh
export FDE_MODEL_MAX_TOKENS=32768
export FDE_MODEL_TIMEOUT=180
```

同时把 `customer/w02/extraction.json` 的 `batch_chars` 改成 2000，运行 `inspect` 看批次数，再重新 `start`。这组设置下每批要等更久，批次太多时仍会超过 600 秒，这时加大 `batch_chars` 或减少本轮 `sources`。Windows 用 `$env:FDE_MODEL_MAX_TOKENS="32768"`。

3. 换配置重新 `start` 会产生新编号，旧运行保留。

### 第 5 步：分组核查（这一步会循环几轮）

生成报告：

```sh
.venv/bin/python tools/w02_workflow.py report
```

用浏览器打开返回的 `report.html`，在“逐项核查”里逐条对照原文，看有没有漏条件、改原意，或把推断当成原话。再从本轮目标反查有没有遗漏。然后写反馈并继续：

```sh
.venv/bin/python tools/w02_workflow.py review --feedback 'CLM-编号 采用；CLM-编号 修订为……，因为……；CLM-编号 暂不采用，因为……；还漏了……'
.venv/bin/python tools/w02_workflow.py resume
```

编号和内容换成报告里的实际候选。反馈较长时，写进文本文件，用 `review --feedback-file feedback.txt`。

- **算完成**：`resume` 返回 `awaiting_review` 就再核查下一组；返回 `awaiting_apply` 就进入第 6 步。
- **容易卡**：`active`、`failed` 是整轮任务的状态，不是每条候选的状态。`reviewed` 只说明这几条给过反馈，不等于已采用。不要只写“同意”，要写清采用、修订或暂不采用及理由。另外留意三类常见偏差：把“这一批没看到”写成“全部材料都没有”；把不同环节的职责或“不掌握”当成冲突；把角色复述的话当成他本人的说法。

### 第 6 步：确认业务模型

```sh
.venv/bin/python tools/w02_workflow.py report
```

在报告“模型修改”里核对旧模型和草稿：原有内容有没有丢，修改有没有依据，两种说法和未知是否保留。要改就：

```sh
.venv/bin/python tools/w02_workflow.py revise --feedback '哪一处要改，依据是什么'
.venv/bin/python tools/w02_workflow.py resume
```

确认后：

```sh
.venv/bin/python tools/w02_workflow.py apply
```

- **算完成**：状态是 `completed`，`docs/w02/business_model.md` 和 `docs/w02/interview_notes.md` 已更新。**到这一步才算采用。**
- **容易卡**：草稿里关于权限、材料和完成情况的说法要逐条核对，分清角色原话、自己的选择和运行事实；写错了用 `revise` 退回，不要直接改运行记录。本轮开始后手工改过这两份文档，`apply` 会停下，要对照当前版本重新组织任务。所以等 `apply` 之后再手工修改。

### 第 7 步：改进提取方法并验证

只跑默认配置不算完成提取。回看第 5 步：哪类信息漏了、错了？把问题对应到 `customer/w02/extraction_prompt.txt`、`customer/w02/extraction.json` 的 `focus_questions`，或 `customer/w02/skills/extract-business/SKILL.md`，改一处，再用同样的材料和模型跑一轮：

```sh
.venv/bin/python tools/w02_workflow.py inspect
.venv/bin/python tools/w02_workflow.py start --previous latest
```

之后按第 5、6 步核查和确认。比较前后两次运行的候选，运行记录在 `artifacts/w02/runs/` 下各自的 `candidates.json`：要改的问题有没有变好，原来对的内容有没有变差。

把这些写进 `docs/w02/interview_notes.md` 的“提取方法开发与验证”：改了什么、为什么改、前后结果怎样、最后的取舍。第一版已经符合要求时，写明验证依据即可，不必故意制造错误。

- **算完成**：记录里能看出方法确实改过或验证过，并引用了运行记录。
- **容易卡**：只换同义词、加一句“更准确”不算方法开发。

### 第 8 步：同题对照

先查最后一轮的提取运行：

```sh
.venv/bin/python tools/w02_workflow.py status
```

把返回的 `extraction_run` 路径填进下面第一条命令，然后运行：

```sh
.venv/bin/python tools/w02_knowledge.py init --from-extraction artifacts/w02/runs/RUN-实际编号/run.json
.venv/bin/python tools/w02_knowledge.py inspect
.venv/bin/python tools/w02_knowledge.py compare --question '自己要核实的业务问题' --expected '希望采用的定义或应保留的未知'
```

问题从自己的访谈里选，要能检验青禾特有的定义、关系或条件，不要在问题里提前写答案。

打开返回路径同目录的 `request.json`，确认业务定义进了请求；再看未提供和提供业务模型两次的回答。把判读写进 `docs/w02/interview_notes.md` 的“Agent 使用与实际判读”：选了什么问题、为什么、回答具体增加或改变了什么。

- **算完成**：有一组成功的对照运行，判读已写好。结果是 `needs_review` 属于正常。
- **容易卡**：业务模型改过后要重跑受影响的问题。不要只凭“回答更谨慎”判断有效。

### 第 9 步：补全两份文档

AI 的草稿不等于完成，提交前对照下面逐节检查。模板见[业务模型说明模板](07_业务模型说明模板.md)和[访谈与核查记录模板](06_访谈与核查记录模板.md)。

`docs/w02/business_model.md`：

| 节 | 写什么 | 写到什么程度 |
| --- | --- | --- |
| 要回答的问题与范围 | 本轮要回答的业务问题，哪些不纳入 | 别人读完知道这份模型管什么 |
| 对象、属性与关系 | 对象的业务定义和相互关系 | 容易混淆的名称解释清楚，不只摘原话 |
| 规则、条件与候选动作 | 规则的适用条件；希望做的动作 | 候选动作不写成已经实现或已获授权 |
| 依据与建模选择 | 哪些来自客户，哪些是自己的选择 | 有其他方案的地方写明选择理由 |
| 未知与分歧 | 没确定的内容，不同说法并列 | 附来源和需要的依据，不补成结论 |

`docs/w02/interview_notes.md`：

| 节 | 写什么 | 从哪里取 |
| --- | --- | --- |
| 访谈目标与记录 | 每位角色为什么访谈、取得什么、原始记录位置 | `artifacts/w02/sources/` |
| 干系人地图 | 能拍板、能否决、需要知道、在意什么、来源、下一步 | 自己的访谈，没问到的写未知 |
| 重要信息的核查与取舍 | 影响模型的候选及取舍理由 | 第 5 步的反馈和报告 |
| 分歧与下一步 | 至少一组分歧：各方说法、时间范围含义、向谁要什么 | 自己的访谈 |
| 提取方法开发与验证 | 第 7 步的内容 | 运行记录 |
| Agent 使用与实际判读 | 第 8 步的内容 | `knowledge_runs/` |
| 当前业务判断与 W1 接续 | 现在的判断、依据、限制；受影响的 fit-gap 条目及理由，沿用原编号；没有受影响项时写核对依据 | W1 提交快照 |

- **算完成**：两份文档没有“待填写”，每项重要判断都能找到来源。
- **容易卡**：修改 fit-gap 时，不要覆盖 `artifacts/w01/product_fit_gap.json`，修订版保存到 `artifacts/w02/product_fit_gap.json`，可以复制 W1 的 JSON 后直接改，沿用原编号；用 checkpoint 的，删掉“沈总首轮访谈（参考稿占位）”这类没有消息位置的证据，或换成自己的记录。提交前通读两份文档，删掉“待填写”和“尚未完成”这类阶段性文字。文档改了业务模型，要重跑第 8 步受影响的问题。


结果是 `needs_revision` 时看 `issues`：`code` 是问题，`path` 是位置，`next_step` 是要做什么，按这些补齐，重跑时把文件名改成 `precheck-v2.json`。结果是 `ready_for_review` 后打包：

- **算完成**：解压后能直接看到 `docs/`、`customer/`、`artifacts/`，预检是 `ready_for_review`。这只说明结构可供审阅，不代表通过。
- **容易卡**：不要放 `.venv`、`.runtime`、密钥和未改动的工程文件。

## 学员实际做 5 件事

### 1. 带着问题访谈，保存原始记录

必访老周、小林、陈姐，王经理本周选访。从各人的实际职责出发，追问具体工作、规则、例外、理由以及不同说法的依据。原始导出记录保留在自己的客户仓库，引用应能定位到具体会议、消息或原文段落。

至少选择一组针对同一业务问题、会影响当前判断的不同说法或解释，作为需要交叉核实的分歧，写清各方来源、适用范围与下一步证据。先核对时间、范围和含义：两种说法可能同时成立，不要求当周证明谁对谁错。各方都说不知道、相同说法或互补信息本身不算冲突，不为了凑数量制造分歧。

### 2. 设计提取方法，用 AI 实际处理材料

先明确自己的调查问题、输入材料和处理要求，再把方法落实到提示词、Skill 或必要代码，实际处理自己的青禾访谈。可以选择两条等价路线：

- 修改课程工具：使用已有的调用、来源检查、人工停点和记录保存能力，根据自己的业务需要修改提示词、Skill 或必要代码。操作入口见包内 `docs/w02_workflow/README.md`。
- 开发自己的 Skill：可以借助 Codex 等 coding Agent 设计方法，组织提示词、参考资料或脚本并实际运行。可沿用课程后续的 Agent 使用验证工具，无需重写访谈服务或整套工程。

提示词开发也属于方法开发，不强制修改 Python。材料路径与本轮目标属于运行准备，还需说明方法怎样处理自己的材料，例如区分提问、陈述与未知，或保留角色和适用条件。只换同义词、加一句“更准确”或只提交一份 SKILL.md，不足以证明完成。

检查实际请求或运行记录，确认材料与方法确实进入处理，并按设计要求核查输出。修改已有方法时，尽量固定材料、模型和其他设置比较前后结果，也检查原来正确的内容是否受影响；自建初稿已符合要求时，说明验证依据即可，不必故意制造错误版本。出现问题再迭代，改动无效也如实记录并解释取舍。在访谈与核查记录中引用方法版本、验证结果并写出判断，不另交开发报告。两条路线都由学员负责业务核查，不能用 AI 自报成功代替。

查看程序保存的候选 JSON 和来源，检查有没有漏掉条件、改变原意或把推断当成原话。遇到超时、空结果或格式不符时，先查看运行记录，修正相应设置后重跑；没有取得完整结果时，不能当作已完成提取。

### 3. 核查信息，形成业务模型说明

分组核对准备采用的信息，保留条件、分歧和未知，把采用、修订或暂不采用的理由反馈给 AI。审阅它提出的模型修改草稿，确认后再保存。可以借助 AI 起草，再由自己决定和解释：

- 本次需要回答什么业务问题，建模范围是什么。
- 需要哪些对象及定义、属性、关系和规则，为什么这样划分。说明对象之间怎样联系、规则在什么条件下适用，以及这些认识怎样帮助回答本轮业务问题；不只摘录原话或罗列未知。
- 哪些内容来自客户说法，哪些是自己为当前问题作出的建模选择。
- 哪些动作只是候选需求，哪些定义或条件仍需核实。

重点核查最终准备采用的信息是否有原文支持、条件是否完整；未采用的候选可以保留，不要求为所有候选逐条点击确认。已有核查可引用其记录，新增或发生变化的内容再核查。

依据可以引用原始记录或提取结果，不必在候选、纪要、模型中反复抄写同一段原话。业务模型说明是单客户初稿，不要求取得后续周才开放的数据或解决全部冲突。

### 4. 让 Agent 使用，并判断效果

从自己的青禾访谈中选择问题，先写明希望回答依据哪些定义、保留哪些不确定性。在模型、问题和其他条件尽量一致的情况下，比较未提供与提供业务模型说明时的实际回答。

选题应能检验客户特有的定义、关系、流程或条件，避免在问题中提前列出预期答案。核对提供业务模型后，回答具体增加、改变或纠正了什么；未提供组也可能谨慎或部分正确，不必刻意制造失败。

检查两个方面：实际请求里是否出现了采用的业务定义；回答是否正确使用定义、保留分歧和未知。不要只看文件存在、加载提示或调用成功，也不要仅以措辞更谨慎判定知识应用有效。

程序负责保存本次使用的文档版本、实际请求与回答，学员在访谈与核查记录中写出自己的判读。出现错误时，定位到信息、模型说明、上下文组织或能力边界，修改并重跑；结果已经正确时，说明依据即可，不要求人为制造错误。

不规定固定题型，也不要求重复一套公共样例。选题应能检验自己的业务定义及有关的不确定性；材料中仍未知的答案不能被编成结论。业务模型中的候选动作也不能作为已经计算、查询或执行的证据。

### 5. 形成当前判断，接续 W1

记录现在理解了什么、仍有哪些分歧、下一步向谁取得什么依据。将干系人地图作为访谈与核查记录的一节，区分职位、实际权限、角色观点与本人推断。

对照 W1 的立项和 fit-gap 判断，仅修订受新增证据影响的条目，沿用原编号、保留前周快照，说明变化及理由；没有受影响项时说明核对依据。使用 W1 checkpoint 的，在参考 fit-gap 上按同样方式修订。

## 怎样判断完成

验收围绕四个问题：

1. 访谈是否取得具体、有用的信息，是否针对角色与已有回答继续追问。
2. 采用的信息是否有依据，限定、分歧和未知是否保留。
3. 业务模型是否清楚，能否解释关键建模选择。
4. Agent 是否实际使用这些业务认识，能否根据请求与回答判断效果。

技术门槛看方法开发及实际验证、可追溯依据、业务模型和使用对照；交付门槛看必访覆盖、有来源的分歧及核实计划、干系人判断和 W1 接续。两项分别判定，不用平均分抵消缺项。自动预检只能检查能够确定的文件和记录关联，业务含义仍需人工审阅。

工程包内 `tools/check_w02.py` 检查两份文档和运行记录的结构与关联。用法见包内 `docs/w02_check/README.md`。使用自己的实现时保留同等的原始输入、请求与回答；自动工具无法识别的记录由教师检查和复跑，不按工具格式直接判为不合格。

未完成项按反馈补齐，不阻断后续材料解锁，核心项需在结营答辩前完成复核。截止后提供的参考状态用于继续学习，不替代自己的访谈、核查和理解说明。W3 深入指标及范围，W5 完善实体与业务工具，W8 接入客户动作，本周不提前完成这些任务。

## 报错对照表

出错时先按这四步排查，再查下表：

1. **看原文**：完整读错误码和位置，不要只看到“失败”就重跑。
2. **分层**：判断问题在哪一层：自己的命令和配置、网络和模型服务，还是业务内容。
3. **缩小范围**：用最小的一步验证，比如只跑不调模型的检查命令，或看这次运行留下的记录。
4. **留证据再求助**：记下运行的命令、错误码和试过的办法。半小时还没解决，就带着这些发到群里。

| 错误码或现象 | 原因 | 下一步 |
| --- | --- | --- |
| `SCHEMA_INVALID`，位置在 `extraction.json/sources` | `sources` 为空 | 按作业路线第 3 步填写 |
| `SCHEMA_INVALID`，`extraction_run` 不为空 | 模型返回的提取结果格式不符合要求，比如字段缺失或 JSON 错位 | 打开 `extraction_run` 那份 `run.json`，看 `error.message` 里的检查位置；这种失败不能 `resume`。先重新 `start`，模型每次输出不同，常能过；连续失败再查 `extraction_prompt.txt` 是否改动了输出格式要求 |
| `REQUIRED_ROLES_MISSING`，`path` 列出角色 | 同题对照采用的这次提取，`sources` 里缺这些必访角色的本周记录 | 没访谈的先补访；已访谈的把三位记录都写进 `extraction.json` 的 `sources`，`start --previous latest` 跑完并 `apply`，再 `w02_knowledge.py init --from-extraction 新路径 --replace`，重跑 `compare` |
| `SOURCE_NOT_FOUND`，`path` 是 `artifacts/w01/product_fit_gap.json` | 工作目录里没有 W1 的 fit-gap | 按第 1 步复制过来，再运行预检 |
| `CONTRACT_VERSION_UNSUPPORTED` | `sources` 里有完整公开记录 | 重新导出提取用记录，或运行 `tools/w02_interviews.py convert 原文件 --output 新文件`，再改 `sources` |
| `SOURCE_NOT_FOUND` | 路径写错或文件不在 | 核对 `sources` 的相对路径 |
| `MODEL_NETWORK_ERROR` | 没拿到模型服务的响应，连接没建立或中途断开 | 运行下面的连接检查，修好后直接运行 `resume`，已给的核查不丢；仍失败就把检查结果和 `status` 发到群里 |
| `MODEL_TIMEOUT` | 单次调用超时，或一次推进超过 600 秒 | 单次慢就设 `FDE_MODEL_TIMEOUT=180`；然后运行 `resume` 接着跑；提取批次多的，减少批次后重新 `start` |
| `MODEL_OUTPUT_TRUNCATED` | 输出被截断 | 按第 4 步「输出被截断和超时要一起看」调整后重新 `start` |
| `MODEL_HTTP_401` 这类 | 模型服务拒绝请求 | 核对地址、模型名、密钥 |
| `HUMAN_ACTION_REQUIRED` | 当前状态不能 `resume` | 跑 `status`：`awaiting_review` 去路线第 5 步，`awaiting_apply` 去路线第 6 步，`failed` 看 `next` 提示：模型没回答的失败直接 `resume`，其他失败重新 `start` |
| `SESSION_INTERRUPTED` | 运行中被中断 | 不能续跑，重新 `start` |
| `WORKSPACE_BUSY` | 上次进程没退出，或锁文件没清 | 确认没有进程在跑，删除 `artifacts/w02/.workflow.lock` |
| `OUTPUT_EXISTS`，位置在 `customer/w02/extraction.json` | `w02_interviews.py init` 要新建的文件已经有了，第 3 步的 `w02_workflow.py init` 已经建过 | 不用处理，也不用再运行这条命令，直接改现有文件 |
| `OUTPUT_EXISTS`，位置在 `customer/w02/knowledge.json` | `w02_knowledge.py init` 重复运行 | 换用另一次提取时加 `--replace` |
| `SCOPE_MISMATCH` | 手改配置时只改了 `extraction_run` | 用 `init --from-extraction … --replace` |
| 访谈里出现「这一轮是系统没能组织好回答」 | 访谈系统这轮没组织好回答，不计提问次数 | 原样重发，或拆成小问题 |

网络、超时、服务端 5xx 这类模型没回答的失败，用 `resume` 接着跑，核查不丢。其他失败要重新 `start`：会重新提取，候选编号可能变，核查判断要对照新候选重新给，旧记录保留。失败的任务不能 `apply`。

**模型连接检查**：不发密钥，也不调用模型，只看能不能连上模型服务。

```sh
python - <<'EOF'
import os, time, urllib.error, urllib.request
t = time.time()
try:
    urllib.request.urlopen(urllib.request.Request(os.environ["FDE_MODEL_URL"], b"{}", {"Content-Type": "application/json"}), timeout=30)
    print("能连上")
except urllib.error.HTTPError as e:
    print("能连上，服务返回", e.code)
except Exception as e:
    print("连不上", round(time.time() - t, 1), "秒", type(e).__name__, str(e)[:200])
print("代理设置", [k for k in os.environ if k.lower().endswith("_proxy")])
EOF
```

看到“能连上”，返回 401、400 都算连通，问题在别处，请把结果发到群里。看到“连不上”，先检查代理和网络，或换一个网络再试。
