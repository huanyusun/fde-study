3. **先剖析，再下结论。** 在剖析入口实现逐字段统计（类型、缺失、取值分布或范围）和字典比对。每个异常都给证据：查询语句，或来源文件加 CSV 记录序号。原始文件只读保留。
4. **字典差异分三类。** 数据与字典、客户说法对不上时，逐处判断属于哪一类，写明影响、要修订什么、向谁核实。你自己在 W03 形成的认识也在核对之列，比如指标里按小样本写死的取值：
   - **字典过时**：数据是对的，字典或我们原有的认识没有跟上；
   - **映射错误**：字段里装的不是字段名说的东西，或者对字段的理解错了；
   - **数据暂缺**：这次导出里根本没有。
   
   类别不同，处理不同。字典过时要按实际数据写映射，并请客户确认；映射错误要改清洗和映射规则；数据暂缺不能当零，要写进覆盖说明和待补数据清单。
5. **访谈核实。** 老周和小林为本周必访：老周讲数据来源、导出方式、字段含义和已知问题；小林讲标签与备注的写法、哪些备注必须遵守，以及她的工作账怎么用。其他角色按缺口选择：卡种和门店注册的情况可以问陈姐，带上剖析结果会更具体；沈总的要求已经发在群里；王经理选访。带着剖析结果去问，不要只按字典逐项提问。数据看出来的和访谈听来的分开记录。
6. **写清洗规则。** 在 `cleaning_rules.yaml` 里写标签与备注的拆分、格式规范、字段映射、无效值和异常记录的处理；规则写成数据，由适配器读取执行。合法信息不能误删：带连字符的标签、字典里没有但经客户确认的标签都要保留；备注按完整的一条保留原文和来源，不拆成碎片；涉及触达限制的备注要全部识别出来。
7. **实现适配器，隔离而不是丢弃。** 完成字段映射，写出契约 CSV。不能接受的记录进隔离文件，带原因、来源文件、记录序号和完整原记录。在 manifest 里写覆盖说明：数据来源、时间范围、各类记录的隔离条数。
8. **全量导入并对账。** 每次都在新目录全量导入，不在旧库上追加；导入两次，结果一致。每类记录满足“读入＝接受＋隔离＋去重”，关键金额汇总前后一致；至少追一条合法记录和一条失败记录，说明它们各自落在哪里。
9. **按核实结果更新业务模型和指标库。** 对照本周数据与访谈，核查 W03 业务模型中的概念、对象关系和业务规则；只修订新证据影响的部分，保存 W04 完整模型。在 `model_changes.md` 中记录核对范围、修订前后、依据与来源、影响的指标及待核事项；经核对无需修改的，也说明核对结果，不为凑修改条数而改。纯字段格式问题在适配规则中处理；证据不足的保留为待核，不写成已确认。再让 38 项指标在导入后的库上运行：指标 ID 不变，按新证据修订受影响的定义，在 `metric_changes.md` 中写明修订前后、依据和来源，并引用相关模型修订记录，核对模型与指标是否一致。数字以本数据的实际值为准。
10. **写数据诊断报告。** 按必备章节写；至少完成一项小林工作账与 CRM 的对照，建议核对勿扰名单与触达限制备注；两边对不上时写成待核实事项，不凭一份快照就下定性结论。区分数据结论、访谈依据、推断和待核事项，写清这份数据覆盖不到什么，最后给出下一步核实清单。
11. **选第一个 demo 并实际跑通。** 结合本期业务目标、要验证的关键假设，以及导入后的实际数据和现有能力，选择第一个 demo。说明它服务哪项会员运营工作、为什么值得先验证，以及覆盖到哪里、有哪些异常、结果能否追溯；用实际运行证据限定结论。在导入后的青禾库上用运营 Agent 实际运行，保留提问、回答、查询和结果，如实标注 bad case。写 demo 方案，其中的 FDE 思维判断说明包括：关键假设、最小验证链路与选择依据、已有证据与待验证条件，以及继续、缩小范围、调整方向各自的条件。
12. **调优部分覆盖下的回答，然后提交。** 数据只覆盖一部分时，回答既不能把未知当零，也不能一律拒答。先定位问题出在协议、数据／SQL、工具、提示词／上下文还是 Harness 策略，每次只改一处；同一问题调优前后各跑一次，记录修改位置、内容和原因；没有改善也如实记录。导出 `demo_run.json`，运行公开预检后提交。

### 第 3 步：先剖析，再下结论

**要改的文件**：`customer/w04/solution.py` 的 `profile(tables, dictionary, context)`。

入参是这样的：`tables` 以文件名为键，比如 `tables['crm_order_export.csv']['fields']` 是字段名列表，`['rows']` 是记录列表，每条记录形如 `{'source_file': 文件名, 'source_row': 从 1 起的记录序号, 'raw': {字段名: 原文字符串}}`。`dictionary` 是字典全文，`context['data_version']` 是命令传入的版本。

要返回的结构，`fields` 每项必须有 `distribution` 或 `range` 之一，`anomalies` 的证据写 `query`，或写 `source_file` 加 `sample_rows`：

```json
{
  "contract_version": "w04-0.1.0",
  "data_version": "qinghe-w04-v1.1",
  "fields": [
    {"source_file": "文件名.csv", "field": "字段名", "inferred_type": "string", "total_count": 100, "missing_count": 3, "distribution": [{"value": "取值A", "count": 97}]},
    {"source_file": "文件名.csv", "field": "字段名2", "inferred_type": "integer", "total_count": 100, "missing_count": 0, "range": {"min": "1", "max": "9"}}
  ],
  "anomalies": [
    {"pattern": "这里写你发现的异常模式", "evidence": {"source_file": "文件名.csv", "sample_rows": [12, 34]}}
  ],
  "dictionary_differences": [
    {"source_file": "文件名.csv", "field": "字段名", "dictionary_claim": "字典怎么写", "actual": "数据实际怎样", "impact": "影响什么"}
  ]
}
```

逐字段统计可以直接写循环，下面这段是通用部分，异常和字典比对要你自己加：

```python
from collections import Counter

MISSING = ('', 'NULL', '-', '无')

def profile(tables, dictionary, context):
    fields, anomalies, differences = [], [], []
    for filename, table in tables.items():
        for field in table['fields']:
            values = [row['raw'][field] for row in table['rows']]
            present = [v for v in values if v not in MISSING]
            stat = {'source_file': filename, 'field': field, 'inferred_type': 'string',
                    'total_count': len(values), 'missing_count': len(values) - len(present)}
            counts = Counter(values)
            if 0 < len(counts) <= 30:
                stat['distribution'] = [{'value': v, 'count': n} for v, n in sorted(counts.items())]
            else:
                stat['range'] = {'min': min(present, default=None), 'max': max(present, default=None)}
            fields.append(stat)
    # 在这里加入：类型判断、异常发现、与 dictionary 的比对
    return {'contract_version': 'w04-0.1.0', 'data_version': context['data_version'],
            'fields': fields, 'anomalies': anomalies, 'dictionary_differences': differences}
```

运行：

```sh
.venv/bin/python tools/w04.py profile --source materials/data/qinghe-w04-v1.1 --dictionary materials/data/02_CRM数据字典_v2.3.md --code customer/w04/solution.py --output artifacts/w04/profile_report.json --data-version qinghe-w04-v1.1
```

- **算完成**：命令打印出报告内容，`artifacts/w04/profile_report.json` 已生成；每个 CSV 的每个字段都有一条统计；每个异常都能回到查询语句或记录序号。
- **容易卡**：空入口会报 `W04_PROFILE_UNIMPLEMENTED`。`anomalies` 和 `dictionary_differences` 都不能是空列表，只跑上面那段通用部分会报 `ValidationError`，加上你发现的内容后才能生成报告。`sample_rows` 是不含表头、从 1 起的记录序号，不是文本行号，字段内换行不增加序号。公开预检把空串、`NULL`、`-`、`无` 都算缺失。`--source` 目录下的 CSV 都会读进来，工作账也在其中，但公开样本里没有工作账，代码不能假定这两个文件一定存在，否则预检的 `execution` 层失败。异常的文字和序号要让预检认得出，核对方式见 `examples/w04/public-check/expected.json` 的 `anomalies`。原始文件只读，不要改。

### 第 4 步：字典差异分三类

**要改的文件**：`docs/w04/data_diagnosis.md` 的第二节表格。把第 3 步的 `dictionary_differences` 加上你和客户对不上的说法，逐条归入三类之一，一条写一行。每一行写到别人不用问你就能去核实：

| 列 | 写什么 | 占位示例 |
| --- | --- | --- |
| 类别 | 字典过时、映射错误、数据暂缺之一 | 字典过时 |
| 字段、差异与证据位置 | 字段名、字典怎么写、实际怎样、在哪看到 | `字段X`：字典写 A，实际是 B，见 `文件名.csv` 第 12、34 条记录 |
| 影响 | 影响哪个指标、哪项判断 | 影响指标 `指标ID` 的计算 |
| 修订对象 | 改映射、改清洗规则，还是写进覆盖说明和待补数据清单 | 改映射，待客户确认 |
| 取证对象 | 向谁核实 | 向某角色核实 |

你在 W03 形成的认识也要核对，比如指标里按小样本写死的取值：打开 `artifacts/w04/library/metrics.yml` 和 `.sql` 文件，对照第 3 步的取值分布看一遍。

这一步不用跑命令。

- **算完成**：剖析出的每处差异都归了类，四列都填了；还没核实的先标“待访谈”，第 5 步回来改。
- **容易卡**：归类决定处理方式。把字典过时当成数据错误去改数据，或把数据暂缺当成零，都属于核心错误。

### 第 5 步：访谈核实

打开访谈服务，按账号的 W04 开放状态进入。老周、小林必访，其他角色按缺口选。每个角色最多 2 次，每次 12 条学员消息；带证据继续讨论在原会话进行。不知道怎样开口，可以看[访谈参考](08_访谈参考.md)（选看）。

问之前，从第 4 步的表里挑出要核实的行，写成这样的问题，内容换成你自己的证据：

```text
我们在导出里看到 字段X 有 N 条记录是 B，字典写的是 A。这个字段实际记的是什么？什么时候开始这样记的？
```

老周那边问数据来源、导出方式、字段含义和已知问题；小林那边问标签与备注的写法、哪些备注必须遵守、工作账怎么用。不要只按字典逐项提问。

- **算完成**：老周、小林都有导出文件在 `artifacts/w04/interviews/`；第 4 步表格里能核实的都核实了，核实不了的继续标待核。
- **容易卡**：数据看出来的和访谈听来的分开记。访谈不到时可用课程方分发的补充材料，标明来源为课程方补充，它不能充抵必访记录。访谈服务失败时保留会话和请求编号，先刷新原记录，不反复创建会话。

### 第 6 步：写清洗规则

**要改的文件**：新建 `artifacts/w04/cleaning_rules.yaml`，路径固定，预检按这个位置执行。结构说明见 `contracts/w04/README.md`，格式示例见 `contracts/w04/cleaning_rules.valid.yaml`。六个顶层字段都要有，不能多字段：

```yaml
contract_version: w04-0.1.0
data_version: qinghe-w04-v1.1
tag_cleaning:
  delimiters: ['分隔符1', '分隔符2']
  legal_tags_source: tags.txt
  hyphenated_tag_handling: 写清带连字符的标签怎样保留
  unknown_tag_handling: 写清未确认的标签怎样处理
  note_extraction: 写清备注怎样识别和保留
invalid_values:
  - source_fields: [来源字段A]
    values: ['无效写法1', '无效写法2']
    action: 写处理动作
    reason: 写原因
abnormal_records:
  - rule_id: 规则编号
    condition: 写触发条件
    action: quarantine
    reason_code: UNLINKED_ACCOUNT
    evidence: 写依据和证据位置
raw_preservation:
  original_files: 写原始文件怎样保留
  notes: 写备注原文和来源怎样保留
  quarantine: 写隔离记录怎样保留
```

逐字段说明：

| 字段 | 怎么填 |
| --- | --- |
| `delimiters` | 第 3 步剖析到的实际分隔符，至少一个 |
| `legal_tags_source` | 标签清单文件名，适配器按规则文件所在目录读取。清单放在 `artifacts/w04/tags.txt`，一行一个，内容来自字典和第 5 步的客户确认 |
| `abnormal_records[].action` | 只能是 `quarantine`、`reject`、`deduplicate`、`normalize`、`keep` |
| `abnormal_records[].reason_code` | 至少能表示孤儿关联、超额退款、契约外卡种、无效日期、主键冲突。已提供 `UNLINKED_ACCOUNT`、`REFUND_EXCEEDS_PAID`、`UNSUPPORTED_CARD_TYPE`、`INVALID_DATE`、`DUPLICATE_PRIMARY_KEY`，其他非空原因可在规则里定义 |

这些规则由适配器读取执行，不要把判断写死在代码里、让 YAML 只当说明。

这一步没有单独的命令，第 7 步 `adapt` 开始时会先校验这个文件。

- **算完成**：第 7 步运行时没有 `ValidationError`。规则覆盖了上一节第 6 步列的标签与备注拆分、格式规范、字段映射、无效值和异常记录。
- **容易卡**：合法信息不能误删：带连字符的标签、字典里没有但经客户确认的标签都要保留；备注按完整的一条保留原文和来源，不拆成碎片；涉及触达限制的备注要全部识别。未经确认的暂定标签作为备注保留，并在诊断报告里列为待核实。

### 第 7 步：实现适配器，隔离而不是丢弃

**要改的文件**：`customer/w04/solution.py` 的 `adapt(tables, rules, context)`。`rules` 是第 6 步解析后的字典，`context['rules_dir']` 是规则文件所在目录，读标签清单时这样写：`Path(context['rules_dir']) / rules['tag_cleaning']['legal_tags_source']`。

要返回五项：

```python
return {
    'tables': {'members': [...], 'orders': [...], 'stores': [...], 'cards': [...],
               'member_tags': [...], 'member_notes': [...], 'quarantine': [...]},
    'record_counts': {'member': {'read': 0, 'accepted': 0, 'quarantined': 0, 'deduplicated': 0},
                      'order': {...}, 'card': {...}, 'shop': {...}},
    'field_mapping': [{'source_file': '文件名.csv', 'source_fields': ['来源字段A'],
                       'target': 'members.member_id', 'transformation': '写怎样转换'}],
    'samples': [{'source_file': '文件名.csv', 'source_row': 1, 'status': 'accepted',
                 'destination': 'orders.csv 记录 1', 'reason': '写为什么接受'},

                 'destination': 'quarantine.csv 记录 1', 'reason': 'UNLINKED_ACCOUNT'}],

                       'time_range': {'start': '2024-09-01', 'end_exclusive': '2026-09-01'},
                       'quarantined': {'member': 0, 'order': 0, 'card': 0, 'shop': 0}},
}
```

七张表每张都要返回，没有数据也给空列表。每行的键必须和下表完全一致，多一列就报错：

| 表 | 列 |
| --- | --- |
| `members` | `member_id`、`registered_at`、`home_store_id`、`tier`；可选 `account_status`（活跃、冻结、注销、未激活）、`registered_channel`（门店、小程序、商城、系统导入）、`created_at` |
| `stores` | `store_id`、`region`、`store_name` |
| `orders` | `order_id`、`member_id`、`store_id`、`ordered_at`、`status`、`gross_cents`、`paid_cents`、`refund_cents`、`quantity`、`channel`（门店、小程序、商城） |
| `cards` | `card_id`、`member_id`、`card_type`、`valid_from`、`valid_until`、`ended_at`、`card_paid_cents` |
| `member_tags` | `member_id`、`tag`，同一会员同一标签只出现一次 |
| `member_notes` | `member_id`、`source_file`、`source_row`、`source_field`、`raw_text`、`note_text`、`category`（触达限制、客户关系、卡务、联系状态、其他）。青禾的 `source_field` 填 `tag`，`raw_text` 保留字段完整原值 |
| `quarantine` | `record_type`（member、order、card、shop）、`source_file`、`source_row`、`reason_code`、`raw_json`。`raw_json` 用 `json.dumps(row['raw'], ensure_ascii=False)` 写完整原记录 |

日期写本地 ISO 日期，金额写整数分，主键不重复不为空，订单、会员卡、标签、备注的 `member_id` 都要能在 `members` 里找到。不能进表的记录进 `quarantine`，不要过滤掉。`record_counts` 每类都要满足 `read = accepted + quarantined + deduplicated`。

### 第 8 步：全量导入并对账

**要改的文件**：`customer/w04/solution.py` 的 `reconcile(payload)`。`payload` 里有 `source`（原始表）、`cleaned`（清洗表）、`metadata`（`adapt` 的返回，不含表）、`manifest`、`first` 和 `second`（两次导入的 `counts`、`order_count`、`paid_cents`、`table_sha256`）、`first_run_id`、`second_run_id`。

- `record_counts` 是列表，每项写 `record_type`、四个计数，以及 `reconciliation: {"balanced": 真假, "evidence": "源文件 N = 接受 A + 隔离 Q + 去重 D；库内 A"}`；

### 第 10 步：写数据诊断报告

**要改的文件**：`docs/w04/data_diagnosis.md`。模板标题不要改，公开预检按标题里的词检查，所以改标题会失败；只查标题，不代表内容达标。

工作账对照可以用占位写法起步：

```text
对照项：工作账 某名单 与 CRM 某类备注。
方法：按会员号比对，窗口以每条拉名单日期为准。
结果：两边都有 N 人，只在工作账 N 人，只在 CRM N 人。
待核实：这 N 人为什么对不上，向某角色核实。证据位置：某文件第 N 条记录。
```

这一步不用跑命令。

- **算完成**：六节都有内容，数字都能在产出文件里找到；每条结论能说清来自数据、访谈还是推断。
- **容易卡**：两边对不上时写成待核实事项，不凭一份快照就下定性结论。工作账窗口以每条拉名单日期为准，不使用当前运行日期。

### 第 11 步：选第一个 demo 并实际跑通

## 4. 公开判定标准

技术门槛和交付门槛都要达标，平均分不能抵消核心缺项。

- checker 在固定样本上重跑你的代码，不只看 JSON：能复现关键异常；合法标签不被误删；备注完整保留原文和来源，触达限制类备注全部识别；每条被拒记录都有去向；重复运行结果一致；对账等式成立；覆盖说明存在且格式正确；各 JSON 通过契约 schema。
- 所有数字以本数据的实际值判定，不拿客户口头的整数判对错。
- 业务模型按本周证据核对并更新受影响的概念、关系和规则，与指标定义一致；无需修改的说明核对结果，待核事项不冒充确认结论，不以修改条数评分。
- 38 项指标在导入后的库上真实运行，ID 不变，受影响的定义按新证据修订并写明依据。
- 字典差异按三类归类，每一处写明影响、修订对象和取证对象；把字典过时当成数据错误去改数据，或把数据暂缺当成零，都属于核心错误。
- 能说明哪些结论来自数据、哪些来自访谈；诊断报告至少完成一项工作账与 CRM 的对照；给出下一步核实清单。
- demo 选线结合本期业务目标、关键假设、实际数据与现有能力，说明服务哪项会员运营工作及为什么值得先验证；在导入后的真实数据上实际运行，用证据限定结论，bad case 如实记录，不以挑选过的成功样例代替。
- 调优前后是同一问题、只改一处。回答要把结论限定在已覆盖的范围内：只在末尾补一句“数据不全”、结论仍按全公司下的，不算解决。

公开预检只报告结构是否通过、哪一层未通过，不公开隐藏样本的期望。业务模型检查文件是否存在且非空，其余文档只检查必备章节是否存在；模型内容、修订依据及其与指标的一致性由助教按标准审阅。助教不按代码行数、语言或所选模型品牌评分。

## 5. 卡住以后

环境问题先重放梧桐的两份快照，按报错区分依赖、读取、适配、导入和查询问题。缺业务事实就继续访谈。字段含义、标签与备注的写法、员工卡这几项缺了会做不完技术任务，访谈不到或回答不稳定时，课程方可以直接分发与访谈事实一致的补充材料；使用时标明来源为课程方补充，不冒充本人访谈，也不能充抵必访记录。

W04 的 checkpoint 随 W05 材料包提供标准剖析结果和清洗后的中间表，供下周继续使用。使用时另存一份，注明采用了哪些部分，不要覆盖自己的失败记录。本周未通过不阻断下周材料开放，核心缺项需在答辩前补齐。遇到访谈服务失败，保留会话和请求编号，先刷新原记录，不反复创建会话。

## 报错对照表

出错时先按这四步排查，再查下表：

1. **看原文**：完整读错误码和位置，不要只看到“失败”就重跑。
2. **分层**：判断问题在哪一层：自己的命令和配置、网络和模型服务，还是业务内容。
3. **缩小范围**：用最小的一步验证，比如只跑不调模型的检查命令，或看这次运行留下的记录。
4. **留证据再求助**：记下运行的命令、错误码和试过的办法。半小时还没解决，就带着这些发到群里。

本周工具报错时，先看返回的 `code` 和 `reason`。`adapt`、`load` 的导入错误包在 `IMPORT_FAILED:` 后面，看里面的 `code`。

| 错误码或现象 | 原因 | 下一步 |
| --- | --- | --- |
| `ModuleNotFoundError` | 没用虚拟环境里的 Python，或依赖没装完 | 用 `.venv/bin/python`，重跑第 1 步安装 |
| `UnicodeDecodeError: 'gbk' codec can't decode` | Windows 没开 UTF-8 模式 | 执行 `setx PYTHONUTF8 1`，重开所有 PowerShell 窗口 |
| `MODEL_NOT_CONFIGURED` | 当前终端没有三个模型环境变量 | 按第 1.2 步配置；`doctor` 看 `model_configured` |
| `MODEL_URL_INVALID` | 地址不是 `https`，或带了问号参数、账号密码 | 改成 Chat Completions 完整地址 |
| `MODEL_HTTP_401` 这类 | 模型服务拒绝请求 | 核对地址、模型名、密钥 |
| `run-demo` 报 `MODEL_HTTP_400` | 用的是 11-05 以前的旧工程包，全量数据上请求超长 | 看工程包 `MANIFEST.json` 的 `package_revision`，不是 `agent-large-dictionary-20261105` 的，重新下载工程包，把 `platform/fde_product/metrics/agent.py` 换成新包里的同名文件，原 `--project` 不用重新导入，换新的 `--output` 重跑 |
| `MODEL_NETWORK_ERROR` | 调模型时网络断了 | 确认网络和模型服务，重跑这次 `run-demo`，换新的 `--output` |
| `MODEL_TIMEOUT` | 模型响应超时 | 确认模型服务，重跑；`run-demo` 单次默认等 180 秒，可设 `FDE_MODEL_TIMEOUT=240`，不要超过 240 |
| `MODEL_OUTPUT_TRUNCATED` | 重试后输出仍被截断 | 缩小问题范围，或换模型后重跑 |
| `OUTPUT_EXISTS` | 重放的 `--output` 目录已存在 | 换一个新目录 |
| `W04_PROFILE_UNIMPLEMENTED`、`W04_ADAPTER_UNIMPLEMENTED`、`W04_RECONCILIATION_UNIMPLEMENTED` | 对应入口还是空白实现 | 到 `customer/w04/solution.py` 实现；重放 `start` 快照时出现属于正常 |
| `W04_TESTS_UNIMPLEMENTED` | 默认测试还没改 | 改写 `customer/w04/test_solution.py` |
| `NO_SOURCE_CSV` | `--source` 目录下没有 CSV | 核对第 1.3 步的解压路径，确认到 `qinghe-w04-v1.1` 这一层 |
| `CSV_WIDTH_MISMATCH:文件名:record=N` | 第 N 条记录的列数和表头不一致 | 看这条记录；原始文件不改，确认是不是读错了文件 |
| `CSV_HEADER_INVALID:文件名` | 表头为空或有重复列名 | 确认文件完整，重新解压数据包 |
| `ValidationError`，提示 `is a required property` | 规则或报告缺必填字段 | 按提示补字段，对照第 3、6、7、8 步和 `contracts/w04/` 的 schema |
| `ValidationError`，提示 `is not one of` | 取值不在允许范围内，比如 `action`、`change_location` | 改成提示列出的值 |
| `KeyError`，提示表名 | `adapt` 返回的 `tables` 少了某张表 | 七张表都返回，没有数据给空列表 |
| `dict contains fields not in fieldnames` | 某张表多了契约外的列 | 按第 7 步的列名表修改 |
| `NEW_OUTPUT_AND_PROJECT_REQUIRED` | `adapt` 的输出或项目目录已存在 | 把 `run-01` 换成下一个编号，旧目录保留 |
| `PROJECT_ALREADY_EXISTS` | `load` 的项目目录已存在 | 换新的 `--project`，不在旧库上追加 |
| `import_failed.json` 出现在运行目录 | 这次写出或导入中途失败 | 看 `stage` 和 `reason`，修正后换新运行编号；目录不能续跑 |
| `UNLINKED_ACCOUNT:表名` | 这张表有记录的 `member_id` 不在 `members` 里 | 关联不上的记录进 `quarantine`，并计入 `quarantined` |
| `DUPLICATE_OR_NULL_KEY:表名` | 主键重复或为空 | 区分完全重复和主键冲突，按规则去重或隔离 |
| `CSV_COLUMNS_MISMATCH:表名` | 清洗 CSV 的列和契约不一致 | 按第 7 步的列名表修改 |
| `DATA_HASH_MISMATCH:表名` | 清洗 CSV 被改过，和 manifest 对不上 | 不手改清洗文件，改规则或代码后换新运行编号重跑 |
| `DATA_COUNT_MISMATCH:表名` | 实际导入行数和 manifest 不一致 | 查字段内换行、引号和空行，换新运行编号重跑 |
| `RECONCILIATION_MISMATCH:类别` | `read` 不等于 `accepted + quarantined + deduplicated` | 查哪条记录没有计入，修正 `record_counts` 的计算 |
| `ACCEPTED_COUNT_MISMATCH:类别` | `accepted` 和实际入库行数不一致 | 改成按实际写出的行数计数 |
| `QUARANTINE_COUNT_MISMATCH:类别` | `quarantined` 和隔离文件行数不一致 | 每隔离一条同时写表和计数 |
| `INVALID_ACCOUNT_STATUS`、`INVALID_REGISTERED_CHANNEL`、`INVALID_ORDER_CHANNEL` | 写入了契约外的取值或空值 | 映射到第 7 步列出的取值；无法映射的进隔离 |
| `INVALID_CREATED_AT` | `created_at` 有空值或不是 ISO 日期 | 修正解析；解析不了的按规则处理 |
| `INVALID_MEMBER_NOTE` | 备注的来源字段、原文、内容或类别不合规 | `source_field`、`raw_text`、`note_text`、`category` 都要填，类别用五个规定值 |
| `INVALID_SOURCE_ROW:表名` | `source_row` 不是从 1 起的整数 | 用记录自带的 `source_row`，不要自己算或写成小数 |
| `INVALID_QUARANTINE_RECORD`、`INVALID_QUARANTINE_JSON` | 隔离记录缺字段，或 `raw_json` 不是完整对象 | 用 `json.dumps(row['raw'], ensure_ascii=False)` 写入 |
| `EMPTY_TAG` | 标签拆分时产生了空标签 | 拆分后去掉空白和空值 |
| `SOURCE_FILE_NOT_IN_MANIFEST:表名` | `source_file` 不是保留的原始文件名 | 用记录自带的 `source_file` |
| `LIBRARY_METRIC_CATALOG_MISMATCH` | `metrics.yml` 和 `catalog.json` 的指标对不上 | 两边 38 项一一对应，ID 不改 |
| `CATALOG_METADATA_REQUIRED:指标ID` | `catalog.json` 的这一项缺名称、单位或来源 | 补齐 |
| `LIBRARY_PREFLIGHT_FAILED`，内含 `MODEL_SQL_INVALID` | 派生模型的 SQL 无法绑定列或来源模型 | 看 `file` 和 `message`，改对应 `.sql`，用新的 `--project` 重新导入 |
| `UNSUPPORTED_SQL_OPERATION:文件名` | SQL 里有不允许的操作 | 只写查询语句，模型文件以 `select` 或 `with` 开头 |
| `DBT_BUILD_FAILED` | 模型构建失败 | 看报错给出的 `build.log`，改库后用新的 `--project` 重新导入 |
| `PROJECT_VALIDATION_FAILED` | 指标校验没过 | 看报错给出的 `validation.log`，改库后用新的 `--project` 重新导入 |
| `run_metrics.py` 打印的方括号里有指标 ID | 这些指标在所选时间没有跑通 | 看 `artifacts/w04/metrics_run.json` 里该指标的 `reason`；时间是否完整自然月，定义是否要修 |
| `DATASET_COVERAGE_REQUIRED` | 项目不是适配器产出的数据，没有覆盖说明 | `run-demo` 的 `--project` 用第 9 步的 `project-c` |
| `status: clarify` | 问题或时间不明确 | 写明完整时间范围，换新目录重跑 |
| `status: unsupported` | 超出覆盖、指标未定义或维度不支持 | 看 `reason`，调整问题或记成 bad case |
| `RUNTIME_ANSWER_REQUIRED`、`RUNTIME_COVERAGE_SNAPSHOT_REQUIRED` | `run_path` 指向的运行缺回答或缺覆盖快照 | 确认路径写到 `trace_id` 这一层；缺快照的运行要用 `run-demo` 重跑 |
| `FileNotFoundError`，路径含 `demo_runs` | 标注文件的 `run_path` 写错 | 路径相对 `artifacts/w04/`，写到 `trace_id` 这一层 |
| `TUNING_QUESTION_MISMATCH` | 调优前后的问题不一致 | 用完全相同的问题重跑调优后这一次 |
| 预检 `schema` 层未通过 | 三份 JSON 或规则文件缺失、格式不对 | 按第 3、6、8、12 步重新生成 |
| 预检 `documents` 层未通过 | 文档缺失、业务模型为空，或模板标题被改 | 恢复 `templates/w04/documents/` 里的标题，内容写在标题下面 |
| 预检 `execution` 层未通过 | 代码在公开样本上运行失败，预检不显示原因 | 用公开样本单独跑，看实际报错：`.venv/bin/python tools/w04.py adapt --source examples/w04/public-check/raw --rules artifacts/w04/cleaning_rules.yaml --code customer/w04/solution.py --output .runtime/w04/public-01/adapt --library examples/w03/library --project .runtime/w04/public-01/project-a` |
| 预检 `profile` 层未通过 | 字段统计不准，或关键异常没被认出 | 核对 `total_count`、`missing_count`，对照公开样本的 `expected.json` |
| 预检 `records` 层未通过 | 公开样本的表内容不符，如标签、备注、金额 | 对照 `examples/w04/public-check/expected.json` 和它的 README |
| 预检 `provenance` 层未通过 | 隔离或备注的来源、原文、文件哈希对不上 | `source_row`、`raw_json`、`raw_text` 都从原记录带出，不改写 |
| 预检 `coverage` 层未通过 | manifest 的覆盖说明缺失或格式不对 | 核对 `coverage_notes` 的 `source`、`time_range`、`quarantined` |
| 预检 `reconciliation` 层未通过 | 计数、金额或报告和实际重跑结果不一致 | 报告要由代码计算，核对 `record_counts`、`repeat_import`、`test_result` |
| 预检 `repeat` 层未通过，带 `differences` | 两次运行的输出不完全一致 | 看列出的文件名，排序后再写出，不依赖 `set` 的顺序 |
| 访谈里出现「这一轮是系统没能组织好回答」 | 访谈系统这轮没组织好回答，不计提问次数 | 原样重发，或拆成小问题 |
