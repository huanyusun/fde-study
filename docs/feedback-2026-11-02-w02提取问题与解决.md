# W02 提取环节问题与解决汇总（反馈课程方）

> 2026-11-02。学员侧环境：macOS、工程包 w02-agent-0.5.4、Python 3.13（.venv）、OpenAI 兼容第三方端点（z.ai，GLM 系列 flash 推理模型），profile `compatible`。本文档仅记录问题现象、定位过程与解决方式，不含密钥与个人账号信息；运行证据见仓库内运行记录（路径见文末）。

## 问题 1：平台导出 JSON 无法直接进入提取（CONTRACT_VERSION_UNSUPPORTED）

**现象**：按 `docs/w02_workflow/README.md` 在 `customer/w02/extraction.json` 的 `sources` 中填写访谈网页导出的 JSON 后，`tools/w02_workflow.py inspect` 返回 `{"status":"failed","code":"CONTRACT_VERSION_UNSUPPORTED","location":"transcript"}`。

**定位**：访谈网页的"导出完整公开记录"不含 `contract_version` 字段；提取工具要求的 transcript 契约带该字段。工具已自带 `tools/w02_interviews.py convert` 子命令处理此转换，但 workflow README 未提及。

**解决**：对每份导出执行 `convert` 生成 `customer/w02/transcripts/*.json`，再把 sources 指向转换后的文件；`inspect` 通过。

**建议**：
1. 在 w02_workflow README 的"准备本轮任务"处，加一句"平台导出需先经 `w02_interviews.py convert` 转为 transcript 格式"，并给出报错码对照。
2. `CONTRACT_VERSION_UNSUPPORTED` 报错信息未说明"这是平台原始导出、需转换"，学员需翻源码定位，建议报错文案附带处理指引。

## 问题 2：推理模型下提取必然 MODEL_TIMEOUT（reasoning 烧尽输出预算）

**现象**：`inspect` 通过后 `start` 提取，两次运行均失败：

| 运行 | profile | 超时 | 结果 |
| --- | --- | --- | --- |
| 第 1 次 | compatible | 90s（默认） | `MODEL_TIMEOUT` |
| 第 2 次 | compatible | 180s（按文档调 `FDE_MODEL_TIMEOUT`） | 仍 `MODEL_TIMEOUT` |

**定位**（读 `step-001.attempts.json`）：
- 第 1 次尝试并非网络超时，而是 `finish_reason=length`、`MODEL_OUTPUT_TRUNCATED`：**completion_tokens=8192 全部用满，其中 reasoning_tokens=8121**——模型把输出预算几乎全花在内部思考上，正文没写完即截断。
- 工具按规则自动以 16384 token / 180s 重试；推理模型生成 1.6 万 token（非流式）远超 180 秒，第二次尝试以 `MODEL_TIMEOUT` 结束。
- 用极小请求直测端点（3.4s 返回），确认端点本身正常，问题在推理开销。

**解决**：将 `extraction.json` 的 `profile` 从 `compatible` 改为 `deepseek-low`（发送顶层 `thinking` + `reasoning_effort: "low"`）。过程中发现**同一 profile 在三层白名单不一致**：模型适配器 `CompatibleModel` 允许 `deepseek-low`，但提取配置 schema（`interview_extraction.py` CONFIG_SCHEMA 的 profile enum）与 `ExtractionModel` 的 profile 校验均未包含它，配置即被拒（`SCHEMA_INVALID` / `PROFILE_INVALID`）。按任务书"修改必要代码"路线，在上述两处各加一项 `deepseek-low`（共 2 行），运行通过。实测 z.ai 端点对该参数组合生效：

| 参数组合 | 同段提取任务耗时 | reasoning_tokens |
| --- | --- | --- |
| 无参数（等价 compatible） | 30.6s | 543 |
| `reasoning_effort: "low"` | 2.3s | 3 |
| `thinking`+`reasoning_effort: low`（即 deepseek-low 形态） | 7.0s | 0 |

另实测 `thinking: {"type":"disabled"}` 亦被端点接受（9.4s，reasoning=0）。平台模块存在 `extraction_thinking` 参数（支持 `"disabled"`，extract 阶段生效），但两个 CLI 调用点均未暴露、默认写死 `enabled`。

**建议**：
1. **统一 profile 白名单**：`CompatibleModel`、`ExtractionModel`、提取配置 schema 三处的 profile 列表不一致（`deepseek-low` 仅第一层允许；`gateway-none` 仅在 `thinking_parameters()` 中出现）。建议对齐或收敛为一个来源。
2. **暴露 `extraction_thinking`**：该参数已实现且进入 policy 记录与校验重建，但 CLI/配置无法设置。推理模型场景下它正是对症开关，建议从配置暴露。
3. **文档**：`docs/model-configuration.md` 的 profile 表建议补充——"推理型模型（先输出思考再给正文）建议用 `deepseek-low`；`compatible` 对推理模型可能把 `max_tokens` 全部耗在 reasoning 上导致截断/超时"。我们是在翻适配器源码后才发现 deepseek-low 的参数实际是通用的。
4. **命名**：`deepseek-low` / `deepseek-json` 名称暗示仅适用 DeepSeek 协议；实际发送的顶层 `thinking`、`reasoning_effort` 同样适用于 z.ai GLM 等其他兼容端点。建议改名（如 `thinking-low` / `thinking-json`）或在文档注明通用性。
5. **报错区分**：`MODEL_TIMEOUT` 未区分"网络慢"与"截断重试后仍超时"。我们这次是先翻 `attempts.json` 看到 `finish=length` 才确认是推理开销。建议 workflow 的失败输出直接带上最近一次尝试的 `finish_reason`，可省一轮排查。
6. **文档已对齐的部分**（确认有效，感谢）:`FDE_MODEL_TIMEOUT=180` 环境变量方案、"提取失败保留旧运行后新建运行"的恢复路径均按文档执行成功。

## 问题 3：模型输出被 markdown 围栏包裹（JSON_INVALID 的真因）

**现象**：压制思考后提取仍失败（`JSON_INVALID`），但检查发现 step-001（提取阶段，约 26 条候选）的正文是**合法 JSON 且严格解析通过**；真正失败的是 step-002（分歧阶段）：模型把 `{"conflicts": []}` 包进 \`\`\`json 围栏，并在后面追加了一段说明文字。

**解决**：将 profile 换为 `deepseek-json`（白名单原生支持，无需改代码）。该 profile 发送 `response_format: {"type":"json_object"}`，实测 z.ai 端点支持（2.4s 返回纯 JSON、无围栏），且与 `thinking`+`reasoning_effort` 参数可并用。

**建议**：提取与分歧阶段的提示词未约束"输出裸 JSON"；推理模型尤其爱加围栏和解释。建议默认 `extraction.json` 模板注明：推理型端点建议直接用 `deepseek-json`（json_object 模式），或在提示词模板中加入"不要 markdown 围栏、不要解释文字"。

## 问题 4：模型用省略号拼接引用，来源检查必然失败（QUOTE_NOT_FOUND）

**现象**：JSON 格式修复后运行至来源检查失败（`QUOTE_NOT_FOUND`，定位到具体候选）。逐条比对发现 32 条候选中 9 条的 `quote` 用 `……` 把同一消息内不连续的段落拼成"摘录"，而来源检查要求引用为原文**连续子串**，全部不匹配。

**解决**：在 `customer/w02/extraction_prompt.txt` 追加引用规则（quote 必须逐字连续、禁用省略号拼接、不连续内容拆多条 evidence）。此为提示词层方法迭代，属任务书"出现问题再迭代"的正常路径；修改会随运行快照留痕。追加该规则后的下一次运行完整通过：26 条候选（18 fact／7 opinion／1 inference）、2 个冲突组，进入人工核查停点。

**建议**：来源检查的连续子串要求是硬约束，但默认 `extraction_prompt.txt` 模板未向模型说明该约束，模型自然倾向拼接摘录。建议课程默认模板即包含引用连续性要求，可省一轮失败迭代。
