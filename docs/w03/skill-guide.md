# 构建 Skill 编写指南

这份指南帮助你把“读资料、判断粒度、选择模型、处理缺口”的方法写进构建 Skill。安装、完整操作命令和问数步骤见 [README](README.md)；输出格式见[工具契约](contract.md)；梧桐的输入、生成结果与验证过程见[样例走读](wutong-walkthrough.md)。

先读懂[梧桐样例 Skill](../../examples/w03/build-metrics/SKILL.md)，再为自己的任务写方法。下面的六段引文均摘自该文件，未改写。客户的金额、状态、日期和资格等事实应留在客户材料中，Skill 写怎样查证、转换和处理缺口。

## 1．Skill 在构建中怎样起作用

### 1.1．一次构建的过程

`build` 从配置指定的位置读取 Skill **全文**，把它作为模型调用的 `system` 消息；再把下表中的输入序列化为 JSON，作为 `user` 消息。六个标题帮助组织方法，程序不会按标题拆成六次调用。调用没有附带工具，模型返回 JSON；框架负责把 JSON 写成 YAML 和 SQL，再构建、检查。

```text
配置指定的 Skill 全文 ── system 消息 ┐
业务模型、材料、目标等 ── user 消息   ┴→ 模型返回完整 JSON
                                          ↓
                            candidate 中的 YAML、SQL 与目录
                                          ↓
                               数据加载、dbt、三项检查
                                          ↓
                                通过后发布到输出目录顶层
```

框架先保存 `input.json` 和 `skill_used.md`，调用记录写入 `trace.json`；成功解析后才保存 `response.json`。之后逐步保存来源核对、候选与检查报告。失败发生得早时，后面的文件可能尚未生成。检查失败的候选仍在运行目录中，不能把 `candidate/` 当成已通过的完成库。

因此，写进 Skill 的要求要能直接指导生成：先核对什么、怎样作判断、判断后写到哪里、依据不足时怎样处理。只写“认真分析，生成正确指标”无法告诉模型怎样完成这些步骤。

### 1.2．input.json 各字段是什么

| 字段 | 实际来源与含义 | Skill 应怎样使用 |
| --- | --- | --- |
| `business_model` | 配置中业务模型文件的完整文本 | 找业务对象、关系、粒度及已确认事实，保留采用依据 |
| `materials` | 配置指定的 Markdown 文件；指定目录时递归读取其中的 `.md`。对象的键是文件名，值是全文 | 汇总分散规则、字典和确认记录；引用时使用输入中的文件名，不能自行编文件名 |
| `targets` | 配置指定的目标清单；传给模型的每项只有 `id`、`name`。使用 `--metrics` 时只保留本批指标 | 逐项处理真实 ID，不能把契约示例里的占位 ID 当作目标 |
| `access_tables` | 程序 `TABLES` 中四张接入表的列名和类型 | 确认哪些物理字段可用；它不提供业务公式、样例数据行或派生列 |
| `dimension_targets` | 工程 `templates/w03/dimension_targets.json` 的完整清单 | 逐项核对实体和属性是否能沿已确认关系查询；这份清单只给目标，不给连接实现 |
| `native_format` | 当前固定为 `dbt semantic_models/measures; MetricFlow 0.213; DuckDB` | 使用本包锁定的 MetricFlow 0.213.0 和旧格式，不混入另一代 YAML 写法 |
| `contract` | 工程 `contracts/w03/build_response.example.json` 的内容 | 按约定组织返回对象；它是输出形状示例，不是客户的模型答案 |

另有 `business_model_filename`，当前固定为 `business_model.md`，用于引用业务模型。`materials` 中的文件即使来自不同目录，也不能同名；还应避免把另一份同名 `business_model.md` 再放进材料列表，以免来源混淆。

配置中的路径以 `build.json` 所在目录为基准。`data` 指向本地检查使用的 CSV，`scope` 用于生成库的客户范围；这两项不在上述模型输入中。框架不会自动把 CSV 行、现有指标库、历史响应或独立测试期望送给构建模型。`time_spine` 由框架按 manifest 覆盖期提供，不在四张接入表的 `TABLES` 清单里。

### 1.3．模型必须返回什么

返回一个完整 JSON 对象，包含 `semantic_models`、`metrics`、`catalog`、`model_sql`、`grain_keys`、`unresolved`、`business_model_usage`。语义模型也由这次调用生成，框架不再读固定骨架。字段含义与完整形状以[构建输出契约](contract.md#构建输出)和[JSON 示例](../../contracts/w03/build_response.example.json)为准。

Skill 要说明输出之前怎样得到这些内容。连续引文校验能检查“这句话是否真的出现在输入里”，不能判断“这句话是否足以支持公式”；后一个判断仍须写进方法，并用独立期望复核。

<a id="six-parts"></a>
## 2．六段分别写什么、写到什么程度

每条方法尽量包括四件事：**何时使用、核对什么、怎样落实到输出、缺依据时怎么办**。不必堆长篇角色设定，也不必把六段写成六个独立 Skill。

### 第一段：目标与输入

**目的**：让模型知道要完成哪些目标，以及到哪里找不同类型的事实。

**通用规则**：按目标 ID 建立处理清单；区分业务模型、报表规则和物理字典的作用；先核对事实是否已确认，再转换。名称相似的目标不能自行合并，资料没有的规则不能凭经验补上。

**写到什么程度**：模型能区分“材料没给定义”和“字典没给字段”，并能对每个目标选择定义或未决。这里写输入职责，具体客户条件由输入提供。

**常见错误**：直接凭指标名字猜口径；把字典中的字段存在当成业务上应计入；把契约示例复制成客户模型。

样例原文：

> 按输入的目标 ID 逐项处理，不新增、不改名、不遗漏。业务模型提供对象、关系和粒度；报表说明提供统计口径；字段字典提供实际列名和单位。

### 第二段：候选及依据

**目的**：在生成表达式前，把一个目标所需的事实凑齐，并保留分歧。

**通用规则**：逐项整理统计对象、行粒度、时间、计入与排除条件、金额或数量构成、聚合方式和单位；每项保留来源。多个说法先并列，确认适用范围和版本后再选择；没有确认时留未决。

**写到什么程度**：能从候选定义追到支持它的原文，能指出缺口影响哪个目标。连续引文不要把两段话拼成一句，也不要把自己的解释包装为引用。候选整理可写在自己的核定记录中，不要求模型新增契约外的“候选表”输出。

**常见错误**：只引用一句看似相关的话；将“后来收到”直接等同于“已经取代旧规则”；丢掉与当前结论不一致的材料。

样例原文：

> 为每个目标整理：统计对象与粒度、统计时间、计入与排除条件、金额或数量构成、聚合方式、单位。每一项都要在输入中找到依据。

### 第三段：字段与计算转换

**目的**：把已核实的业务定义转换成可计算表达式。

**通用规则**：先确定表达式作用于哪种行，再映射字典字段；逐项检查计入项、扣减项、空值处理和聚合方式。字段名保持原样；显示单位与底层计量单位分别核对。需要多个计算阶段时，转交第六段处理派生模型。

**写到什么程度**：能解释每个计算项来自哪条已确认事实，以及为什么在当前粒度上求和、计数或去重；不能只写“用合适的聚合函数”。条件不满足时是否取零，也要符合指标定义，不能把未知和未定义一律改成零。

**常见错误**：漏扣退回；用单笔条件代替按期累计；对被一对多关联放大的行直接求和；把非空的单位字符串当成单位正确。

样例原文：

> 按已核实的粒度写 measure：行级表达式只使用字典中存在的列；计入与排除条件写进表达式（例如不满足条件时取 0）；金额类指标逐项核对计入项与扣减项是否齐全。选择与统计对象一致的聚合方式。

### 第四段：依赖与输出协议

**目的**：让定义、依赖、目录和返回格式组成同一个可执行库。

**通用规则**：输出前检查依赖是否闭合，measure 名称是否全局唯一，目录是否与已定义指标一致；按材料设置查询限制；最终只返回约定 JSON。比率应引用相应指标依赖，不能拿一段公式文字充当 ID。

**写到什么程度**：每项输出都能在同次返回中找到依赖；未决目标不混入可查询目录。把最终输出格式说清楚，但不用把整个契约再抄进 Skill。

**常见错误**：因为最终落盘是 YAML，就直接让模型返回 YAML；依赖只存在于另一个批次；限制只写进 description，没有设置 `query_policy`。

样例原文：

> 只返回一个 JSON 对象，包含 semantic_models、metrics、catalog、model_sql、grain_keys、unresolved、business_model_usage，不返回 Markdown 或 YAML。

### 第五段：未决、冲突与修订

**目的**：让生成在依据不足时停在明确的缺口上，而不是凑出可执行公式。

**通用规则**：区分缺事实、相互冲突和物理字段不清楚；记录缺什么、影响什么、需要哪位已确认的负责人回答。补充事实后更新业务输入，再重新生成；不要把模型自己作出的选择写成已确认事实。

**写到什么程度**：接手的人能拿着未决说明去提一个具体问题，而不只看到“待确认”。写法见[第 6 节](#unresolved)。

**常见错误**：为了清空 unresolved 自行补条件；同一指标既定义又列未决；把“程序能编译”当成业务分歧已经解决。

样例原文：

> 资料缺少某个目标的定义，或资料之间说法冲突时，把该目标列入 unresolved，写明缺什么依据或冲突在哪里，不要为了覆盖目标而补写公式。每个目标只能出现在已定义或未决其中一边。

### 第六段：语义模型与派生模型

**目的**：决定业务定义落在哪些模型、关系和行粒度上。

**通用规则**：对象与角色映射到模型；已确认关系映射到实体主外键；属性映射到维度。每个模型先声明一行代表什么，再确定键、聚合和连接。需要多阶段计算时生成派生 SQL；逐项核对维度目标，并在输出前检查原生命名限制。

派生 SQL 使用 SELECT／WITH 和 dbt `ref`，模型名不覆盖接入模型或 time_spine。Skill 应要求不生成文件／网络读取或写入操作；框架也保留相应的危险操作检查。

**写到什么程度**：不只写“生成语义层”，还应给出选择原始粒度或派生粒度的方法、识别不同角色的方法、关联前后行数的检查方法，以及事实缺失时的退出方式。不要固定某个客户专用的模型清单或 SQL 答案。

**常见错误**：把每张 CSV 机械复制成一个语义模型；原表与派生表照抄同一个主实体；拼接一个看似唯一的键，却不检查真实组合粒度。

样例原文：

> 先声明一行代表什么，再写聚合。每个模型的 grain_keys 给出实际粒度列名列表；单键按主键检查，组合粒度逐列检查，不能用会吞掉空值的拼接逃避检查。

<a id="semantic-models"></a>
## 3．从业务模型到语义模型

可以在第六段写下这样一组处理顺序：

1. 列出目标涉及的业务对象，写明各自的一行含义和物理来源。模型按业务对象、角色及粒度组织，不要求与 CSV 一一对应。
2. 对每条关系核对方向、两端对象及关联键。作为被关联目标的键必须唯一且非空；不能仅因列名或值长得相似就连接。
3. 检查同一对象是否承担不同角色。角色不同，语义名称和查询路径也要分开。
4. 将属性映射为局部维度，确定有统计时间的模型使用哪个时间维度，再逐项核对查询目标。
5. 为每个模型声明真实粒度列。对依赖这些模型的指标，检查关联是否会增加事实行。

梧桐的订单关联一个会员账户和一个**成交门店**；会员账户另有关联的**归属门店**。两条关系回答的问题不同。梧桐样例让订单通过 `store` 关联门店，让会员通过 `home_store` 关联门店的另一语义角色。两种角色都可以引用同一物理门店表，不必造两套门店数据。

| 梧桐对象／角色 | 一行代表什么 | 建模时要区分什么 |
| --- | --- | --- |
| 订单 | 一笔订单 | 订单主键、会员外键、成交门店外键 |
| 会员 | 一个账户 | 会员主键，以及归属门店关系 |
| 成交门店 | 一个门店在成交关系中的角色 | `store` 与该角色的区域、名称 |
| 归属门店 | 一个门店在会员归属关系中的角色 | `home_store` 与该角色的区域、名称 |

局部属性名 `region` 与查询 ID `store__region` 分属两个位置。不要将后者直接填入 `dimensions[].name`。定义了实体和属性，也不保证任意指标都能查询它们：框架从实际语义图取得逐指标可达路径，维度目标全覆盖也不等于每项指标拥有全部维度。

当前粒度检查会分别检查声明的 grain_keys 和主实体／唯一实体，外键检查要求同名实体恰有一个 primary／unique 目标，且未匹配行数为零。外键空值也会成为未匹配行。资料如果允许关系缺失，应先核实当前接入与建模方式能否表达，不能为了通过检查随便填一个关联值。

<a id="derived-models"></a>
## 4．什么时候需要派生模型

先问：**指标的一个统计对象，是否就是原始表的一行？计算是否必须分阶段完成？**

梧桐月内大额会员数作用在“会员 × 月”上，原订单表是一行一单。单个会员同月可能有多笔订单，必须先得到该会员当月累计值，再判断是否达到客户定义的门槛。只给订单表增加一个行级金额判断，不能表达跨订单累计。

写进 Skill 的是判断方法：确认统计对象和期间，汇总到目标粒度，再按已确认条件计数。门槛及扣减口径继续来自梧桐材料。完整生成物见[样例走读](wutong-walkthrough.md)。

### 4.1．三类多阶段规则怎样写成通用方法

| 规则类型 | 在 Skill 中要求先核实 | 再指导怎样建模 |
| --- | --- | --- |
| 排序 | 排序对象、参与范围、排序时间、相同时间怎样处理，以及排序使用的历史范围 | 先形成排序需要的行集合，再按已确认的分组和顺序产生序号或位置；不能让本次查询窗口悄悄改变业务要求的历史顺序 |
| 按期汇总 | 对象、期间边界、归期时间、计入项与扣减项 | 先聚合到“对象 × 期间”等目标粒度，再在该粒度上作后续判断；如果还要保留更细维度，应先确认业务允许怎样分摊或分组 |
| 资格判断 | 判断对象、判断时点或期间、事实来源、重叠记录怎样处理、缺值的含义 | 按已确认事实得到每个判断对象在目标时点／期间的判断结果，再接回同粒度计算；未确认的条件留未决，不默认选一种解释 |

这张表只说明建模时要问什么，没有替任何客户确定排序范围、资格条件或日期端点。

### 4.2．grain_keys 怎样声明

`grain_keys` 的键对应每个语义模型的名字，值是该模型关系中真实存在的列名列表。组合粒度逐列声明，不写 SQL 表达式，也不只交一个人为序号。

梧桐样例中派生模型的声明是：

```json
"monthly_member_receipts": ["member_id", "month_start"]
```

这表示同一会员同一个月份最多一行，两个组成列都要非空。即使另生成 `member_month_key` 作为主实体键，也仍需检查上述实际组合。每个语义模型都要声明 grain_keys，不能只给派生模型填写。无重复只能证明数据符合声明，还需判断声明是否符合业务。

### 4.3．先汇总，再进行可能放大行数的关联

遇到一对多关系时，先写出两端的一行含义，再检查关联后的行数。多条明细若只为提供一个对象级判断或汇总，应先收敛到需要的对象粒度，再与主体关联；也可在定义允许时表达“是否存在”，避免为同一对象带回多行。

另外两种写法要分清：

- **只判断是否存在某类明细**：用 `EXISTS`（或等价的半连接）筛选主体，不把明细行带回主体。在主体原本一行一个对象的前提下，每个主体最多参与一次。例如，从一行一单的订单表中筛出含某类商品的订单，筛出的仍是订单；若要计算这类商品明细本身的金额，需要先明确明细粒度的计入范围和金额口径，不能直接用订单金额代替。
- **已关联后恢复成主体一行**：按主体键收敛前，必须检查三件事：保留的字段都属于主体；金额等主体属性在各重复行里一致；筛选含义没有因关联改变。确认这三点后，才能恢复主体粒度。不能随手取 `MAX` 或 `DISTINCT` 掩盖字段归属、属性值或筛选含义上的不一致。

“先汇总再关联”要求汇总键保留后续所需的关系和维度。不能先把成交门店聚合掉，又直接给会员月表接入所有成交门店，那会重新放大月表。如果业务定义并不支持这个拆分，应明确可查询范围；如果必须支持，先确认拆分口径再调整模型。`DISTINCT` 也不能代替这项判断：它可能消掉重复标识，却无法修复已重复累加的金额。

<a id="complex-materials"></a>
## 5．复杂资料怎样处理

### 5.1．规则散落在多份材料

按目标整理候选，不按文件各写一套相互独立的答案。可在核定记录中使用以下栏目：目标 ID、事实主题、候选说法、原文与文件、适用对象和时间范围、确认状态、影响项、待问问题及负责人。

先区分三种情况：几份材料分别补足同一定义；同词在不同范围下含义不同；同一范围内的说法真正冲突。只有输入中有明确的适用范围或已确认替代关系，才能据此选择。材料顺序、措辞强弱、发送时间较晚本身都不能自动充当裁决依据。

在 Skill 中要求保留每个尚未排除的候选及其出处，并把无法确认的定义列为未决。客户补充后，将确认内容及来源更新到业务模型或材料中，再重跑。当前构建器不会读取你没有放进配置的笔记，也不会自动追问客户。

### 5.2．一对多关系

让模型逐条回答：计的是哪类对象？哪一侧是唯一行？一条主体会匹配多少条明细？明细是用来筛选、判断存在，还是计算金额？在目标粒度上去重、汇总或判断存在后，再核对关联是否保持预期粒度。

不要默认 `count(*)`、`count(distinct ...)` 或 `sum(distinct ...)` 能通用解决重复。先决定哪些行在业务上属于同一个统计对象，再选择计算方式；金额相同的两笔真实业务也可能都应计入。

### 5.3．有效期、端点与空值

先确认使用哪个业务时间、开始和结束当天是否计入、空结束日期表示什么、缺失时间表示未知还是另一种状态、多个时间记录重叠时如何处理。必须依据客户确认，不能用数据库默认比较、常见行业习惯或字段名替客户作决定。

若这些事实影响当前目标，列明不同解释会影响什么，向负责该业务口径的人核实。在确认前，不能把某个比较运算符或空值默认值写成“临时正确答案”。本节仅是通用核查方法，不给出任何客户的端点或空值规则。

<a id="unresolved"></a>
## 6．未决怎样写

一条有用的未决至少回答：**缺什么事实、影响哪个目标及哪部分计算、向谁核实什么问题**。

下面是形状示意。`target_metric_id`、`target_dimension_id` 都是占位符，实际返回必须换成本批真实目标 ID；这些不是梧桐当前存在的缺口。

```json
{
  "unresolved": [
    {
      "metric_id": "target_metric_id",
      "missing_facts": ["材料对统计对象的说法不一致，缺少已确认的适用范围"],
      "reason": "影响该指标的计数对象；待向报表口径负责人确认两个说法各适用于什么范围，并保留原文出处。"
    },
    {
      "dimension_id": "target_dimension_id",
      "missing_facts": ["缺少该属性与统计对象之间已确认的关联关系"],
      "reason": "影响按该维度分组和筛选；待向维护这项关系的负责人核实关联对象、键及唯一性。"
    }
  ]
}
```

当前契约没有规定独立的“问谁”字段，因此把负责人和问题写入 `reason`；详细候选与出处继续留在核定记录里。先采用材料中已确认的角色；不知道负责人时，明确请项目对接人确定，不能凭空写一个人名。

两种未决的程序含义不同：

- **指标未决**：本批每个指标必须在“已定义”与“未决”中二选一。未决指标不进入 metrics 和 catalog；合并工具拒绝仍有指标未决的批次，提交预检也要求实际库覆盖全部目标。记录未决是如实暴露缺口，不代表作业已完成。
- **维度未决**：用真实 `dimension_id`，并填写非空的 `missing_facts`、`reason`。维度覆盖检查可接受明确未决，但没有实际可达路径的维度不会成为运行时可用维度。报告 passed 不等于该维度已经能查；完成情况还要看逐项 `queryable` 和 `unresolved`。

程序检查这些结构，不会证明“缺的事实确实不存在”或“问的人合适”。已知关系不能为省建模工作而写成缺事实；还应复核未决是否真实、是否影响关联指标。

<a id="iteration"></a>
## 7．怎样小批次试跑和迭代

### 7.1．先验证方法，再扩大范围

在 README 的构建命令上用 `--metrics` 选择少量目标，ID 用英文逗号连接。例如梧桐可以先选 `receipt_count,net_receipts_cents`。若试跑比率，依赖也要包含在同一批：梧桐的 `gross_receipts_cents,returned_cents,return_ratio` 是一个依赖闭合的组合。程序不会自动补选依赖目标。

小批次只缩小 `targets`，业务模型、材料、接入表结构和**完整维度目标**仍会传入；语义模型仍须完整生成，三项检查也照常执行。先看这批是否暴露方法问题，之后用新目录生成完整目标集。

若要合并，除各批依赖闭合外，同名语义模型须内容完全一致，来源输入哈希、客户范围、同名 SQL、粒度声明和维度目标也须一致。只为同一个模型在不同批次各加几个 measures，会造成完整模型冲突。合并工具不会自动把这些差异揉成一个模型；遇到不一致时，重新生成一致的批次，或一次生成完整库。

### 7.2．失败应该改哪里

先看失败发生在哪一层。以下是排查方法，不表示这些现象全部来自同一次运行。

| 现象／记录 | 先核实什么 | 方法该改在哪里 |
| --- | --- | --- |
| 没有调用成功，或输出不能解析；看 `trace.json` | 模型调用错误还是返回格式错误 | 格式错误强化第四段；网络、凭证或超时先排环境，不能靠改业务规则解决 |
| 目标漏项、重复或目录不一致 | 本批真实目标、依赖闭合、已定义与未决是否互斥 | 第一、第四、第五段 |
| `source_check.json` 不通过 | 文件名是否来自输入、quote 是否为连续原文 | 第二段；资料缺失则补充输入，不伪造引用 |
| 原始数据加载失败 | manifest 哈希、计数、表头、原始键和关联是否符合接入约定 | 先核对数据版本与接入问题；不把这些失败归咎于 Skill，也不为过检查改业务口径 |
| `validation-project/build.log` 中 dbt 失败 | 字段、ref、命名、依赖及原生语法 | 第三、第四、第六段；此时三份报告可能写着 checks not executed，并非三项各自发现了错误 |
| `grain_check.json` 不通过 | 声明的一行含义、主键／组合键、唯一关联目标、未匹配行 | 第六段，必要时回第二、第五段补关系事实；同时检查实际数据是否违反已确认事实 |
| `dimension_check.json` 不通过 | 属性局部名、角色、实际可达路径，是否确实缺关系依据 | 第六段；真缺事实按第五段列未决，不能补一个虚构连接 |
| `metricflow_check.json` 不通过 | 原生配置、依赖、表达式及实际存在的列 | 第三、第四、第六段；逐指标编译与 EXPLAIN 会检查真实表达式 |
| 结构通过但数字、单位或解释不对 | 先固定期望与实际结果，定位差异所在层 | 按[测试与判定编写指南](test-guide.md#diagnosis)逐层核查，再修订 Skill 或有依据的业务输入 |

如同一有效输入暴露了框架故障，应保留证据反馈程序问题，不能要求 Skill 用错误业务设计绕过故障。

### 7.3．怎样留下可复核的迭代

每轮记录失败现象、原因判断、改了哪条方法，以及下一轮用什么案例检查。把修正写进自己的 Skill；事实更新写进带来源的业务输入。**不要直接修改返回的 response.json、metrics.yml 或 SQL 后，称为 Skill 已能生成正确结果。**

每次使用新的构建目录和加载目录，保留失败输入、`skill_used.md`、trace、已生成的响应和报告。当前 build 不会覆盖已存在的输出目录，也不会自动将上次失败诊断加入下一次提示；需要你把通用修正落实到 Skill。发生模型请求重试时，要从 trace 区分请求重试与自己发起的新一轮构建。

三项结构检查通过之后，继续按[测试与判定编写指南](test-guide.md)编写独立期望、检验判定程序并定位差异；运行命令仍按 README 执行。

<a id="known-issues"></a>
## 8．真实运行中出现过的配置问题

下表问题来自真实运行，仅摘出配置或表达问题，不展开其他客户的定义。表中编号只用于本文内引用，不能据一次构建成功推断普遍成功率。

| 编号／现象 | 原因 | 怎样在 Skill 中预防 |
| --- | --- | --- |
| 1：模型返回 YAML，`JSONDecodeError`，未生成库 | 把最终落盘格式与模型返回协议混淆 | 第四段明确“只返回一个 JSON 对象”；按 contract 组织内容，YAML 由框架写出 |
| 2：`month` 被报为保留的时间粒度名，dbt 解析失败 | 把时间粒度词当成局部维度名 | 第六段要求时间维度使用实际日期列或非保留的派生日期列名，并在默认统计时间中引用 |
| 3：`metric_time` 被报为 MetricFlow 保留名 | 把查询层的统一时间概念当成模型维度名 | 区分模型时间列与 `metric_time__day`／`metric_time__month` 查询 ID；不使用保留名命名实体或维度 |
| 4：含双下划线的查询 ID 被报为非法名称 | 将查询路径直接填进 `dimensions[].name` | 局部属性只写 `region` 等局部名，实体前缀由语义关系形成；输出前逐个检查 |
| 5：`Duplicate dimension + primary entity pairing`，dbt 拒绝 | 原表和派生表重复使用了同一主实体与时间维度配对；重新生成时曾再次引入 | 在生成全部模型后统一核对配对。不同粒度或行集合使用清楚区分的主实体／primary_entity，不能仅改显示标签 |
| 6：结构检查通过，独立比较报单位错误 | 目录中的单位与指标量纲不一致；单位字段非空无法证明单位正确 | 第二、第三、第四段贯通统计对象、金额或数量单位，以及分子分母量纲；独立期望也比较单位 |
| 7：修订单位时改坏物理字段名，逐指标 SQL 检查报语法错误 | 定向修订连带改动了不应变化的表达式 | 第三段明确字段逐字使用字典标识，展示文字与物理标识分开；修订后重新检查全部引用和配置，不默认未涉及部分一定没变 |
| 8：有 dimensions 的模型未定义 primary entity，dbt 拒绝 | 模型声明不完整 | 第六段要求有维度的模型声明主实体或 primary_entity，并对每个模型给出真实 grain_keys；只补一个名称不足以证明粒度正确 |

第 6 项属于语义与元数据错误，并非原生解析一定会拦截的错误。第 7 项的历史修订方式也不是让学员照做响应补丁；本指南采用“修订 Skill／有依据的输入，再重新生成”的迭代方式。

## 9．结构检查管不住什么

### 9.1．梧桐的两类错误注入

教师曾在真实生成结果的副本中**显式注入**下面两种错误，再执行构建与查询；这不是模型自然生成失败的记录。

| 编号／教师改动 | 检查和查询现象 | 说明 |
| --- | --- | --- |
| 9：把月度累计改成单笔最大值 | 结构检查通过，但 7 月大额会员数得到 0，独立期望为 1 | 表仍可能满足“会员 × 月”唯一，聚合规则却已经变错 |
| 10：把扣退后累计改成实付累计 | 结构检查通过，但 7 月得到 2，独立期望为 1 | 字段都存在、SQL 也能执行，仍无法证明金额构成正确 |

选择独立案例时，要让跨订单累计、门槛相等、全额退回等业务差异真正影响结果，才能识别这些错误。

### 9.2．缺事实不一定自动变成未决

11：青禾缺事实实验中，模型没有可靠地把缺口列入未决，而是补出了未经确认的解释。一次运行通过了三项结构检查，之后被独立测试发现口径错误。这里只引用实验现象与结论，不公开该客户的定义或计算答案。

因此，“要求缺事实时列未决”仍需要人工检查是否执行；来源引文存在、主键唯一、外键能连上和配置可编译，都不能证明业务事实完整。还要检查遗漏事实和冲突、独立计算的数值与单位，以及回答是否忠实解释结果。

## 10．提交前自检

- [ ] Skill 六段能说明触发条件、核对步骤、输出位置和缺依据时的处理；客户事实仍可追溯到输入。
- [ ] `input.json` 是本轮实际要使用的模型与材料；本批目标和完整维度目标已核对，来源文件名不混淆。
- [ ] 每个指标恰好在已定义或未决之一；未决说明写清缺什么、影响什么、向谁核实。
- [ ] 每个模型都先说明一行含义，再声明真实 grain_keys；对象角色、主外键方向和唯一目标有依据。
- [ ] 一对多关联不会放大计数或金额；多阶段规则已放到适当粒度，汇总没有丢失必要关系。
- [ ] 字段名、原生格式、局部维度名、实体配对、指标依赖、目录单位和查询限制逐项核对。
- [ ] 三项检查已实际执行并通过；维度逐项区分“可查询”与“未决”，没有把未执行的报告当成通过。
- [ ] 用独立期望核对真实查询，覆盖会改变答案的业务边界；未从本次结果复制期望。
- [ ] 判定程序能拒绝有代表性的错误；自然语言解释另作语义复核。
- [ ] 保留每次 Skill、输入、响应、失败与检查记录；最终库确实来自所声明的运行，没有用手工改返回结果冒充方法修复。
- [ ] 构建、测试、提交预检及人工审阅分别记录。检查通过不等于真人试做、客户验收或正式发布。

这份指南说明方法和排障，不增加作业任务书之外的必交文件。具体提交路径与范围以随包任务书为准。
