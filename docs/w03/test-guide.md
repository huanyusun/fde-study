# 测试与判定编写指南

这份指南帮助你为自己的客户任务编写 `tests.json` 和判定程序，检查它们是否可靠，并根据记录定位结果差异。安装与运行命令见 [README](README.md)，接口与字段约定以[工具契约](contract.md#测试与判定)为准；梧桐的完整输入和生成物见[样例走读](wutong-walkthrough.md)。

本文只讲写法和核查方法，不增加作业提交物。具体任务、提交目录与范围以随包任务书为准。

<a id="parts"></a>
## 1．测试由哪几部分组成

| 部分 | 你要准备或检查什么 | 职责边界 |
| --- | --- | --- |
| 测试集 | 问题、事先确定的独立期望及其来源 | 说明应该得到什么，不从本轮实际结果复制答案 |
| 判定程序 | 比较期望与实际结果，返回是否通过和具体差异 | 只比较，不调用大模型，不另起查询 |
| 框架 | 按问题调用运营 Agent 的标准问数内核，再调用你的判定程序，保存报告 | 不替你确定业务期望，也不替你实现全部比较项 |

一次测试包含自然语言理解、原生查询和成功结果的解释。你编写的判定程序收到的是结构化期望与实际结果，不能通过重新问一次、重新查一遍来决定哪边正确。自然语言解释另按[第 10 节](#answer-review)人工核查。

<a id="independent-expectations"></a>
## 2．期望怎样独立得出

在运行前先确定期望，再冻结本次测试集。可采用客户已核对过的样本结果、按业务定义逐单手算，或逐记录计算的独立审核程序。审核程序不导入被测指标库，也不调用被测 SQL；另写一段 SQL 仍可能重复同一个口径误解，应先用小表手算校准。

`expected_source` 要让另一个人能复核，至少说清：依据哪份定义、哪版数据、取哪些记录和时间、怎样计入与扣减，以及怎么算到期望。客户确认过的结果还应保留确认材料的实际位置与版本，不能只写“客户说的”或“人工确认”。

梧桐 8 月扣退后收入可追到[收款说明](../../examples/w03/materials/report.md)与 [orders.csv](../../examples/w03/data/orders.csv)：只计 `paid`，按原订单日期归月，WO1 为 10000－2000 分，WO2 为 5000 分，WO3 取消不计，合计 13000 分。来源写出这些步骤，比只写“正确答案 13000”更容易排错。

记录版本信息不等于复制答案。你可以从事先选定、已经核对的材料和加载项目取得版本标识；业务状态、意图、数值及单位仍应独立确定。

<a id="test-cases"></a>
## 3．tests.json 怎样写

### 3.1．先从包内原例读起

文件最外层是非空数组，每项的 `id` 唯一。下面摘录 [examples/w03/tests.json](../../examples/w03/tests.json) 的第一条用例，内容保持原样；放回测试集时，外面还要有数组方括号。其余两条分别检查 7 月和 8 月的月内大额会员数。

```json
{
  "id": "independent-net-income",
  "question": "2026 年 8 月梧桐书店扣退后收入是多少？",
  "expected": {
    "status": "ok",
    "intent": {
      "metrics": [
        "net_receipts_cents"
      ],
      "start": "2026-08-01",
      "end": "2026-09-01",
      "group_by": [],
      "filters": []
    },
    "columns": [
      "net_receipts_cents"
    ],
    "rows": [
      [
        13000
      ]
    ],
    "units": {
      "net_receipts_cents": "cents"
    }
  },
  "expected_source": "独立核算 2026 年 8 月：WO1、WO2 的 paid 实付合计 15000 分，退回 2000 分，差额 13000 分；7 月追加订单不在窗口内。"
}
```

| 字段 | 怎样填写 |
| --- | --- |
| `id` | 给用例取稳定且不重复的名字，便于跨次运行追踪同一问题 |
| `question` | 写实际要交给 Agent 的完整自然语言问题；不要用指标 ID 列表代替业务问法 |
| `expected` | 独立确定的结构化期望；先写状态，成功时补齐意图、列、行和单位 |
| `expected_source` | 写可复核的计算来源；框架不会替你验证这段文字，需与测试集一起保留 |

### 3.2．成功结果的字段

`expected.status` 写 `ok`。`intent` 按[查询与结果契约](contract.md#查询与结果)填写下面五项，不用自然语言公式替代指标 ID。

| 意图字段 | 写法与容易漏掉的地方 |
| --- | --- |
| `metrics` | 指标 ID 数组；一个问题可含多项指标，不能遗漏或增加另一项 |
| `start`、`end` | `YYYY-MM-DD` 字符串；Asia/Shanghai 的半开区间，包含开始日、不含结束日。8 月写到 `2026-09-01`，不是 `2026-08-31` |
| `group_by` | 查询维度 ID 数组；不分组写 `[]`。梧桐成交门店用 `store`，实际是否可用要看加载项目的 `dimensions.json` |
| `filters` | 不筛选写 `[]`。每项含 `field`、`op`、`value`；`eq` 用字符串，`in` 用非空字符串数组，多项之间为 AND。不能写任意 OR 或 SQL |

筛选写法示例为 `{"field":"store","op":"eq","value":"W01"}`；它是意图片段，不是已经运行的测试用例。维度、筛选值须来自当前数据与指标可达范围，多指标组合还要有共同可用路径。

`columns` 列出分组列和指标列的名字，`rows` 是二维数组，每行的值按列名位置排列。比如 `columns` 为 `["store", "net_receipts_cents"]`，一行 `["W01", 6000]` 表示这个门店的金额；两者必须一起解释，不能假设所有结果第一格都是数字。`units` 用指标 ID 作键，值是约定单位，例如 `cents`、`count`、`ratio`。分与元、原始比率与百分数不能混比。

### 3.3．四种状态，及 null 与 0

下表是**期望写法示例**，依据查询规则编写，不是这些问题的新运行记录。

| 梧桐场景 | expected 写法要点 |
| --- | --- |
| 8 月月内大额会员数 | `status` 为 `ok`，按完整意图填写，指标列对应 `rows: [[0]]`、单位 `count`；覆盖内已知为零 |
| 6 月没有订单时的退回占比 | `status` 为 `ok`，指标为 `return_ratio`，时间为 `[2026-06-01, 2026-07-01)`，`rows: [[null]]`、单位 `ratio` |
| “梧桐书店扣退后收入是多少？”未给时间 | `{"status":"clarify"}` |
| 查覆盖期外的 2026 年 9 月，或只查半个月的月内大额会员数 | `{"status":"unsupported"}` |
| 在受控故障条件下检查执行失败状态 | `{"status":"error"}`；仅示范状态期望的写法，不把正常业务问题预设成失败 |

例如，缺时间的完整用例可以这样写；这是自拟写法示例，未声明已运行：

```json
{
  "id": "wutong-needs-period",
  "question": "梧桐书店扣退后收入是多少？",
  "expected": {"status": "clarify"},
  "expected_source": "未给时间范围，需先确认期间，不能默认选取某个月。"
}
```

`clarify`、`unsupported` 既可能来自意图理解，也可能由查询规则返回；`error` 可能来自模型调用、响应格式或查询执行失败，具体阶段要看记录。非 `ok` 期望只比较状态及明确锁定的版本，不要求成功结果的列、行或数字。原因和解释是否恰当另作人工核查。

梧桐数据覆盖到 2026-09-01，终点不含。超出覆盖不能按零。当前引擎在**不分组**时，把返回行中 `simple` 指标的空值改为 0，比率保留 null；这不是把所有空值或缺行补零。6 月扣退后收入可以是已知的 0，而同月零分母的退回占比未定义，应为 null。不要把 null、缺字段、空数组和 `[[0]]` 当成同一结果。

### 3.4．什么时候锁版本

同一个期望对应固定数据快照，或要防止误加载旧库时，在 `expected` 中增加以下字段。只比较明确写入的版本，缺失也要报差异。

| 字段 | 从哪里核对、锁定什么 |
| --- | --- |
| `data_version` | 加载项目 `dataset.json` 的 `id`，对应所选数据版本 |
| `data_sha256` | 引擎对 `dataset.json` 去掉 `library_sha256` 后、按键排序的 JSON 序列化内容计算的哈希；并非某张 CSV 的哈希 |
| `catalog_sha256` | `dataset.json` 的 `library_sha256`；实际覆盖加载前库目录内的 JSON、YML、SQL 文件内容，不只是 `catalog.json` 一个文件 |

先确认加载项目、数据 manifest 和库版本是本次选定版本，再按上述来源锁定。换用规模数据、业务口径修订或重新生成库后，重新核对版本与独立期望，不把旧哈希机械复制过去。测试纯比较逻辑时也可给版本字段使用明确的合成标识，但不能把它当成真实数据哈希。

当前非 `ok` 返回通常没有这三个版本字段；没有实际字段依据时，不要给非 `ok` 期望强加成功结果的版本信息。需要拒绝错版本的注入检查，应选择已经明确锁版本的成功期望。

<a id="case-selection"></a>
## 4．用例怎样选

先列“这条用例要抓什么错误”，再选择有区分力的数据和问法。

| 指标或场景 | 选例时让什么差异真正影响结果 |
| --- | --- |
| 单数 | 统计对象、取消单、重复关联是否改变计数 |
| 金额 | 计入项与扣减项是否齐全，分与元是否混淆 |
| 比率 | 分子、分母、零分母，以及原始比率与百分数 |
| 按期累计与门槛 | 跨订单累计、归月与恰好等于门槛；梧桐 7 月 W1 扣退后恰好 10000 分，应计入 |
| 分组与筛选 | 角色、分组键、筛选是否漏加或多加，漏组是否被发现 |
| 查询边界 | 未给时间、超出覆盖、整月限制、覆盖内无业务与不支持的查询 |

梧桐 8 月的成交门店与会员归属门店恰好对应，不能用该月的分组结果证明两种关系已被区分。按 [orders.csv](../../examples/w03/data/orders.csv) 和 [members.csv](../../examples/w03/data/members.csv) 手算 7 月：WO4 在 W01 贡献 6000 分；WO5 在 W02 贡献 4000 分，但两单的会员 W1 都归属 W01；WO6 扣退后为 0。

| 分组含义 | W01 | W02 | 合计 |
| --- | ---: | ---: | ---: |
| 成交门店 | 6000 分 | 4000 分 | 10000 分 |
| 会员归属门店 | 10000 分 | 0 分 | 10000 分 |

这是原始数据的独立手算，不是 Agent 实际查询结果。问句应写明是哪种门店。如果材料没有确认“按门店”的默认含义，先把期望定为澄清并请客户确认；实际若直接选一种解释，应登记差异，不能改期望迁就它。确认默认含义后，再把依据写进业务材料。

同义问法围绕同一个已确认问题改写，预先约定等价的指标、时间、分组和筛选，比较等价意图与结果；不能因为数字相同就当作同义。保留每种问法，才能知道哪一种触发了误解。

规模数据由课程另行发放，是教师造数程序按固定种子生成的一份大数据，学员不自行复制或造数。在规模数据上另建加载项目进行验证；期望须按这份数据的版本独立计算，数据量大时用[第 2 节](#independent-expectations)的独立审核程序逐记录计算，不能照抄小样本的答案。运行时记录环境与耗时，不设统一的响应时间目标。

## 5．判定程序怎样实现

### 5.1．接口与扩展起点

入口从标准输入读取一个 JSON 对象 `{"expected": ..., "actual": ...}`，向标准输出写一个 JSON 对象 `{"passed": true, "differences": []}`。`passed` 必须是布尔值，`differences` 必须是数组；调试信息放标准错误，不夹在 JSON 前后。框架对判定进程设 30 秒超时，非零退出或返回格式错误会中断测试。

[客户判定模板](../../templates/w03/customer/judge.py)的 `compare` 默认未实现。可参考 [examples/w03/judge.py](../../examples/w03/judge.py)，但它只处理单指标单行，不支持完整的多指标、分组、空值和版本比较，必须自行扩展。它对所有数值使用同一相对容差 `1e-9` 和绝对容差 `1e-7`，只适合样例这样的小数额，不能作为任意金额的精确核对方法。

例如，期望整数 `1000000000`、实际整数 `1000000001`，在样例的统一容差下会被判通过。金额相差 1 分也被放过，是因为相对容差随数值变大。这是合成比较输入的反例，不是梧桐业务数据或实际问数记录。

### 5.2．按顺序比较

| 顺序 | 实现要点 | differences 应指出什么 |
| --- | --- | --- |
| 1．状态 | 先检查期望状态是否为支持的四种状态，再比较实际状态；不一致即失败，不能继续把残留数字当成功 | 期望状态、实际状态 |
| 2．版本 | 逐一检查期望里明确锁定的版本字段；非 `ok` 在此结束，不进入数值比较 | 哪个字段不一致或缺失 |
| 3．意图 | 比较指标、半开时间、分组、筛选；不能只检查意图里出现过目标指标 | 字段路径及两边值，例如 `intent.end` |
| 4．单位 | 对照每个指标的单位，漏项、多项或单位不同都应拒绝 | 指标 ID、期望单位、实际单位 |
| 5．列 | 列名非重复、集合吻合；每行长度与各自列名数量一致。允许列顺序变化时，必须先按列名映射 | 漏列、多列、重复列、行长度 |
| 6．行 | 按分组键对齐，检查缺组、多组和重复组；无分组的单次汇总应只有一行 | 分组键及缺失、额外或重复情况 |
| 7．值 | 先分清 null 与数字，再按整数或浮点规则比较；布尔值不能当作 0 或 1 | 分组键、指标、期望、实际及使用的容差 |

意图可以先作严格结构比较。要接受等价顺序时，先检查结构、重复和合法性，再规范化：指标和分组按名字对齐、AND 筛选条件排序、`in` 的值排序。不删除多出的筛选，不把成交门店和归属门店规范成同一个角色，也不把不同时间归一成“同一个月”。SQL 文本不要求逐字相同。

行对齐时，分别把两边每行变成“列名 → 值”，以 `group_by` 中各列的值组成键。插入索引前先检查这个键是否已存在，不能直接用字典覆盖重复组；索引建完再比较两边键集合，最后逐组逐指标比较。无分组可用空元组作键，仍须单独检查期望与实际都只有一行。分组键按约定类型精确比较，不用数值容差。

### 5.3．整数、浮点、空值

**期望为整数时精确比较数值**。分、单数等期望写 JSON 整数，实际 `13000.0` 与期望 `13000` 可以相等，`13001` 必须失败；不要先把整数转成浮点。比率等浮点期望写成小数，即使是零也写 `0.0`，采用预先声明的容差。

下面只演示值比较这一小段，不是完整判定程序。容差示例沿用 `rel_tol=1e-9`、`abs_tol=1e-7`，实际任务应按精度要求确定并记入测试说明；不能为让失败通过而临时放宽。

```python
import math

def equal_number_or_null(want, got, *, rel_tol=1e-9, abs_tol=1e-7):
    if want is None:
        return got is None
    if type(want) not in (int, float) or type(got) not in (int, float):
        return False  # 同时拒绝布尔值和数字字符串
    if type(got) is float and not math.isfinite(got):
        return False
    if type(want) is int:
        return got == want
    return math.isfinite(want) and math.isclose(
        want, got, rel_tol=rel_tol, abs_tol=abs_tol)
```

空值只等于空值，0 不能冒充 null；缺字段应在结构检查时失败。布尔值即使在语言里能与 0、1 相等，也不是本协议的数值。浮点比较同时检查有限值，不接受 NaN 或无穷大；不要先四舍五入成展示文字再比较。

`differences` 可以用字符串或对象数组，但要让人能据此定位。例如 `{"path":"rows","group":{"store":"W02"},"metric":"net_receipts_cents","expected":4000,"actual":5000,"rule":"exact"}`。最后由差异数组是否为空计算 `passed`，避免出现 `passed: true` 却带着差异的自相矛盾结果。

<a id="judge-checks"></a>
## 6．怎样检验判定程序本身

框架在第一条正式问数前，把首条期望同时当作期望和实际调用一次判定程序。这只检查进程能运行、返回格式符合接口，不检验能否拒绝错误，也不以该次自比的 `passed` 值决定是否继续。你需要另外确认正确输入通过、错误输入被拒。

从一份已与独立期望核对过的真实 `result.json` 制作深拷贝，原件只读保留。每份副本只改一件事，记录原文件、改动字段、改前改后值、预期判定与实际判定。改出的结果明确标为合成注入，不称为模型真实犯错。null 场景如果尚无真实结果，可以单独构造比较输入，注明只是判定程序自检。

| 注入项 | 梧桐写法示例 | 应有判定 |
| --- | --- | --- |
| 错误日期但数字不变 | 8 月结束日从 9 月 1 日改为 8 月 31 日 | 拒绝意图差异 |
| 错指标 | 把扣退后收入的指标 ID 改为到账总额 | 拒绝意图差异 |
| 多出筛选 | 原本全门店，实际多出 W01 筛选 | 拒绝意图差异 |
| 错单位 | `cents` 改成 `yuan`，数字保留 | 拒绝单位差异 |
| 错数值 | 13000 改为 15000 | 拒绝数值差异 |
| error 带原数字 | 保留正确行，仅把状态改为 `error` | 拒绝状态差异 |
| 错数据版本 | 在已锁版本的成功用例中替换实际 `data_version` | 拒绝版本差异 |
| 漏组 | 删除一条门店结果 | 拒绝缺组 |
| 重复组 | 重复追加同一门店的一行 | 拒绝重复组，不能覆盖后通过 |
| null 改成 0 | 把未定义的退回占比改为 0 | 拒绝空值差异 |

这十项应全部被拒。再做两个正向检查：原始正确结果应通过，只改变行顺序应通过。扩展了多指标、列重排或意图规范化，也要相应检查新增能力没有漏比字段。

数值分支另检查 `13000` 对 `13000.0` 通过、对 `13001` 拒绝，以及 `1000000000` 对 `1000000001` 拒绝；比率分别用容差内外的差异检查。给数值位置放入 `true`、数字字符串或非有限浮点输入应拒绝。非有限值属于程序防御性自检，不能写进合法 JSON 测试集。错误注入不能替代真实 Agent 用例，两者分别记录。

<a id="reports"></a>
## 7．运行与读报告

完整命令按 [README 的安装与样例闭环](README.md#安装与样例闭环)及[开发与使用](README.md#青禾开发与使用)执行。`--judge-command` 后面是你的判定进程及其参数，框架的 `--project`、`--cases`、`--output` 等参数放在它前面；需要 `--cwd` 时也放在前面，它用于指定判定子进程的工作目录。

测试输出目录不能复用，已存在会报错。每轮保留新目录，不覆盖首次失败。完整报告 `metric_test_report.json` 含：

| 字段 | 看什么 |
| --- | --- |
| `contract_version` | 报告使用的接口版本 |
| `complete` | 是否已走完全部用例；不是正确率 |
| `passed`、`total` | 完成后的通过数与总数；`passed` 在这里是数量，单条比较内才是布尔值 |
| `cases` | 每项包含 `id`、`question`、`expected`、`actual`、`comparison`；从 `comparison.differences` 找差异，再回看两边证据 |

每完成一条用例，框架先写 `complete: false` 的进度报告，只含版本、完成标记和已完成的 `cases`；全部结束后才写汇总数。中途失败可能只有部分报告，第一条尚未写出时也可能没有报告。`expected_source` 不会复制进报告，原测试集和核算依据要一并保存。不能仅凭命令退出码或 `complete: true` 判断通过，还要看通过数与每条比较。

测试中的单次记录位于本次输出目录的 `traces/<trace_id>/`，由 `actual.trace_id` 定位：

| 文件 | 用来核对什么 |
| --- | --- |
| `result.json` | 最终结构化结果；成功时含意图、SQL、列、行、单位、版本及回答，失败时先看状态、代码和原因 |
| `intent-trace.json` | 问题、上下文、中文目录、可用维度等实际输入，以及理解调用的原始回复或错误 |
| `answer-trace.json` | 成功查询后的解释调用输入和回复；未到解释阶段时可能不存在 |

失败越早，后续记录越可能不存在。自然语言回答不是查询原始数据；成功结果的列与行看 `result.json`，不能从回答文字反推一份“实际值”。

<a id="diagnosis"></a>
## 8．结果对不上时逐层看什么

本节处理**结构检查通过、结果不对**。构建或加载检查失败先按[构建 Skill 编写指南第 7.2 节](skill-guide.md#iteration)排查。开始前固定问题、测试集、Skill、业务输入、数据及库版本、加载项目、报告目录和 `trace_id`，不要一看到差异就改期望或提示词。

下表中的“项目”指测试命令 `--project` 实际指定的加载目录，“构建目录”指生成该库时保留的输出目录。

| 层次 | 看哪个文件与证据 | 该改哪里 |
| --- | --- | --- |
| 问题与意图 | `tests.json` 的问句与独立意图；单次 `intent-trace.json`、`result.json`。核对指标、半开时间、分组角色、额外筛选；歧义是否真的有业务默认依据 | 问句或期望确有歧义，先确认业务含义；理解选错时检查项目 `catalog.json` 的名称、别名与维度说明。目录方法错误则改 Skill 或补已确认输入后重新生成；输入无误仍误解时保留记录反馈，不能保证改 Skill 就能修好 |
| 业务模型与材料 | 构建目录 `input.json` 中实际送入的业务模型、材料和目标；再对照原始材料及确认记录。确认定义、时间和金额构成是否齐全、是否冲突 | 回访补有依据的事实，更新业务模型与材料；不在生成结果里临时补一个猜测 |
| 实际加载的指标库 | 项目 `models/metrics.yml` 的 measure 表达式、`models/*.sql` 的派生计算、`catalog.json` 的中文目录和单位、`dimensions.json` 的可达路径；用 `dataset.json` 核对版本 | 加载旧库就重新加载正确库；表达式、聚合或角色转换错，改 Skill 的相应方法，重新生成、检查、加载。不能直接手改生成定义或 SQL 后宣称 Skill 已修复 |
| SQL 与原始结果 | 单次 `result.json` 的 `sql`、`columns`、`rows`；对照相应版本的原始 CSV 逐单核算。检查过滤、关联放大、归月、扣减与分组 | 回到造成差异的业务输入或生成方法；若定义和输入都正确而执行仍不符，保留最小证据反馈程序问题，不改业务口径绕过 |
| 期望来源 | 原 `tests.json` 的 `expected_source`、手算明细或独立审核程序及数据版本。检查是否算漏记录、用错版本或重复被测算法 | 只有业务依据证明期望错误时才修订，并保存旧期望、修订原因和新来源；不以实际输出作为更改依据 |
| 判定逻辑 | 自己的判定源码、`comparison.differences`、本次 expected／actual 和注入自检结果。看是否漏比意图、用错单位、丢组、把 null 当零或容差过宽 | 修订判定程序，重做正确输入、错误注入和顺序变化检查，再回归全部用例 |

SQL 中可能用包含两端的 `BETWEEN`，查询协议仍比较半开区间；引擎会把终点减一天后交给原生查询。不能仅因 SQL 形式不同就报业务错误，也不能因为数字碰巧相同就跳过意图检查。

<a id="regression"></a>
## 9．修复后怎样回归与留记录

每轮写清失败现象、证据、原因判断、只改了哪个因素、准备怎样验证。保留首次失败，不把修复后的结果覆盖回原目录。构建、加载和测试分别使用新目录，保证报告能追到实际输入与版本。

改 Skill 或补业务输入后，要重新生成库、通过检查、加载，再让 Agent 按测试问题真实问数。回归所有原先通过的用例，包含其他指标、分组、状态、同义问法及已纳入的规模数据，不能只跑刚修好的那一条。

独立 SQL 或小表核验可以缩小原因范围，但不能代替“理解问题 → 查询 → 解释 → 判定”的整条链路。修订独立期望或判定程序也要留前后差异；重新比较旧结果仅能证明比较逻辑的变化，不能登记为新问数。

<a id="answer-review"></a>
## 10．解释怎样人工核查

成功查询后的解释调用会收到问题、客户与数据上下文、去掉 SQL 的结构化结果，以及选中指标的目录定义；它没有收到实际 SQL。人工核查时同时读 `result.json` 和 `answer-trace.json`，不能因回答流畅就推定 SQL 或口径正确。

- **客户与范围**：是否对应当前客户、当前数据覆盖，没有借其他客户的知识补结论。
- **时间**：是否说清开始与结束，终点不含；没有把整月限制说成支持任意日期。
- **实际筛选与分组**：是否忠实描述已执行条件，分清成交门店与归属门店，没有声称执行并不存在的筛选。
- **口径**：是否符合已确认的计入、排除、扣减与累计方法；目录说明还需与执行定义对照。
- **单位与空值**：13000 分是否正确展示为 130.00 元；比率与百分数是否正确换算；零、未定义和无覆盖是否分清。

非 `ok` 时核查原因是否足以说明缺口或失败，没有把失败解释成零。分别记录查询结果正确、解释忠实、客户确认口径和结果、业务效果验证的证据。**机器判定通过不等于客户验收**。

<a id="checklist"></a>
## 11．自检清单

- [ ] 每条用例有唯一 ID、完整问题、独立期望和可复核来源，期望在运行前确定。
- [ ] 用例能区分要抓的正确与错误算法，歧义有确认依据，多问法没有冒充新增业务覆盖，规模数据的期望按该数据版本独立计算、没有照抄小样本。
- [ ] 四种状态、半开时间、列与行、单位、null 与 0、需要锁定的版本写法已核对。
- [ ] 判定只比较，状态、版本、意图、单位、列、分组键和值逐项检查，拒绝漏组、多组与重复组。
- [ ] 整数精确比较数值，浮点容差明确；布尔值、数字字符串、缺值不会冒充合法结果。
- [ ] 十项注入全部被拒，正确原始结果和仅改行顺序的结果通过，新增比较能力也有相应自检。
- [ ] 报告已完整结束且通过数与总数核对，原测试集、核算依据及每轮输入输出均保留。
- [ ] 失败按证据定位，修复后回归全部原有用例，没有用手改生成物或小表核算冒充整条链路通过。
- [ ] 回答解释已单独核查；程序检查、真实问数、人工核查和客户验收分别登记。

以上用于检查测试集和判定程序本身的质量，提交要求仍以任务书为准。
