### 二、业务对象及关系

本轮可执行对象定义源为 `customer/w05/member.linkml.yaml`（核心类 `Member`、`SourceAccount`、`Store`），以下业务语义与之一致，具体判断由 `customer/w05/solution.py` 三个客户函数执行：

1. **来源账户（`SourceAccount`）**：
   - 含义：各原始业务系统的独立账户实体，使用带命名空间的唯一编号 `CRM:<hy_id>` 与 `POS:<pos_member_id>`，保留不可变文件与行号溯源（`source_file`、`source_row`，行号自去掉表头后第 1 行起算）。来源：材料（`03_身份关联与数据使用说明.md` 第一节、`06_输入与工程说明.md` 第三节）。
   - 不可混同：不同系统编号相同不代表同一账户；姓名、脱敏手机号、设备号等相似线索不能自动合并身份。来源：材料（`03_身份关联与数据使用说明.md` 第一、二节）。
2. **统一会员（`Member`，`identity_status = verified`）**：
   - 含义：经**当前有效且依据可定位**的业务记录确认归属同一自然人的来源账户集合（多来源合并为 `resolved`，有覆盖依据支持独立开户的单来源账户为 `singleton`），由框架分配统一 `member_id`（`U...`）。
   - 身份依据采信规则：
     - `migration_records.csv`：仅采信参考日内有效（`valid_from <= 2026-09-01 < valid_until`）、`status == "success"`、双端均在本次导出且通过 `verify_basis` 的记录，作为 `relation = "same"` 边（本批 `39,917` 条有效；其余 `3` 条状态为 `failed`/`revoked`/`unknown` 的历史尝试记录不采信并写入 `findings`）。来源：材料（`03_身份关联与数据使用说明.md` 第二节）与数据计算（`migration_records.csv` 核查）。
     - `account_review_records.csv`：仅采信参考日内有效、`status == "current"`、双端均在本次导出且通过 `verify_basis` 的记录，按 `conclusion` 产生 `same` 或 `different` 边（本批共 `46,018` 条，其中 `11` 条右端账户不在本次导出中，不建边而保留引用与缺失说明写入 `findings`；其余 `46,007` 条有效，含 `35,927` 条 `same` 与 `10,080` 条 `different`）。来源：材料（`03_身份关联与数据使用说明.md` 第二节）与数据计算（`account_review_records.csv` 核查）。
     - 独立开户认定（`verified_singletons`）：依据 `coverage.json` 的 `account_review` 声明（覆盖两来源全部导出账户，并校对文件 SHA-256 一致），未确认登记人的例外账户由 `operational_verification.csv` 中 `kind == "abnormal_identity"` 的有效记录列明（`12,001` 个 CRM 账户），其余不在例外中的无关联边账户认定为独立开户对象。来源：材料（`coverage.json` `account_review`、`06_输入与工程说明.md` 第二节）与数据计算（`operational_verification.csv` 核查）。
     - 冲突处理：若有效 `same` 连通分量中存在有效 `different` 边，框架判为 `conflict` 不强行合并。本批数据实测无跨边图冲突（`conflict = 0`）。来源：材料（`03_身份关联与数据使用说明.md` 第二节）与数据计算（冲突图试跑核查）。
3. **未决来源与独立财务桶（`Member`，`identity_status = unresolved`）**：
   - 含义：无法确认登记人归属或存在身份冲突的来源账户（本批为 `12,001` 个经 `operational_verification.csv` 确认为 `abnormal_identity` 的未确认登记人账户）。框架不将其合并为自然人，而是按来源账户各自建立独立财务桶（`X...`），以保证订单与金额在财务核算中守恒。
   - 不可当成什么：**未决来源账户与独立财务桶不是已核实自然人**，不能计作已验收的精确自然人数或会员运营可联系对象。来源：材料（`05_作业任务书.md` 第五节、`06_输入与工程说明.md` 第三、四节）与数据计算。
4. **门店关系（`Store`：注册门店 vs 购买门店）**：
   - `registered_store` / `registered_stores` 仅表示来源账户的**注册门店关系**；订单中的 `store_id`（`shop_cd`）表示**购买门店（交易发生地）**，两者含义不同、绝不合并或互替。
   - CRM 来源账户提供 `reg_shop`（经 NFKC/去空白/大写归一）；旧 POS 账户无注册门店字段，保持为 `None`/未知，**绝不用 POS 订单的购买门店反填**。
   - 同一统一会员关联多个 CRM 账户时，可拥有多个注册门店（去重集合）；单店圈选按“存在该店注册关系”命中并按会员去重，全公司人数不能由各店人数直接相加；POS 独有会员因无已知注册门店，在单店查询中不归入该店名单、也不重复列为每家店的待核名单，只在范围说明中提示“注册关系未知不等于确定不属于该店”。来源：材料（`02_W05新需求说明.md` 第四节、`03_身份关联与数据使用说明.md` 第一、三节）。
5. **会员属性三分法（正常值 / 来源冲突 / 真实缺失）**：
   - 承接 W04 清洗与缺失值规范：CRM 姓名字段中的空字符串 `""`、`"NULL"`、`"无"`、`"-"`（本批分别出现 `4,179` / `888` / `521` / `112` 次）均属**真实缺失标记**，在 `sources` 中保留溯源位置，在业务属性中不作为真实姓名参与展示或冲突判定。来源：数据计算（`crm_member_export.csv` `nm` 字段剖析）与材料（`05_作业任务书.md` 第三节第 2 步）。
   - 多来源合并后，若有效姓名、有效等级存在多个不同值，则明确记录入 `conflicts`，且代表属性 `display_name` / `tier` 置为 `None`（不强行取第一条覆盖冲突）；仅在全部有效来源值一致时给出唯一代表值；所有有效来源均无值时表达为真实缺失（`None` 且不记冲突）。来源：材料（`03_身份关联与数据使用说明.md` 第三节、`06_输入与工程说明.md` 第三节）。

### 三、订单、金额与复购的统计选择（W05 粒度修订）

1. **`buyer_count` 及人数类指标粒度变更**：
   - W04 阶段受限于单 CRM 数据，`buyer_count` 统计的是“不同 CRM 会员账户数”。
   - W05 接入统一身份映射与未决来源独立财务桶后，`buyer_count` 统计的是**购买财务实体数**（即：产生有效购买的已核实统一会员数 + 未决来源独立财务桶数），**不等于全公司精确自然人数**。
   - 本轮须同步更新 `work/library/catalog.json` 中 `buyer_count` 的显示名为 `购买财务实体数`，并在 `work/library/metrics.yml` 的 `description` 中写明该粒度及“精确自然人数待核”边界；保留原指标 ID、公式、窗口与历史 `sources` 原文。未分组查询 `buyer_count` 时，回答首句必须直接说明统计对象为购买财务实体数、自然人数待核。来源：材料（`05_作业任务书.md` 第三节第 4 步、`06_输入与工程说明.md` 第四节）。
2. **其他受身份粒度影响的指标**：
   - 包括 `refund_buyer_count`、`new_member_count`、`first_buyer_count`、`monthly_buyer_count`、`monthly_repeat_buyer_count`、`monthly_repeat_rate`、`monthly_paid_buyer_count`、`monthly_paid_repeat_buyer_count`、`monthly_paid_repeat_rate`、`avg_buyer_value`、`purchase_frequency`：其 `member_id` 粒度均由 CRM 账户升级为“已核实统一会员 + 未决来源独立财务桶”。其中 `new_member_count` 的注册日期取来源 CRM 已知入会日期最早值，POS 独有账户注册日期未知，不以建档日期替代，亦不可验收为完整新入会自然人数。来源：材料（`06_输入与工程说明.md` 第四节、`platform/fde_product/w05/prepare.py` 语义承接逻辑）。
3. **消费净额、有效购买与沉睡条件**：
   - **消费净额（`net_sales_cents`）**：仅计支付状态为 `paid`（含已支付/已完成/部分退款/全额退款）的订单之 `paid_cents - refund_cents`，取消订单不计，异常退款（`refund > paid`）隔离；金额以**分**为内部计算单位（3,000 元 = `300000` 分）；时间窗口左闭右开 `[start, end)`。来源：材料（`02_W05新需求说明.md` 第四节、`06_输入与工程说明.md` 第二、三节）。
   - **有效购买与沉睡**：存在有效购买（`status == 'paid'` 且 `paid_cents > refund_cents`，即实付大于退款；全额退款与已取消订单不算有效购买），且最近一次有效购买距固定参考日 `2026-09-01` 满 `60` 天（`>= 60` 天；59 天不满足，60/61 天满足）；覆盖窗口内无有效购买不自动归入沉睡。来源：材料（`02_W05新需求说明.md` 第四节、`05_作业任务书.md` 第三节第 5 步）。
   - **运营排除与经营指标分离**：员工/异常身份的运营排除仅作用于推荐名单，**不删除源订单，不扣减经营金额或既有经营指标**。来源：材料（`04_运营对象核验说明.md` 第二节）。

### 六、工作账、核验记录与联系限制的解释

1. **运营对象核验（`operational_verification.csv`，共 `12,308` 条，全部 `current` / `confirmed` 且通过 `verify_basis`）**：
   - **员工（`kind = employee`，`307` 条：`288` CRM + `19` POS）**：`scope = member`，经已核实身份关系作用于整个统一会员（`member_excluded = True`），不推荐联系。来源：材料（`04_运营对象核验说明.md` 第一节）与数据计算。
   - **异常身份（`kind = abnormal_identity`，`12,001` 条，全为 CRM）**：`scope = account`，经有效核验确认的按账户级排除运营推荐（列入 `confirmed_exclusions` 与 `account_exclusions`），不无条件传播给其他关联账户；仅疑似、缺证据或依据冲突的才列为运营待核（`pending_verifications`）；仅当会员全部来源账户均被排除时 `all_source_accounts_excluded = True`。运营核验排除结论与“自然人登记人身份是否查清”分别处理。来源：材料（`04_运营对象核验说明.md` 第一节）、数据计算与真实访谈（2026-11-26，老周 `MSG-06715`）。
   - **覆盖解释**：`coverage.json` 的 `operational_verification` 声明已覆盖两来源导出账户的员工登记与注册授权复核（核对两源表 SHA-256 一致），但“无记录”仅表示本批未发现相应排除，不声称已证明永久非员工/异常。来源：材料（`coverage.json`、`04_运营对象核验说明.md` 第一节）。
2. **联系限制合并规则（CRM 备注 + 小林勿扰工作账 + 补充确认记录 + 回访工作账）**：
   - **CRM 备注（`crm_member_export.csv` `tag` 列）**：承接 W04 R7，明确以“勿打电话”开头限制 `telephone`，以“勿发短信”开头限制 `sms`，明确“请勿再联系”限制 `all`（本批共 `443` 行含明确 `勿打电话`/`勿发短信` 条目，注意部分记录以空格、斜杠或中英文标点分隔，解析时须完整切分避免遗漏）。来源：材料（`05_联系限制与建议说明.md` 第一节、`docs/w04/business_model.md` R7）与数据计算。
   - **小林勿扰工作账（`121` 条）与补充确认记录（`contact_scope_confirmation.csv`，`121` 条一一对应）**：原工作账仅有原因（本人要求/投诉/其他），不能推定渠道；须结合补充确认记录解释：
