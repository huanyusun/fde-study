# V04 ChipNeMo 的任务选择与评价

> 视频 18:36(article 1028697)。字幕稿本地见 `transcripts/v04-ChipNeMo的任务选择与评价.md`(不进 Git)。

## 核心方法与机制

NVIDIA ChipNeMo(2023 论文)当作 SOW 案例:把"提高芯片设计工程师效率"的宽泛目标拆成**本阶段三类应用 + 一类排除**。

1. **范围拆解**:调查工程师工作流 → 四类候选场景(文档问答/EDA 脚本生成/缺陷摘要分析/日志排查辅助)→ 第一阶段做前三类,日志排查明确排除留待后续——排除项写进 SOW。
2. **每个应用写清输入/依据/输出/边界**:问答(覆盖哪些材料=支持哪些问题;领域适配+检索增强);脚本生成(限定 Python/TCL 两种工具环境,工具知识准备由人工整理接口说明——人机分工);缺陷分析(同一输入按角色出三类输出:技术摘要/管理摘要/任务分配建议,分别写要求)。
3. **三方职责**:研发(乙方)、领域工程师(供资料/任务样本/参与评价,类甲方)、使用者;数据、环境、人员投入写入安排。
4. **分层评估**(关键):
   - 问答:检索表现与回答质量**分开检查**——结果差时能区分是"资料没找到"还是"找到了没用好";
   - 脚本:简单任务自动评估集,复杂任务人工评正确性;
   - 缺陷摘要:40 条真实缺陷追踪结果作评估集,人工打分。

## 与青禾沙盘的连接点

- **分层评估思想**直接映射到本周测试设计:意图(找没找对指标/时间)与数值(算得对不对)分开判、解释另作人工核查——对应任务书"测试检查意图、数值、分组、单位,解释另留人工核查记录"。
- 范围排除的写法(本期做 A/B/C,日志排查类留待后续)对应 SOW「本期、后续与排除范围」;付费资格月报"暂不按门店渠道拆"也是同类边界声明。

## 可用于作业的证据 / 判断

- 评估集要来自真实记录(40 条缺陷追踪)——我们的小样本手算期望/规模数据审核程序同理,期望与数据版本绑定。
- "同一输入服务不同用途时分别写输出要求"——38 项指标里同名口径在不同报表的差异(如退款订单 vs 退款金额的归属)要分别写定义。

## 课件补充(26 页结构,比字幕稿更细的点)

- **总体目标与阶段范围分开说明**:总体目标(提高工程师效率)与阶段范围(开发和评估前三类应用、确认它们在相关任务中提供哪些帮助)分开陈述;其他同样影响效率的工作留后续阶段。
- 每项应用按**输入/依据/输出**三段定义:问答(输入=工程师问题、依据=内部设计资料、输出=回答,回答须符合公司实际设计工具情况;覆盖哪些资料/支持哪些问题直接决定能帮什么);脚本(接自然语言描述生成工具脚本,工具环境 Python 与 Tcl 二选一,**支持哪种工具就是工作范围的一部分**);缺陷(输入=内部缺陷系统记录,输出三种)。
- **领域适配 + 回答时检索**两条腿:通用模型不熟公司内部知识——用内部文档和代码继续训练 + 回答时检索相关文档作为本次依据。
- **问答评价**:为测试问题准备参考答案和对应文档段落;①检查检索表现(有没有找到相关知识)②人工评价回答质量。**分开检查才能区分要改的是资料查找还是对资料的理解使用**。
- **脚本评价**:较简单 Python 任务用自动评估集;复杂任务由工程师评正确性;复杂任务评估条件=已为模型提供相关工具接口说明——**这些资料由谁准备要提前约定(SOW)**。
- **缺陷评价**:40 条缺陷记录留出评估集,技术/管理/分派三种输出分别人工打分;各项用途分别检查才能看出对应要求是否满足。
- **能力验证与实际效率改善分别确认**:确认实际改善要观察使用、比较同类工作人工总耗时(计入检查、修正、必要配合);**若本阶段承担效率目标,使用安排和效果观察也进工作范围**。
- 检查→验收条件的四件套:检查范围(哪些任务属本阶段)/完成要求(须满足什么)/检查责任(谁组织谁确认)/后续处理(不符怎么办)。
- 收尾链条:大的业务期待→具体任务与明确范围→分工、配合与完成条件→**各方理解一致、可执行可检查的约定**(内部项目未必叫 SOW,事项一样要约定清楚);知识/规则/关系落到系统 → 引出 V05。
