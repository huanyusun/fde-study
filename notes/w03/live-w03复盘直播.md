## 一、访谈点评

核心是"带草稿和证据去访谈",别把访谈次数花在补缺口上。

| 讲评要点 | 做法 |
| --- | --- |
| 访谈前带草稿和证据 | 未带正文就追问细节,消耗访谈次数且无法补全缺口;把提案写成条款并附查询校验证据,请对方核查 |
| 角色职责对齐 | 财务经理只管钱与合同验收,不问其不懂的业务细节;定不下来的事列为 SOW 未决项(负责人待定) |
| 避免无效转介 | 规则问不到时在两人间反复切换只会消耗次数;被转介两次后整理记录,找项目负责人协调或问助教 |
| 用具体实例核对口径 | 只问"指标怎么算"易得抽象定义;拿已在用的报表数字核对实际口径,并自行验算 |
| 生产环境问题列依赖项 | 对方不掌握细节时,一次性讲清核查对象、用途、范围及手头材料,再请求配合 |

## 二、作业讲评

### W1 补交作业问题

- 客户随口回答不能当成明确要求。
- fit gap 要写客户诉求,不是产品功能。
- 样例跑通不等于客户需求。

### W2 作业

常见问题:

- 技术组对模型疑点全写"采用",等于没核查。
- 干系人地图把拍板与否决权限写反。
- 把自身提问记成对方的话。
- 模型里夹带过程记录,污染提示词。
- 重跑后判读案图未更新。

亮点参考:

- 提取方法:标准答案与打分脚本评估先行。
- 查清用途后换回明确配合。
- 分清主体授权层级。
- 一组组带回原文给判断。
- 回到原编号改上周结论。

### W3 作业

常见问题:

- 数值通过不能代替解释口径通过。
- 错误注入只看"拒绝了",不看拒绝理由是否匹配预期。
- 规模回归只测一种问法/月份,要多换。
- SOW 写成过程记录,影响审批。
- 把缺方法当成缺失值去问客户。

亮点参考:

- 缺失依据让构建停住,补充后再重建。
- 期望先冻结算好,再查询验证。
- 构建失败一轮只改一处,按错误码定位。
- 用具体例子问端点,拆穿假冲突。

## 三、参考答案解析

### 业务模型写法

写明新增来源、精确到会议/消息、解答程度及未知部分。本期统计规则不能推广为固有定义;统计口径的选择不等于复购率公式已核定。

### 指标构建 Skill 规范

- 目标:要么输出完整定义,要么列成未决项,不留中间态。
- 月度指标未给月份,先澄清再动手。
- 引文逐字一致,保留 Markdown 符号。
- 不写客户事实,以积累跨项目复用能力。

### 判定程序核心逻辑

先比状态、意图、版本列 → 再分组件行对齐 → 最后比数值换算单位。验收看数据 Diff 结果,不看 SQL 写法是否相似。

### 参考答案使用建议

非唯一标准,不要求照抄。保留自己的交付与失败记录对照迭代;采用部分注明出处。

## 四、工具方法与报错排查

- **材料阅读策略**:跟着任务书作业路线走,每次只看当前步骤;文档太多可交 AI 读任务书提示下一步,但客户材料和访谈记录必须自己读。
- **FDE 定位**:不做"工具手"。遇到问题先基于资料自主排查,定位不了再带证据找产研;实操交给 AI 辅助,判断留给自己。
- **排查三步顺序**:① 查任务书报错对照表 → ② 交 Coding Agent 排查 → ③ 带排查记录问助教。
- **向 AI 提问的上下文**:在工程目录下启动 coding agent,提供任务书位置、当周说明、出错命令完整输出、运行记录、检查文件及改动说明。
- **AI 排查边界**:叮嘱 AI 先定位再动手;不动课程方工具和原始数据;密钥走环境变量,不直接粘贴。
