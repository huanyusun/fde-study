# V05 本体怎样进入交付

> 视频 32:17(article 1028698,课件 39 页;字幕稿 `transcripts/v05-*.md`)。Palantir 官方方案设计示例(航线告警)。**业务模型→数据→程序→接口→验证的完整链路课。**

## 三段总框架(课件开篇)

①理解业务:业务模型帮 Agent 理解客户业务;要完成查询或操作还需要相应的数据和程序实现。②构建实现:FDE 依据业务模型组织数据、开发程序,把**对象、关系、动作**对应到实际数据与操作接口。③运行与变更:系统运行时 Agent 通过这些接口完成业务任务;业务认识变化,相应实现也要调整。

## 课程推演案例(Palantir 航线告警)

- 工作流:查看自己负责航线的告警 → 结合航班信息判断 → 决定处理。系统支撑:记录航线/告警/经办人并跟踪进度、整理辅助判断数据、提供操作界面。
- 本题任务:员工查看分配给自己的待处理告警工单,并把其中一条转给同事。**转派三条规则**:①工单必须处于待处理状态 ②接收人必须是有效员工 ③留下原经办人、新经办人和执行人的记录。
- 推演数据:A-17(航线 R-01,经办林工,待处理)、A-18(R-02,周工,已完成);追踪"林工把 A-17 转给周工后,哪条记录改变,双方待办怎样变化"。

## 六步落地

1. **找出任务相关的业务定义**:对象(航线/告警工单/人员)与关系(每条工单关联航线;每条工单关联当前经办人;航线负责人);业务模型还要写清:"我的待办"按什么条件判断/什么情况允许转派/转派后哪些信息改变要留什么记录。**负责航线与经办工单是两种关系**——一条航线多条工单、不同工单不同经办人;查"我的待办"看工单当前经办人,**不能直接用航线负责人替代**(先确认业务含义,再决定字段和关联)。
2. **把对象和关系对应到数据**:告警工单 A-17→工单表 A-17 记录;人员林工→人员表 U-01;A-17 经办人是林工→经办人字段 U-01;A-17 关联 R-01→航线字段 R-01。**用工单/人员/航线 ID 识别记录,再通过字段取值建立关联**。**属性要对应取值,字段还要核实含义**(状态码 0=待处理;状态记的是发出的指令还是实际处理结果?金额是分还是元?——名称对得上不代表业务含义一致)。
3. **查询规则→查询逻辑**:"我的待办"=当前经办人是本人 **并且** 状态为待处理;林工查询 A-17 应出现,周工查询 A-18 已完成不应出现;只按经办人查会混入已完成历史工单,只按状态查会混入别人的待办。**权限机制仍需检查用户能看哪些数据,经办关系不能替代查询权限**。查询逻辑可在两个阶段形成:开发时预先实现(业务规则+数据映射→SQL/函数→查询接口,Agent 调用接口执行已有逻辑)或运行时动态生成(用户请求→Agent 读规则与数据映射→生成 SQL→查询工具执行);**两种方式都需要正确的业务口径与数据映射**(本例采用前者)。
4. **补上符合规则的转派接口**(前提:已有工单和人员数据,没有符合规则的转派接口):调用方 Agent 提供工单 ID+接收人人员 ID;服务端**根据认证信息确定发起人**(发起人身份来自认证信息)、检查转派权限、记录是谁执行了这次操作。**执行端先读取当前记录,再逐项检查**(工单是否仍待处理/接收人是否有效员工/发起人是否有权转派;任何一项未过→不修改工单,返回拒绝原因)。通过后:经办人更新为接收人、**保留待处理状态**、保存原/新经办人和执行人记录、返回成功。**转派只意味着换了经办人,工单仍需处理**——误改成"已完成"它会从待办列表消失。**理解意图与执行规则各自落实**:确定性的事情交给规则,模糊的事情交给模型;Agent 理解"转给周工"组织请求,执行端依据当前记录检查规则再执行;即使 Agent 请求转派已完成工单,执行端也应拒绝;业务模型中的限制要落实为明确的程序检查;客户已有接口时先核实规则再决定接入或修改。
5. **把接口接入界面或 Agent**:林工"把 A-17 转给周工"→人员查询(周工→人员 ID)→转派调用(传 A-17+接收人 ID)→服务端执行转派逻辑;界面上的转派操作也调用相应接口;每个接口都要说明用途、输入参数和返回结果;人员查询与"查询我的待办"是不同的查询。**用户反馈必须跟随执行结果**:返回成功或拒绝,界面/Agent 据此反馈;成功后重新查询待办展示变化;用户核对三问(哪些工单等我处理/刚才那条是否转出/还有哪些待办留下)——界面围绕这些工作问题组织。
6. **验证**:分别用林工和周工的测试账号查"我的待办"(林工:转派前有 A-17→成功后没有;周工:前空→后有 A-17);仍应保持工单编号 A-17、关联航线 R-01、待处理状态;操作记录应说明原经办人、新经办人和执行人。**不该成功的操作也要检查**:尝试转派已完成的 A-18→应拒绝;把 A-17 转给不存在的人员→应拒绝。**如果 A-18 竟然转派成功,不能立即认定业务模型有错**——先查转派接口是否执行了状态限制,区分规则定义有误与执行检查缺失。**让未参与建模的人尝试使用模型**(从真实业务工作中选取问题,让没有参与建模的人寻找对象、理解关系并得出答案)——帮助发现哪些业务含义只存在于建模者经验中、还没有在业务模型里表达清楚;建模的人熟悉每条关系,可能看不到新用户会遇到的困难(Palantir Ontology Design Validation)。

## 规则变更的影响评估(课件后段+字幕稿)

- 门店区域统计从"当前区域"改为"成交时区域"——**只改涉及时间维度的关联逻辑,金额计算等不变部分保留**;更新后确认系统加载新版本。
- 设计针对性测试样本:**受变更影响的数据验证新逻辑 + 未受影响数据回归旧逻辑**,防止误改。
- 业务模型的价值:记录关键定义的**适用范围、版本、依据**——变更时精准定位修改点、追溯决策来源,确保系统实现始终与业务语义一致。

## 与青禾沙盘的连接点

- 付费资格规则=确定性规则,必须落为程序检查(派生 SQL 的资格判定),Agent 只做意图理解;即使 Agent 请求了不该查的口径,执行层也要能拒绝。
- 端点规则实测的定位:如果 A-18 竟然成功,先查实现再查模型——**区分规则定义有误与执行检查缺失**的排查顺序,对应我们测试失败时先查业务输入还是 Skill 实现。
- 反向用例必须被拒(转已完成单/不存在的人)→ 测试集中 clarify/unsupported/error 期望 + 9 类错误注入的理论基础。
- 未参与建模的人试用模型 → 我们的小样本独立期望(不调指标库的审核程序)就是"非建模者视角"的验证。
