# V07 独立校验与错误定位

> 视频 30:24(article 1028700,课件 43 页;字幕稿 `transcripts/v07-*.md`)。**第 9–11 步(测试集/判定程序/定位回归)的方法课**,配合《测试与判定编写指南》使用。W07 才讲黄金集/异常集/安全对抗集/版本回归/客户出题——本讲聚焦指标查数校验:期望怎样独立得出、结果怎样确定性比较。

## 一、独立构建测试集

1. **用例 = 问题 + 期望,并写明来源**:期望依据已核实的业务要求、**运行前**定好;不能靠被测系统自己证明自己;每条期望写明来源便于复核。
2. **期望三种来源**:①客户核对过的样本结果(V02 查数项目由财务负责人预先核对——王经理场景)②小数据按业务规则逐单手算 ③大数据用独立审核程序逐条计算——不导入被测指标库、不调用被测 SQL。
3. **另写一段 SQL 不自动等于独立**:审核程序与被测系统若都误解口径(都忘了减退回),得到同一个错数,测试照样通过。审核程序照业务依据编写→先用小数据手算校准→再用于大数据。
4. **按要抓住的错误选例**:每个指标至少一条用例测到;新增用例按"要抓住哪类错误"设计——金额(计入/扣减)、比率(分子/分母/零分母)、门槛(恰好等于)、关联放大、月份边界(清单见测试指南)。
5. **数据要能区分对错算法**(梧桐成交 vs 归属门店,stores 表声明两次):8 月两种分组结果相同(80/50)发现不了接错;**7 月按原始数据手算成交 60/40、归属 100/0,总额同为 100、分组不同才能区分两种算法**——要测关联是否接对,数据里必须有两种关系不同的情况。
6. **问题有歧义先确认期望**:客户确认默认含义→期望按确认分组;两种都常用或客户也不知道→期望 Agent 先问清楚(期望 clarify);一直没确认→在用例中消除歧义直接问"按成交门店"。
7. **扩展用例两法**:换说法(同问题不同问法各一条用例,期望相同;日期或条件变了就是另一个问题,要重写期望);规模数据(检查结果+耗时;**必须基于这份规模数据重新独立计算期望,不能照抄小样本**;没有规模数据可按分布构造,四种状态也是构造的一部分)。

## 二、判定程序(确定性比较)

1. **四种状态先写状态,正常返回才比数值**:正常返回(覆盖内没有写 0;零分母未定义写 null)/需要澄清(先写对应状态)/不支持(超出覆盖是不知道,不能写 0)/执行出错(不写成期望;出现即用例没跑通)。
2. **分工**:测试集(学员写)→测试命令(课程提供)→运营 Agent→实际结果→测试命令把每条期望和实际交判定程序(学员写)→输出是否通过、差在哪一项。
3. **实际结果是一整份记录**:status/intent/SQL/columns/rows/units/data_version——判定程序据此判整个输出,不只是数值。
4. **判定必须给出稳定结论**:同样的期望+同样的实际,每次比较结论都一样;**不让另一个大模型判定**——可能与被测 Agent 误解同一口径把错误藏住;结果有不确定性,同一用例时过时不过,无法拿来验收;确定性任务用大模型还浪费 token。
5. **按六类检查项比较**:状态→版本→意图→单位→表格结构→数值;**状态先拦住**(该澄清却给数、该不支持却给 0);期望非正常返回时**只比状态和版本,比完结束**。
6. compare 实现要点(样例代码):先比 status;**显式锁版本**(data_version/data_sha256/catalog_sha256,期望写了才比,不同合法库不能默认同一版,版本不一致比数没有意义);意图四项(指标/时间/分组/筛选)——**不比 SQL 文本**(同一意图不同写法,SQL 的错在数值比较中暴露);单位按指标登记逐项比(cents/ratio;分写成元、原始比率写成百分数都算错,不能放宽容差);列检查(无重复、集合相同);**按分组键对齐行**(一店对一店;行顺序不同照样通过;少组/多组/重复组都拒绝;不分组时只有一行);数值:整数精确(13000.0=13000 过,13001 拒)、浮点预声明容差、null≠0。
7. **判定程序自己也要校验**:注入已知错误,验证能否拒绝、报出的差异是否与改动一致(判定程序的回归);数字不变其他地方出错也要注入(只改结束日期,只比数字会漏);两类对照:原本正确的结果仍通过、只有行顺序变化的也通过——**拒绝错误、不误伤正确、不纠缠无关差异**;改判定后重跑注入;框架启动时的自比较只验证程序能跑,不是严格判定(样例十项注入清单可参考)。

## 三、定位与修复(逐层,不盲改)

- 出错先固定比较条件(问题/测试集/Skill/数据与库版本/加载项目/报告目录/trace_id),未明确问题前不盲改——像调试程序,对象换成 Agent。
- 顺序:意图对不对(看中文目录别名与维度)→ 实际加载的指标库(measure 表达式/派生 SQL/目录口径)→ 回溯业务模型与材料定义 → 构建库的 Skill 是否有误 → 用例期望和判定程序本身有没有错。
- 修复落点分情况:意图选错→补访谈/业务模型/材料;表达式或派生模型错→改 Skill 或补业务输入重新生成;**不要直接修改生成的指标库**(动态生成的,直接改会在下次构建时出问题);加载错库→重新加载;期望错→**必须基于业务依据修改并写明原因**,不盲改为通过测试;判定程序错→修正并重新注入校验。
- 梧桐案例演示:扣退后收入被改成只取实付不减退回→六条用例中三条数值失败(退回占比/收款单数/月内大额不受影响,因为不用这个 measure——**一个错误的影响范围取决于它在库中的引用情况**);定位顺序=意图层→SQL 与原始结果→measure→回材料确认口径→修 Skill 重新生成。
- 多个不相关错误可一起修+全面回归;修改缺信心或错误在同一段代码→一次只修一处。修复完成的标志=所有原通过用例重新全过。

## 四、把测试证据写进 SOW

- 甲方通常要求测试用例及结果作为交付物(查数项目 M2 验收依据含约定的查询结果;期望值来源=财务负责人提供样本期望)。
- V02 门店分组计算错误=承诺范围内的修复(影响约定查询结果),定位+回归修正。
- SOW 测试结果三栏:**已验证支持的查询 / 能力限制 / 部分指标的支持范围**(如筛选只支持等于和属于、月度指标仅整月);未验证的问题或数据规模列为待验证项,不写成承诺;**机器判定通过 ≠ 客户验收**,系统能力与业务效果分层判断。
