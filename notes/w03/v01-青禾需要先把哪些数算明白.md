# V01 青禾需要先把哪些数算明白

> 视频 14:29(article 1028678,课件 11 页;字幕稿 `transcripts/v01-*.md`)。全周地图课。

## 核心方法与机制

1. **本周主线**:W02 初步建模(了解参与者→梳理会员/账户/订单对象关系→初步业务模型)→ 本周核实新规则 → 建指标库 → 与王经理谈交付约定。每位同学判断与未决问题不同没关系,随项目推进逐步收敛。
2. **三角色具体诉求**:小林(先查清数字、口径统一、说明依据;之后才讨论关注哪些会员/运营安排;也期待可触达名单——但那是下一步);沈总(回应复购下滑、尽快看到阶段进展);陈姐(不要重复算人;统计结果会不会直接被拿去改门店考核)。
3. **查数/圈人/动作都服务于小林的运营工作流**:了解购买情况→确定重点人群→准备运营安排→协调线上与门店执行→跟进反馈(例:回访一段时间未购买的会员,先了解情况再定人群和安排)。
4. **客户已提供 vs 还需核实**:已提供测试数据、数据字典、现有报表与口径说明,大部分指标有计算依据;**付费会员的部分业务规则仍不清楚,直接影响计算结果**——继续核实并更新业务模型;结果适用范围、需要客户配合什么也要核实。
5. **标准产品升级**:同一运营 Agent 逐周升级(W01 独立样例分析+调用标签系统;W02 接入业务知识检查理解;W03 新增通用查数能力——原会话入口自然语言提问,已支持范围内实际查询返回数字/结果表并说明业务口径;引入 MetricFlow,实现留技术课)。
6. **FDE 的本质**:客户业务现状随项目推进不断澄清;后方标准产品按自己节奏持续迭代——**FDE 填补两个动态范围之间的鸿沟**。
7. **梧桐样例截图展示的输出形态**:结果(130.00 元)+ 统计口径说明(按原订单日期、取消单不计、分换算元、未按维度分组、合成样例数据)+ 依据编号 + 工具依据与运行记录——"既看到结果,也知道按什么规则计算"。
8. **三步适配**:①进一步了解业务(付费会员究竟包括哪些人,规则待核实)②把规则落实到产品(构建青禾自己的指标库,按青禾口径查数)③核对实际查询结果(检查是否符合约定)。
9. **期望差异与交付讨论**:"把运营 Agent 做好"——我们可能以为交付查数圈人系统即完成;客户可能期待协助用到实际运营、产出可直接触达名单、跟进到效果提升。若客户要我们继续参与实际运营,讨论三问:参与到哪一步/哪些工作谁承担/是否承诺运营效果+怎样衡量验收。不同理解范围不同,影响投入与交付安排。
10. **先明确范围与责任,再约定交付和变更**:交付与配合(先交付什么后交付什么、双方何时备好条件)、验收与后续(怎样验收、验收后怎样持续经营迭代)、付款安排(何时、何种方式)、变更提前约定(新发现/新要求由双方确认是否调整范围与投入,变更方式一开始商量好)。
11. **项目难点判断**:具体技术实现可能不是最大难点;更难的是一开始就在不影响推进、不伤客情的前提下把工作范围定好——哪些支持、哪些不支持、按什么节奏交付。

## 与青禾沙盘的连接点

- 本周作业 = 三步适配的完整执行:核实口径(第 3–5 步)→ 建指标库(第 6–8 步)→ 核对查询结果(第 9–11 步)+ SOW(第 12 步)。
- 期望差异三问就是 SOW 讨论的框架;陈姐两问(重复算人/改考核)直接来自她访谈的关切。

## 可用于作业的证据 / 判断

- "查数 + 说明口径依据 + 依据编号 + 运行记录"是产品能力验收的展示形态——我们聊天入口的验证照此核对(result.json 的 intent/sql/rows/answer)。
- 口径未确认的指标(付费会员)必须访谈核实后再实现;范围/责任/验收/付款/变更在过程中补齐是常态。
