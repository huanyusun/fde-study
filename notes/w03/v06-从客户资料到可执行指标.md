# V06 从客户资料到可执行指标

> 视频 56:53(article 1028699,课件 73 页,本地 `lectures/w03/W03-V06_*.pdf`;字幕稿 `transcripts/v06-*.md`)。**第 6–8 步的技术说明书,本讲 = 构建指标库 + 看懂 MetricFlow + 判断结果可信。**

## 一、补全定义:一个指标要算对,必须写全哪些约定

**梧桐"扣退后收入"定义**:按原订单日期统计、取消单不计、到账总额减退回金额。落到可计算要补齐(三类资料各管一段):

| 资料类别 | 提供什么 | 梧桐实例 |
|---|---|---|
| **业务模型** | 计算对象、对象关系、统计粒度 | 一行一单,每单归一个会员账户+一个成交门店 |
| **收款说明(报表口径)** | 有效范围、计算口径、特殊规则 | 按原订单日期统计、取消不计;扣退后=到账-退回;退回占比分母零未定义 |
| **数据字典** | 字段含义、单位、快照规则 | paid_cents 实付分/refund_cents 截至快照累计退回分;**不存在 paid_amount_cents**;gross_cents 是原价不是到账 |

**五个核对点**:①一行代表什么 ②哪些订单、按什么日期 ③金额列 ④汇总方式 ⑤零/未定义/未知三分(覆盖内无订单=0;到账总额 0→占比未定义;超出覆盖=未知,不能当 0)。

**参数 vs 定义**:"查 8 月"是本次查询参数;"按原订单日期归属"是指标定义本身。refund_cents 是**截至数据快照的累计退回**——按原订单日归属回答"8 月订单最终退回多少",**不能**回答"8 月里发生了多少退款"。

## 二、让模型每次现写 SQL 的三个局限(补充例题 A1~A5,与梧桐样例独立)

1. **关联放大**:A1 两条明细 → join 后 8000 算两次(4 行合计 26000)。`COUNT(DISTINCT order_id)` 修好单数(3)但金额仍 26000;`SUM(DISTINCT 金额)` 把 A2/A3 各自的 5000 误并 → 13000。**单数正确不代表金额正确**。
2. **日期边界**:8 月 = `≥8/1 且 <9/1`;写成 `<8/31` 漏掉 31 日的 A3,`BETWEEN 到 9/1` 多算 9/1 的 A4。
3. **历史区间维度**(门店 8/15 北区→南区):按成交日取生效记录,条件=门店相同+开始日≤成交日+(结束日为空或成交日<结束日)——开始日含、结束日不含;A2(8/15)属南区:北 13000/南 5000。**用左关联数每单匹配条数暴露缺失(0 条)与重叠(>1 条);内关联先丢行把问题藏起来**。

三局限:容易出错、不易发现(SQL 能跑、结果像对)、口径不稳定(换问法生成不同 SQL)。模型更强只减少错误,不解决"每次计算一致"。

## 三、四类实现(松→紧)+ 业内现状

1. 只给表结构直写 SQL(演示/原型);2. 大量上下文直写(OpenAI 数据 Agent:3500 用户/7 万数据集;多对多/条件下推/空值仍可能悄悄错;常用复用工作流保一致);3. 先建语义模型辅助写(Cortex Analyst/Genie/Power BI Copilot,DAX);4. **只选指标/维度/筛选,引擎生成 SQL(Looker/LookML、dbt+MetricFlow)——本课程采用**。混合常见(Cortex 优先语义、限时失败回落原始表——真实项目若做回落须标"口径未核定+人工核对")。上下文路线的五种定义传递法(字段描述/验证 SQL few-shot/数据库对象/代码来源/事后回归)本质都在"逐步补出定义层"。

## 四、MetricFlow 与构建/查询两阶段

- **MetricFlow = 语义层 = 指标计算引擎**:输入 YAML 定义 + 结构化请求(指标/分组/时间/筛选)→ 固定 SQL。Transform 开发 → 2023 dbt 收购 → 2025-10 Apache 2.0 开源。
- **构建阶段**:FDE 写 Skill → 大模型按业务模型/报表/字典生成定义 → 程序检查+人工核查 → 加载。**查询阶段**:自然语言 → 大模型提意图 → 程序校验 → MetricFlow 生成 SQL → 数据库执行 → 大模型组织回答。
- **MetricFlow 不调大模型、不懂自然语言;同定义同请求 SQL 固定**。定义核查一次,反复使用:口径只写一次;易错计算交给确定性程序、有限指标可逐项核查测试;能力边界可写进 SOW;口径变化改一处重新构建。
- 适合:口径必须一致、结果要验收(写 SOW)。探索式分析更适合上下文路线。局限:库外指标答不了;定义要先整理构建核查测试;指标增多/口径常变维护成本上升。
- **YAML 写法**:本课程用旧写法 semantic_models+measures(已标弃用仍可用,dbt Copilot 尚不支持新写法);2026-07-12 新写法(取消 measure)不要混用。
- **查询协议有意收窄**:支持 等于/属于/并且;不支持 或/任意表达式——课程程序边界而非 MF 限制;逐项校验字段与取值,取值错误判 unsupported,**不悄悄返回 0**。
- 课程无回落到模型写 SQL;无论哪类方案,FDE 都要**整理口径→核查→测试**。

## 五、指标库四件套(沿扣退后收入读懂)

1. **语义模型**(metrics.yml):model=ref('orders');defaults.agg_time_dimension=ordered_at;entities:order primary(order_id)/member foreign/store foreign;dimensions:ordered_at(time,day)/channel/status(categorical)。**语义模型 ≠ 业务模型**——由模型按 Skill 生成。
2. **measure**(行级计算+聚合):`CASE WHEN status='paid' THEN paid_cents - refund_cents ELSE 0 END, agg: sum`——表达式落实"取消单不计""扣退后=到账-退回"。
3. **metric**(对外稳定 ID):simple 型 `measure: net_receipts_cents_measure`;**ratio 型 numerator/denominator 引用 metric ID**(returned_cents / gross_receipts_cents)——改底层指标定义,依赖它的比率跟着变。
4. **中文目录**(catalog.json):id/中文名/aliases/**unit**/sources(**file+原文 quote**)/constraints/query_policy(full_month_only)——单位和别名属目录,不进计算;改别名不改公式。

**聚合方式取决于统计对象**:金额=逐单求和;收款单数=paid 记 1 否则 0 再求和;**会员数=对会员号去重计数**;人均=金额÷去重人数(分母口径客户定);金额重复不能靠去重修复。**样本必须能区分两种算法**——梧桐 8 月订单数=会员数=2 区分不了"订单数 vs 去重会员数"(假想 W1 再加一单:订单 3 会员仍 2);测试样本要有区分力。

## 六、意图→SQL 的实际链路(运行记录逐层看)

- 意图:`{metrics:[...], start, end, group_by, filters}`(2026-08-01~09-01,半开)。
- SQL 里 measure 成为列(`... AS __net_receipts_cents`);**半开区间由程序转 BETWEEN**(end 减一天;协议与框架参数必须明确转换)。
- **比率先总和再相除**(不是逐单比率求平均);`NULLIF(SUM(分母),0)` 零分母返 NULL;结果 [13000, 0.1333],units {cents, ratio}。
- 按成交门店名称分组:意图 group_by=store__store_name;**外键→主键关联不放大**;LEFT OUTER JOIN 保留找不到门店的订单;MetricFlow 禁止扇出关联;**声明主键的前提是数据真的唯一**——粒度错了声明再对也会重复,构建时还要检查。
- **查询策略必须由程序执行**:缺时间→clarify;超覆盖或 start≥end→unsupported;指标未定义→unsupported;full_month_only=true 时非整月/带筛选/非按月展示→unsupported;跨月必须按月展示(delta≠1 且 group 非 metric_time__month→unsupported)。
- **覆盖内为 0,覆盖外不能当 0**:覆盖内空聚合仅 simple 类型补 0(代码注释:A covered empty aggregate has a known zero for additive/count only;ratios remain undefined);覆盖来自资料与元数据,不能从样本最早最晚日期推断。
- 四种状态:ok/clarify/unsupported/error;**三个修改入口:换中文叫法→改目录;换查询月份→只改参数;改公式→回业务定义、用 Skill 重新生成(不手改生成物,防后续构建覆盖)**。

## 七、Skill:六段与第六段三原则

- 六个指标可手写;真实客户几十上百项、资料随访谈更新,逐项手改 YAML 无法保证一致性——**把重复流程抽象成 Skill**:从哪份资料取依据、怎么选字段与聚合、依赖怎么写、依据不足怎么办;资料更新后用同一方法重新生成,保留定义引文与方法版本记录。梧桐 Skill 供参考思路,客户规则不能照搬。
- **六段**:①目标与输入 ②找齐依据引用原文 ③定义转计算表达式 ④依赖与输出格式 ⑤依据不足/冲突/未决 ⑥从业务模型推导语义模型与派生模型。第三、四段对应"读定义",第二、五段对应"结果核对"。
- **业务模型是 Skill 起点**:对象/关系/统计规则决定指标库(语义模型+必要派生模型+指标+中文目录);第六段写不清 → 机械地一表一语义模型、漏掉必要数据整理。
- **第六段三原则**:①写推导方法,不写某客户的模型与 SQL 答案(换客户同一方法可用)②按业务对象与关系表达语义模型 ③先判断粒度,必要时先派生。
- 落地:对象→语义模型、关系→主键外键、属性→维度与统计时间;逐个核对 dimension_targets(实体查询 ID=实体名、属性查询 ID=主实体名__维度名);**同一对象被不同关系使用必须分别声明**(梧桐:orders.store→stores.store;members.home_store→stores_home.home_store,同一物理 stores 表、主实体名不同);**先声明粒度(每模型一行代表什么)再决定是否派生**(粒度不一致→SQL 整理:排序/按期汇总/判资格;整理时先汇总再关联)。
