# V02 标准产品定制开发与交付责任

> 视频 22:14(article 1036153,课件 13 页;字幕稿 `transcripts/v02-*.md`)。toB 常识课,不讲代码:配置/实施/定制开发/二次开发怎么分、各方干什么、上线后谁维护——对应作业第 6 步报告里分工与维护责任两处说明。

## 核心方法与机制

1. **四个概念先分清**:配置=在产品已有选项、参数和规则范围内调整行为(例:按已确认业务条件设置"按消费金额+最近购买时间筛选会员"的参数);实施=准备客户资料、部署、配置、对接系统、验证结果、培训等全过程,配置只是其中一部分;定制开发=为特定客户新增/修改功能(例:为青禾编写账户关联逻辑,让新旧账户数据共同参与决策);二次开发=基于已有产品或平台继续开发,可通过 SDK、Open API 等扩展机制接入——**不一定改产品源码,也不一定客户自己完成**,可由实施团队做。
2. **两个名字不矛盾**:同一个开发任务既是定制开发(满足青禾特定需求)也是二次开发(基于已有产品),强调角度不同。注意:某些定制开发可能已包含在 SOW 范围内,不应因"名为定制"而额外收费,一切以 SOW 约定为准。
3. **能配置就不写代码**:配置加现有工具能满足需求,就不要为展示技术水平写额外代码。FDE 的核心工作包括在平台上配置和编写工作流;写代码只是手段,最重要的是解决问题、完成交付、在实际使用中验证业务效果。
4. **SaaS 与私有化是另一个维度**:描述提供、部署、运营方式,与是否定制无关——SaaS 也可能要客户适配甚至基于 API 二次开发,私有化部署的也可以是标品。定制功能的开发和维护都需专门商定,不能想当然"私有化=定制、SaaS=纯标品"。
5. **四方分工**:客户业务人员解释业务规则并确认效果(小林规定哪些会员不能联系,FDE 确保 agent 建议遵循限制、并共同检查结果);客户 IT 协助数据导出与接口对接(老周协调旧 POS 导出、确认可用、告知字段使用条件;必要信息无法导出可能要改原系统、找旧 POS 供应商);产品团队开发维护通用功能、提供 Open API/SDK 等扩展机制,并在提供接口时明确使用条件与限制——大版本升级兼容性是最易出问题的地方;FDE 把业务要求落实为软件功能、协调各方、把现场问题反馈产品团队。
6. **FDE 反馈缺口的现场例**:客户要求资料无法确认两账户是否同一会员时保留"待核实"状态,而标品只支持记录是/否——FDE 要把该缺口及其业务影响反馈给产品团队,双方讨论是走现有接口二次开发,还是改产品通用功能;反馈≠产品团队承诺改进或给了时间。OpenAI 和 Anthropic 的公开 FDE 岗位说明都写了两项职责:客户工程交付+向产品团队反馈现场认知——连接是双向的;许多公司允许 FDE 经评审、测试流程把改动合并进产品代码库。
7. **FDE 负责整体技术方案**:在 SOW 范围内明确标品功能覆盖哪些需求、哪些靠配置/开发补,客户现有系统提供哪些数据或接口、如何通过二次开发交换数据共同完成业务流程(例:旧 CRM/旧 POS/新 CRM 的数据 ETL、ID mapping 是否走二次开发);协调各方进度与依赖;交付时说明已满足的要求和存在的限制,正式验收依 SOW。
8. **交付后的维护责任必须明确**:产品团队负责标品迭代和 bug 修复;客户环境中的二次开发代码、配置、业务规则由另一方承担——不能默认标品售后会覆盖所有工作,也不能假设 FDE 写的代码必须 FDE 永远维护;可由客户团队或其他服务团队接手,但范围和交接安排要确认。神策例:客户找标品售后,售后没能力也没职责维护没向他们交付培训过的非标品代码→争议;应由售后作第一责任人、路由到定制开发团队支持。整体交付由 FDE 推进,但长期维护不应始终绑在最初 FDE 身上。
9. **模型升级是最现实的适配问题**:agent 产品换大模型版本后,二次开发代码和配置要不要调、谁负责适配验证。例:青禾升级模型后会员查询成功,却忽略记录里"请不要再联系"的提示、建议继续联系→这是 bug;原因可能出在产品模型适配有问题、原提示词不确定、或工具/知识配置错,按既有定位步骤排查。
10. **版本发布与升级的约定**:新版本要说明改了什么、行为变化、支持的接口工具、兼容性承诺,并**提前数个版本**预告哪些接口工具将不再支持(开源工具惯例),留出适配时间;维护方即使不调代码也要随升级做回归验证。产品团队标准测试通过≠升级完成,要指定负责人组织**整体业务验证**,通过了才算升级成功;大型升级在测试/沙盒环境验证后再上生产;大版本升级要向客户提交方案,写明回滚方法和失败后的止损措施。
11. **兼容责任以证据划界**:产品团队未履行承诺的兼容范围→责任在他们;交付侧依赖了不受支持的内部行为或工具(运维工具、内部 API)→兼容问题自行解决,所以要用正式支持的 API 和 SDK。神策实施团队用了仅提供给运维的工具,升级后不可用引发争执——这类纠纷必须靠证据判断,不能简单归咎产品升级。
12. **预算里要预留升级适配**:确定交付方案、评估项目投入时,提前考虑产品和模型升级后的适配与验证工作,并做好预算。

## 与青禾沙盘的连接点

- 本周写的三个客户函数和 YAML 就是在标准产品扩展点上的客户开发:既是定制开发(落实青禾身份/限制规则)也是二次开发(基于产品预留接口)——报告 `reuse_and_scope_explanation` 回答"为什么会员能力要做成独立于聊天入口的共享模块、本轮怎样接续已有客户版本",用的就是这里的分工与维护代价。
- 分工对号入座:小林明确联系限制→`contact_constraints` 要遵守并共同检查结果;老周协调旧 POS 导出与字段使用条件→`identity_evidence` 的数据来源;产品团队只提供扩展机制,客户代码不进产品主干(与 V03 隔离做法衔接)。
- 模型升级反例("请勿再联系"被忽略)= 任务书注意事项"未知不等于允许联系、明确禁止不被空白或较新记录自动解除"的原型;升级后要组织整体业务验证,不是标品测试通过就完事。
- 交付说明要"已满足+存在限制"两面写:报告 `delivered_capabilities` 没做到的不写,`unresolved_impacts` 写清未决对象与影响——正是 V02 对交付说明的要求。

## 可用于作业的证据 / 判断

- 概念四分法用来给本轮工作定性:能用配置和现有工具(指标库、知识机制)的不写代码,三个客户函数只做产品做不了的业务判断——报告和自检说明里都可用。
- 范围判断按 SOW/需求说明,不按场景名:哪些定制已含在本轮范围,对照需求说明第五节支持/不支持条件表;范围内换条件属正常使用,范围外说明缺口按变更另行确认,不能单方面扩或砍承诺。
- 维护责任写进交付:客户代码、配置、规则的维护归属要明确(业务模型第七节/报告),不能默认标品售后兜底,也不能默认 FDE 永久维护。
- 升级适配提前预算:`time_log` 把验证与返工耗时如实记;评估投入时为"产品和模型升级后的适配验证"留预算是 V02 的明文要求。
- 只依赖正式支持的接口:用了不受支持的内部工具,升级出问题责任自担——作业只用产品预留扩展点,不绕过框架内部逻辑。
