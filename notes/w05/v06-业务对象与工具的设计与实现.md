# V06 业务对象与工具的设计与实现

> 视频 37:44(article 1036162,课件 23 页;字幕稿 `transcripts/v06-*.md`)。本周技术主线第二段,对应作业第 2、3、4 步:填 YAML、写三个客户函数、让直接入口与 Agent 用上同一份实现。

## 核心方法与机制

1. **实施围绕三件事**:①产品现有业务模型如何承接客户需求;②客户数据如何接入(来源映射);③业务规则如何执行(配置还是扩展函数)。FDE 在已有标品基础上工作,先理解产品能力,再落实客户的定义与规则。
2. **产品预设模型的三种形态**:①核心业务抽象——神策分析的 event/user/item 是跨行业用户行为模型,交付时把抽象映射到客户业务(电商客户:支付成功=事件、消费者=用户、商品 SKU=item),事件口径、发生时间、属性按客户明确;②可扩展平台——Palantir Foundry(字幕稿作"方锐")支持自定义设备、维修工单等对象与关系,Palantir FDE 先基于本体论建模,再转成程序可用的对象定义,行业解决方案可复用、不必每个客户从零开始;③多数产品兼具两种特点,核心区别是预设程度与定制开放程度——既要复用产品定义,也要补充客户所需定义。
3. **承接关系先查产品支持**:客户确认一个会员可关联多个注册门店(多值关系),实施时先检查产品是否支持——支持就复用,可配置就配置,配置也不行才按通用性/阻塞性判断走产品迭代还是二次开发。
4. **对象定义写成结构化 YAML,业务判断放不进去**:LinkML 用 range 指向 store、multi_value: true 表达"可关联多个门店"。分工:Markdown 业务模型继续保存完整含义、依据和待核问题,YAML 只放程序要读的对象结构(标识、属性类型、关系指向),两份材料约定一致。本周沙盘确认会员、来源账户、门店三类对象;订单、会员卡、联系限制暂不进对象定义,放在查询服务与函数里。但 YAML 只能规定属性为文本、允许缺失,"多个来源冲突时选哪一个"这类规则很难用 YAML 表示——写进 description 不会生效,要找其他执行位置(扩展函数)。
5. **代码生成的好处与纪律**:LinkML 同一份定义可由不同生成器转成不同产物;gen-sqla 生成描述对象与数据库表属性对应、对象间关系的 Python 代码(SQLAlchemy 工程)。同一对象的属性关系会同时出现在存储结构和访问接口契约里,手改多处容易漏;用生成器只改源头定义、一次生成全部。纪律:直接改生成代码会在下次生成时被覆盖——沙盘工程包检查生成代码,手改报错;生成代码与业务代码分开维护。
6. **来源映射**:明确对象标识、属性值、关系建立依据来自哪些数据源。来源形式多样(数据库表、视图、文件、接口、消息/事件流),实际项目组合使用;配置指定字段映射与关联依据(关系表哪列是会员编号、哪列是门店编号、分别对应哪张表的标识字段),缺读取/解析/转换支持时补适配代码;CRM 查询接口返回编号和姓名时,接入程序按已确认对应关系赋给对象标识与姓名属性。身份用前面已确定的统一标识,不再重新判断。
7. **两条红线:含义与缺失**:字段名称和格式相同不代表业务含义一致——"最近一次购买的门店"不能误当注册门店;来源缺失必须保留——会员关联三个来源账户,两个有注册门店信息、一个缺,要既保存已知关联也记录哪个来源缺,否则汇总就丢了信息;具体取舍与客户确认。
8. **数据访问两种安排**:①先接入再查询——按来源映射读客户数据、转换后存本地库,定期批量或 CDC 同步,查询访问本地;②按需读取——查询时直接访问数据源(客户库结构适合且允许时经生成器映射直接查),接口可做缓存。按产品支持能力与客户数据更新需求设计。沙盘:来源字段到本地表的映射代码由工具包提供,查询服务启动时用同一份生成映射把会员和来源账户一次性读入内存。
9. **Foundry/OSDK 是参照不是作业**:Foundry 把接入数据组织成数据集(表格型,行+列),FDE 配置哪些列对应对象属性、哪列标识对象、关系怎么映射(一对多单独建关联数据集:会员编号对应会员对象编号列、门店编号对应门店对象编号);OSDK 按应用所需本体生成含类型与调用入口的 SDK,应用经入口查对象与关系,平台执行查询返回——应用不必在每个使用点重读原表、解释字段、拼关联。沙盘不用 Foundry(复杂、需注册),用轻量开源方案,但"定义对象→来源映射→生成/配置→访问"核心步骤不变。
10. **业务规则进扩展点**:标品已有规则直接用;配置能满足就配置;需补充业务判断时写扩展函数——标品准备输入、调用客户函数、处理返回;扩展点不限于函数,也可以是程序包、二进制。风险:客户函数性能不佳或未经充分测试会拖垮整体数据处理。沙盘三个扩展点:生成依据(identity_evidence)、会员属性(member_attributes)、联系限制(contact_constraints);归组与结果读取由课程工具包负责,客户函数只写判断——模拟 FDE 在真实项目里的分工。
11. **规则逐情况落实,执行时机显式选择**:规则要覆盖客户确认的每种情况——例:CRM 姓名不为空用 CRM;CRM 为空且 POS 不为空用 POS;都空保留缺失。客户没明确说的情况不能擅自加规则让程序跑通,坦然承认未核实状态、选一个业务结果,并与客户确认是否保留信息,让后续使用者了解来源。执行时机两种:查询前执行(保存结果,省每次查询的计算,数据或规则变化后要重跑)vs 查询时执行(每次现算);也可结合(数据已在本地,查询时再执行规则)。按标品支持的执行方式、业务对结果更新时间的要求、可接受的查询耗时选。沙盘:准备程序执行客户函数并保存结果,查询服务直接读结果,改规则要重新准备;最近一次购买是否满足沉睡条件这类判断仍留到查询时算。
12. **agent 使用链路与交付确认**:agent 调用已有工具,工具调用产品业务查询。沙盘里会员属性与来源账户/注册门店关系来自按对象定义生成的本地库,订单和会员卡来自前几周的查询数据库,业务规则来自准备时保存的处理结果,同一查询服务组合返回。FDE 交付时要结合实际调用记录和返回结果,确认 agent 用的是调整后的实现、返回符合约定。

## 与青禾沙盘的连接点

- 三个客户函数就是三个扩展点,都在 `prepare` 时执行并保存结果,查询服务读结果——改了函数不重新 prepare,查到的还是旧结果;对象定义、代码、数据、规则或知识任何一项改过,都要重新 prepare→bind 新 home→init(任务书"改过就换新目录")。
- `member.linkml.yaml` 只填 Member/SourceAccount/Store 三处 slots;业务含义依据留在 `docs/w05/business_model.md`,业务判断写在 `solution.py`;把规则写进 YAML 的 description 不会生效——三份文件分工是"含义在 Markdown、结构在 YAML、判断在函数"。
- 两条红线的直接体现:registered_stores 必须与来源账户注册门店一致(不一致报 REGISTRATION_PROVENANCE_MISMATCH),POS 账户没有注册门店保持未知、不用购买门店反填;冲突、缺失和正常值分别表达,不能拿购买门店填未知。
- B 组直接入口与 Agent 逐项一致,对应第 12 条"确认 agent 使用了调整后的实现";D 组在隔离副本改一项规则、before/after 对照,对应"改规则要重新准备并验证改动确实生效、未涉及部分不变"。

## 可用于作业的证据 / 判断

- YAML 三处 slots 只能引用同文件下方已定义的字段名,填了没定义的名字报 gen-sqla CalledProcessError;TODO 三处都要删,只填一处仍报 MODEL_TODO_FILL_CUSTOMER_SOURCE;改 YAML 或函数返回值,不手改生成文件。
- member_attributes 契约:display_name 未知或冲突时为 null、不能硬选第一条,names/masked_mobiles 保留数组,tier 不确定为 null,conflicts 单列冲突,registered_stores 为去重关系集合、缺为空集合,sources 数组要能定位原文件、记录及字段——不新增猜测值。
- 来源映射对应"使用统一标识,不再重新判断身份":统一会员 ID 由框架从 identity_evidence 的有效依据生成,材料里读不到最终答案表;函数不得因被调用就认定对象是自然人,identity_status 由框架按映射写入。
- contact_constraints 在准备阶段 channel 为 None,要同时给出电话和短信状态,不能默认电话;actual_contact_authorized 本轮恒为 false;account_exclusions 不自动扩大为会员结论,单个账户排除与全体来源排除分开表达。
