# V07 业务知识的组织、检索与适用判断

> 视频 53:23(article 1036164,课件 34 页;字幕稿 `transcripts/v07-*.md`)。本周技术主线第三段,对应作业第 5 步 B、C 组:retrieve_knowledge 的层级与参数、建议的两类依据与程序把关。

## 核心方法与机制

1. **先选提供方式再谈实现**:资料少且集中→直接提供;资料多且每个问题只涉及部分→检索;有明确结构且稳定的知识(指标定义)→组织成目录按标识精准读取,不必走 RAG。沙盘知识索引材料只有 3 个文档、合计不到 10K,直接提供也能用,选检索是为了看清检索怎么实现;38 个指标也是直接全量放进提示词。
2. **切分三法与片段权衡**:按标题结构(制度、规范、产品手册,每小节一个片段);按段落/句子(无标题但段落分明);固定长度(会议转写等无结构材料的兜底,可能切断句子)。先看资料自身结构再选。片段大小没有通用最佳值:小片段主题集中、易匹配具体问题,但可能把结论与成立条件切开;大片段含义完整但混多个主题、返回无关内容;结合文档结构、常见问题类型与实际检索结果调。常用缓解是相邻片段部分重叠,让结论与条件同留一个片段——条件与结论相隔远时重叠不够。
3. **有条件规则的切分陷阱**:规则"只有 A 型设备且质检通过才可远程重启",若检索只返回"可以远程重启",有条件的许可就变成普遍许可。做法:匹配用小片段,命中后取回所属整段或相邻片段;两种实现——切分时把前后几句/所属小节标题存进片段(相邻片段冗余存储,修改要同步更新),或只记录指针(标识、段落、章节归属)按需获取。条件要登记在它真正约束的内容上:远程重启登记条件,"其他情况转人工检查"拆成独立部分。
4. **元数据三个用途**:①来源/版本——追溯;②有效期/业务范围——筛选;③指针——读取关联内容。哪些内容参与匹配、哪些字段供程序筛选、哪些随片段返回给大模型,要逐项确定并测试;来源、版本这类说明依据的字段一般不参与匹配。LlamaIndex 切分得到节点(片段正文+元数据);沙盘文档短,自编切分按空行切段落建节点,只支持文档级适用条件。
5. **两类索引**:关键词索引——拆词建倒排索引(记全部词只去停用词,或只选代表词但未选中的词检索不到),适合查明确术语,换一种表达就匹配不上,中文还要处理分词,实际项目复用开源分词工具或检索引擎;沙盘工具从简,直接记录连续词组。向量索引——embedding 模型把文字转向量,意思相近向量相似,查询时问题也转向量算相似度;问题和片段必须用同一嵌入模型,换了模型全部向量重算。
6. **相似不等于适用**:两条规定说同一件事,一条过期一条生效,过期的可能相似度更高;向量检索衡量文字相似,不判断规定是否生效、定义是否正确。命中后必须用元数据(有效期等)筛。课程作者的项目把指标定义放进向量库后效果反而下降,常检索到不相关或错误定义——不能据此说向量检索都不行,但印证"相似≠适用≠定义正确"。
7. **检索三步**:①取得候选——用匹配方式找可能相关的片段;②筛选——元数据过滤,用结构化条件而非自然语言;③返回——排序并带上下文与来源。一般讲 RAG 强调①③,处理业务规则时②才是关键。筛选条件值优先由调用程序提供(当天日期、提问者部门、资料访问权限,可靠);让大模型从问题里推断条件再填入检索 schema 不一定准;筛选只缩小范围,不能替代事实核对。
8. **先多取再筛,沙盘参数有明确语义**:筛选前只取最相关 3 条,可能这 3 条都过期而排在后面的仍适用;候选过少会在筛选前漏掉适用内容,数据量大要提前设部分条件缩小候选。沙盘知识工具:LlamaIndex 关键词索引取候选,文档小且数量上限高,匹配到的片段基本都保留;确定性代码按有效期与适用条件筛——片段上登记的知识工具及参数,与调用时传入的会员实际情况、联系渠道等不符则排除;条件未传入时片段仍返回,但明确指出缺哪些条件;参考日期未传则用数据参考日。三份文档 conditions 均为空,实际起作用的是有效期和层级:层级是参数,填错层级整份文档被过滤;按匹配关键词数量排序,默认最多返回 5 条。
9. **排查分三种情况**:片段没进候选(查问题表达、切词、索引,或换匹配方式);进了候选被筛掉(查片段上条件、日期、请求条件是否准确);返回但内容不完整(查数量限制、关键信息提取、组装)。三种都表现为"模型没拿到内容",要改的地方完全不同——每步中间结果应可见。沙盘知识工具只给最终结果,被筛掉的片段及原因不显示、全筛完只返回"未找到",难以区分前两种,要回运行记录里看;项目里用产品的知识检索,要问能否提供每步中间结果。
10. **分级加载**:几百个指标、多业务域(会员/商品/门店)全塞提示词不现实;三级——业务域入口(各域与覆盖范围)→域内指标目录(标识、名称、简述)→完整条目(定义、范围)。分寸:上一级足以选下一级入口,不重复下一级内容;简述用于发现、完整定义用于准确理解;名称相近的指标在简述写明区别(按支付统计 vs 按扣款统计);同一指标被多域使用指向同一份定义,避免复制多份口径漂移。读取分"发现"(逐级或检索)与"精准读取"(已知标识直接读、可跨域)。打标签不等于分级加载——要有目录结构、指针关系、可发现的入口,且 agent 能按此调用;Claude Code/Codex 的 skill 组织同思路(上下文只放简述,用到再读正文)。代价:每级选择由模型推断,每加一步引入不确定性——沙盘不为分级而分级。
11. **规定来自知识,事实来自业务工具**:知识是普遍适用的规定,业务工具提供特定对象的具体事实;规定能否用于该对象,要把条件(规定成立的条件)与事实(对象实际状况)对照。判断由谁执行取决于条件表达:已结构化为元数据字段→程序确定性判断;只在正文中→大模型按原文推断,可能出错,要输出推断依据供检查——能登记为字段的尽量明确化。确定性限制(设备安全锁定禁止一切远程操作)直接写进业务程序,每次操作前程序检查;知识库可放文字说明方便 agent 解释原因,但真正起作用的是程序限制,仅凭检索到的文字解除不了;对照用的事实必须经业务工具查询,不能由大模型转述或自行填写。
12. **适用判断两层设计、校验三种结果**:沙盘两层——调用知识工具时传会员实际情况,工具当场判断规定是否适用、指出缺哪些条件(避免大模型填参数出错);agent 提交建议后,确定性程序拿建议引用的规定条件与 get_member 返回的事实核对,这是真正把关的地方(身份核实、会员等级由程序查出,联系渠道经查询工具传入原样返回,按年限限制判断渠道可用)。课程实测六轮任务只有一轮模型把查到的事实填进参数,其余几轮因条件不齐被拒——工具已告知条件不足,模型仍凭规定提建议、从不回查事实,最终确定性判断也拒绝。结论:关键条件不仅靠提示,必须有确定性校验;校验三种结果——①条件全满足,知识可依据使用;②有条件不符(质检未通过),知识不适用,agent 说明原因并拒绝;③事实未查全——业务相关向客户澄清、系统可查的用工具补全,始终补不全则知识不能作依据。配套纪律:已获取的知识补齐事实后直接判断,对象或问题变化才重新检索;设调用次数上限防不遵循指令;每条结论指出两类依据(对象实际状况+适用知识片段),并确认引用的事实和知识是本轮查到的、不是上一轮遗留或模型猜测;校验通过不等于任务完成——校验只针对已提交内容,没查全或没按要求给结论时也可能通过,还要从任务语义审视。

## 与青禾沙盘的连接点

- `retrieve_knowledge` 的 `level` 按知识目录三份文档填:`definition`(03_身份关联与数据使用说明)、`domain`(04_运营对象核验说明)、`usage`(05_联系限制与建议说明);层级会筛选文档,查联系限制却填 `domain` 取不到 usage 层内容;不确定可不传,不传仍受关键词、有效期、适用条件与条数限制。
- `context` 只放 `channel`/`identity`/`tier`,从 `get_member` 返回的 `recommendation_context` 取值,不自行编写或猜测;本周三份文档 conditions 均为空,传不传不影响返回,但建议校验仍会把引用片段的条件与 `recommendation_context` 核对。
- B、C 组建议要同时指得出两类依据:会员事实来自业务工具(get_member/member_relations),适用规定来自知识片段;明确联系禁止由 `contact_constraints` 程序判断,知识不能解除,"未发现限制"不能说成联系授权(actual_contact_authorized 恒为 false)。
- Agent 返回 `incomplete` 先按第 9 条三情况定位(没进候选/被筛掉/不完整),别急着改提示词;名单非空时每人要有建议或不建议记录,`facts_pending`/`no_applicable_knowledge`/`evidence_missing` 只能 incomplete,`program_blocked` 可以完成——对应第 12 条校验三结果。

## 可用于作业的证据 / 判断

- C 组从公开记录各选一个明确电话限制对象和一个渠道范围待核对象:程序与 Agent 都要保留禁止/待核及补充确认来源;knowledge-*.json 的检索证据要与对象查询结果互相印证,片段条件与会员事实对得上。
- 不给建议的理由要有当轮证据支持(evidence_ids),模型声称查过但工具没返回的事实不算数——"事实来自业务工具"是 checker 与人工审查共同的判据;`CANDIDATE_NOT_DISPOSED` 常见原因是只圈了名单没逐人查详情、关联记录和知识。
- 检查 Agent 回答四点:建议是否基于充分的事实和知识;明确禁止和待核事项是否保留;不同任务的依据是否混淆;对照原题确认涵盖全部要求。GROUNDED 只说明校验通过,不等于题目完成,提交前对照原题逐项核对。
- 思考题方向:新增"不能发短信"是确定性限制→改程序(contact_constraints 与校验),同时在知识文档更新说明让 agent 能解释依据——只改一处不成立,限制与解释两处都要动。
