# V10 身份关联与业务口径对齐

> 视频 21:48(article 1036168,课件 22 页;字幕稿 `transcripts/v10-*.md`)。交付实录课:神策 ID-Mapping 从一对一走到多实体的演进,加上投手 Copilot 两段亲历——同一条素材怎么认定、"在投"口径怎么写成明确定义。放在 V05、V06 之后看,印证本周方法。

## 核心方法与机制

1. **神策 ID-Mapping 的起点:一对一**:产品从实时数据流设计,每条数据进来先定归属再入库。最初一个匿名设备 ID 只关联一个用户 ID——设备首现分配主 ID 记录匿名行为,首次登录时直接沿用,登录前后同一个主 ID,已写数据不用改,省掉历史回溯;代价:人换了设备,新设备关联不到旧设备的登录前行为,那批匿名行为在系统里成了"另一个用户"。
2. **放开到一对多**:业务上要把同一人经 APP、网页、小程序的行为归到同一用户,于是允许多个匿名设备关联同一登录 ID;代价是数据回溯——实时写入要与批量修正的历史数据配合,实现难题多,售后运维压力大。
3. **多层次 ID 树**:银行、券商客户的身份关系本身分层——一个身份证对多个手机号,每个手机号又对多个设备 ID;为适配这种业务,ID 映射扩成多层 ID 树。同时分析主体可自由选择:用哪个用户标识计算、算出什么结果,由业务决定——这就是身份口径。
4. **解绑与多实体**:金融客户有账户迁移合并,迁移本质是先解绑再绑定,于是加解绑功能;零售连锁商超要把商品、商铺纳入系统打标签、跨系统贯通商品 ID,扩成多实体映射。演进链条:一对一 → 一对多 → 多层 ID 树 → 解绑 → 多实体。
5. **演进的方法论**:ID map 不是一开始就大而全——先为技术实现和稳定性接受明显限制,随需求逐步放开,每放开一步都付出工程代价。FDE 是这个系统的使用者,要判断客户身份关系的复杂度与产品支持的匹配:功能够就别过度设计,功能不足就核对需求与支持之间的缺口。
6. **素材认定的弯路:名称不可靠**:广告素材是核心业务对象,一条好素材可反复用于不同系列(换受众和触达方式测试效果),评估表现要先确定哪些广告用了同一条素材。客户有命名规范(广告直接用素材名命名,含类型、款号、红人信息),最初按名称判断;核验上万条广告、数千条视频后发现几百条素材横跨多个系列,一条甚至跨十几个系列投放近一年。
7. **两类名称错误,创意 ID 也不可靠**:同一素材多个名称(帖子编号中途更改、复制广告名字加后缀)→ 按名称汇总被拆成多条;同一名称对应多条不同素材 → 上百条被算成一条。平台创意 ID 同样不行——最常用的视频对应几十个创意 ID,每次投放几乎都重建。这两类错误本质就是 ID-Mapping 里的漏合并与误合并。
8. **定标识:资产 ID**:素材用平台接口返回的资产 ID 标识;一条素材可进多个广告,广告与素材的关系单独保存、对新广告增量补充。名字只用于展示,不可作标识;规则用确定性代码固化进钉盘计算。
9. **文档改了,执行没跟上**:规则写进文档四天后,7 月 7 日团队首次用 agent 完整跑钉盘,发现数据仍按广告名汇总——四天前已被证伪的方法。业务规则和文档变化时,执行程序必须同步更新,否则结论和建议全错。
10. **"在投"口径事件:234 vs 77**:7 月 7 日接口显示某账户有 234 个开启状态的广告系列,投手认为只有 70 多个。平台三层结构(系列、组、广告)各有独立开关;投手日常只关广告层(关广告即停止投放),上层的组和系列一直不动,账户里积累了大量"开启但无广告在跑"的空壳。投手后台按"投放中"筛会自动滤掉空壳,而 API 统计没做这层过滤,把空壳都计了进去。
11. **口径写成规则**:按投手思路重算,数字对上;把"投放中"明确定义为"系列(或广告主)开启,且其中至少有一条广告开启"。接口返回的状态字段含义不能凭字段名猜,没有现成字段就用业务逻辑实现。记录规则要带三样元数据:适用范围、获取日期及原因、当前有效性;规则只适用于特定账户,换账户要重新验证;变更时知识库加新条目、旧条目标记"已替代"而非删除,保留历史判断依据。次日独立盘点:234 个中 77 个在投、157 个空壳。
12. **口径事件反过来改了产品**:钉盘界面改为展示全部系列列表——空壳不显示,有建议的在上方、无建议的折叠在下方;客户随后提出误关的广告要在后台显示为灰色、可查看可修改,"不显示空壳"的规则在新用途下显得不足。与 W03 茶饮案例对比:茶饮是指标定义在客户内部有歧义;本案定义在投手间无歧义,是我们错用系统字段代替了业务口径。

## 与青禾沙盘的连接点

- 神策演进的启示落在 V05 的作业路线上:青禾走"明确关联 + 离线生成映射"这一路(迁移记录、核查记录),不需要概率匹配和实时处理;先想清身份关系的复杂度,再核对产品支持的缺口,不过度设计。
- 素材案例的两类错误就是青禾身份合并要防的漏合并/误合并:姓名、脱敏手机号、设备相同都不足以认定同一人,身份判断写进确定性代码(客户函数),不靠临场推断。
- "在投"口径事件对应 `buyer_count`:统计口径写明粒度(购买财务实体数、含身份待核的来源账户),回答第一句就说明;规则连同适用范围和依据一起进知识库。
- "文档改了执行没改"对应"改过就换新目录":改了身份规则或指标描述必须重新 `prepare`,否则查询返回的还是旧口径的结果。

## 可用于作业的证据 / 判断

- V10 结尾布置的思考题就是本周作业:"青禾会员数据里哪些记录属于同一个人、按什么口径计算"——不同行业的答案不能照搬,处理思路一致:先明确依据,再谈推断。
- 报告里写规则(身份依据、采信规则、联系限制)参考投手案例的三件套:规则本身 + 适用范围 + 获取日期及原因 + 当前有效性;变更留痕,旧条目标记已替代,不删。
- 接口/导出字段的状态值不能凭字段名解释:青禾各来源字段含义以材料和访谈为准(身份依据、导出范围、记录状态问老周),解释不清保留待核,写清缺什么、影响什么。
- Agent 遇到没有合适建议对象时返回空名单,与钉盘"无建议折叠展示"一致:B 组验证遇到空名单先核对条件与覆盖,不为非空改主条件或编建议。
