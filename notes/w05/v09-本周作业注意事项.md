# V09 本周作业注意事项

> 视频 10:55(article 1036166,课件 10 页;字幕稿 `transcripts/v09-*.md`)。作业导览:两张架构图定位本周两块开发,把 8 个步骤讲成五件事,再给 5 处容易漏掉的提醒。动手前看一遍,提交前对照后半段逐条检查;完整步骤以《W05 任务书》「作业路线」为准。

## 核心方法与机制

1. **本周两块开发**:在 W04 基础上继续——一块是 ID-Mapping(打通会员身份,属准备阶段),一块是会员业务能力(按条件圈选会员、查看记录与关联信息、给出有依据的建议)。本周只做到建议,不调 API 打标签、不实际联系。
2. **数据流图(准备阶段)**:输入三路——前几周成果(W03 指标库、W04 清洗好的 CRM 数据)、本周新导出的 POS 数据、迁移核查等业务记录。程序读取输入后调用身份依据函数,判断哪些账户属于同一人;课程方提供的框架给每个会员分配统一 ID,新旧订单挂载到该 ID 上,写入查询库。
3. **准备阶段的产出**:查询库、对象库、一组状态文件、知识索引四样,另外生成对账结果,核对账单与订单金额的一致性。
4. **运行时架构图**:运营 Agent 底座 W01 已存在,本周配 5 个工具——查指标(W03 接入)+ 新增 4 个(圈选会员、会员详情、关联记录检索、知识检索),都来自同一个会员业务模块;两个入口——客户运营人员直接用 Agent,门店走命令行直接入口,两边结果应一致。
5. **数据从哪来**:查指标和圈选用 W03 指标库在库上计算;会员信息来自对象库,结构由 YAML 决定,YAML 按 W02 维护的业务模型填写,属性内容由会员属性函数提供;联系限制等客户函数在准备阶段执行,查询读的是已准备好的结果——改了函数不重新准备,查到的还是旧结果。
6. **本周要写的东西**:一份 YAML(`Member`、`SourceAccount`、`Store` 三个类的字段和关系列表)+ 三个客户函数(身份依据、会员属性、联系限制);其余是前几周成果或课程提供,指标和平台不用重写。不想用 Python 也可以,但输入输出契约要一致。
7. **8 步讲成五件事**:①读材料、列缺口(缺口里的规则需访谈确认实现细节);②填对象定义、写三个客户函数;③运行准备——`prepare` 生成新目录、核对账户订单金额和指标、`bind` 绑定新运行目录、`init` 初始化;④验证并写报告——五组验证(A–E)成败都记进同一份报告,其中一项确认筛选不局限于沉睡条件(Agent 能力不限于唤醒沉睡会员);⑤导出、补齐、自检、提交,对照任务书第 7 步提交表。
8. **提醒一:改过就换新目录**:代码、数据、规则一变就重新 `prepare`、绑定新目录再 `init`;继续用旧目录可能报错或查到旧结果。建议每次修改都换新目录,保留旧结果用于对账。
9. **提醒二:区分冲突与缺失**:不同来源的值不一致是冲突,来源确实没提供才是缺失;不要把冲突标记成缺失,也不要把缺失误当成真实值。
10. **提醒三:`buyer_count` 口径变了**:本周不分组的买家数统计的是财务实体数量(含身份待核实的来源账户),不是自然人数。要打开指标库,把显示名和描述改成明确写数据粒度;验证时第一句就说明粒度,不能只在末尾补一句。
11. **提醒四:知识层级不要凭印象填**:层级填错会取不到对应内容,不确定时可以不传;层级与文档的对应关系在业务知识一讲的表格里。
12. **提醒五:程序通过不等于作业完成**:自检脚本只查常规项。典型是 B 组主条件筛选会员验证——有建议对象就给带依据的建议,没有就返回空名单,不要为有内容而编造;提交前对照任务书原题逐项核对。卡住先查任务书第 6 节排查表,再找助教。

## 与青禾沙盘的连接点

- 两张架构图就是「作业路线」的骨架:第 0 步环境与带入 W04 成果 → 第 1 步读材料列缺口 → 第 2–3 步填 YAML、写三函数、`prepare` 对账 → 第 4 步 `bind`/`init`、试调两个入口 → 第 5 步 A–E 验证 → 第 6 步报告 → 第 7–8 步导出、自检、提交。
- "客户函数在 `prepare` 执行、查询读准备好的结果"解释了任务书注意事项里的"改过就换新目录":只改指标库时旧目录照样能跑,跑出来的是修改之前的结果,自己不容易发现。
- 两个入口结果一致对应 B 组验证:直接入口和运营 Agent 用同一个会员业务模块,这是系统集成"返回正确还要被正确使用"的做法在本周的落点。

## 可用于作业的证据 / 判断

- 提交前 checklist 来自提醒五:拿任务书第 5 步原题逐项对一遍;空名单、待核、部分结果都可能是正确表达,不为非空改条件或编建议。
- `buyer_count` 的验收口径在提交表第③项:显示名和描述写明"购买财务实体数、自然人数待核",回答第一句说明粒度——这不是可选项。
- 冲突/缺失/正常值三分法对应第五节判定:可确定的必须算准确,未决对象明确单列;POS 账户没有注册门店时保持未知,不用购买门店去填。
- 每组验证的预期写在运行之前;看到失败不改题、不换题,定位原因后同题回归,失败记录如实保留进同一份报告。
