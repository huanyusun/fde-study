# V04 系统集成:从接口契约到联调验证

> 视频 26:19(article 1036155,课件 19 页;字幕稿 `transcripts/v04-*.md`)。系统之间怎样约定和验证:接口契约消除哪些歧义、"调通了"之后还要回答什么——对应作业第 4、5 步(共享入口一致性、A~E 验证证据)。

## 核心方法与机制

1. **系统集成是交付的核心工作**:把不同模块和系统的功能连接起来,按业务需求交换数据、协同完成任务。例:方案里"查询会员资料并交给 agent 分析"画在图上是一根线,实际要明确资料谁提供、怎么取得、返回内容表示什么、agent 怎么用——架构图的每根连线都要逐项澄清。真实项目例:连接广告平台与客户业务系统做分析,先对接账户体系、统一报表口径。
2. **调用关系两个角色**:发起操作的程序=调用方,提供操作的模块/服务=提供方。API、SDK、MCP、模块调用、client 处于**不同层次、不是互斥关系**,按语境理解。
3. **进程内模块调用**:同一进程内调用另一模块的函数(如 agent 直接调会员查询模块的读取函数),通常无需单独部署网络服务;被调模块可能由另一个团队(甲方、开源社区)在不同代码库维护——要了解怎么传参、依赖哪些库、如何初始化。
4. **远程调用三件套**:API 多数情况指远程 API,运行在独立服务,调用要有服务地址(IP+端口)、访问权限、网络连通性;SDK=程序库+工具+文档,封装请求构造和返回值解析,用时要查语言和版本兼容、封装了哪些操作、错误报告方式、服务依赖;MCP 为应用取得工具提供统一约定,MCP client 发请求、MCP server 按协议提供工具,本地进程通信或 HTTP 均可,不一定走网络。
5. **一条路径可同时出现多种方式**:agent 经 MCP 调会员查询工具→MCP server 借 SDK 访问远程 API→远程服务真正执行数据库查询——MCP 定义工具交互方式、SDK 简化远程调用、实际查询由远程服务完成。搞清层次才能明确方案中每项能力的提供方、调用方式和调用条件。
6. **接口契约的思想实验**:"输入会员 ID,返回会员资料"一句话没法正确使用——会员 ID 来自哪个系统?返回资料含哪些内容?未查到怎么处理?资料覆盖哪些来源?数据是什么时间点的?契约要说明操作、调用条件、输入输出、错误处理;可写在接口文档、函数说明、类型定义或工具 schema 里,用实际样本或测试案例检查;FDE 结合业务用途与提供方确认——没有规整文档的项目,靠不断询问和尝试逐步完善。
7. **契约五要点**:①操作对象——统一会员 ID 还是客户 CRM 的 CRM ID?都是字符串但编号体系和指向对象不同,传错可能查不到也可能格式兼容,契约只写"字符串"不够;②返回字段含义——姓名的格式编码、来自 CRM 还是 POS、两系统不一致时的返回规则;金额单位是角还是分、时间哪个时区,不能凭字段名猜;③区分不同返回结果——操作失败/未找到/找到但异常(身份未知、部分资料缺失)要各有表达,避免把"未找到"和"执行失败"混为一谈;④适用范围——覆盖哪些数据、更新时间、数据和规则版本,随结果返回或写进配套说明;⑤分页、调用频率、超时等限制与处理——下一页怎么取、怎么判断结束、超限怎么办、多久算超时、超时怎么反馈。
8. **契约的表达形式随调用方式变**:远程 HTTP 接口可用 OpenAI 式描述规范(记录操作参数、返回结果及说明);进程内函数主要靠类型定义和示例。现有接口满足不了业务需求→回到 V03 的方法调整解决方案。
9. **契约明确≠问题解决,集成验证要备三样**:①运行环境——能真正运行的模块或至少可访问的测试服务,确认版本与结果说明一致;确保程序读的是本次验证所需的数据(读错数据核对就白做);备好测试用例=输入+**事先独立确认的预期结果**。②访问权限覆盖计划验证的范围——测试账号只能查一家门店,验证范围就先限于这家,查其他门店先取授权;还要确认网络可达。③配合人员——接口服务提供者及参与时间提前沟通,联调双方共同检查调用过程和结果,事先约定版本和测试用例。这些是项目计划的一部分,FDE 要单独列出系统集成的时间和资源预算并留余量。
10. **"已经调通了"之后必须回答三个问题**:①操作是否成功——远程调用收到响应≠成功,要查响应状态;进程内函数没抛异常也不保证成功,按契约检查请求和反馈;②返回内容是否正确——与事先独立确认的预期结果对照,依据是契约:对象归属、字段和状态准确性、数据范围版本一致性;③调用方是否正确使用结果——提供方反馈的状态和资源限制被正确使用,处理结果符合业务任务预期。反例:目标函数成功返回了资料,但未记录数据版本、未与预期对账、未检查下游使用→只能确认"执行成功",正确性不确定、缺乏使用证据。
11. **尽早验证、先打通最细真实链路**:具备必要条件就尽早做集成验证,不等所有功能开发完——后续开发和排期依赖这些接口的数据;越早核实假设,返工越少;拖到后期,大量代码建立在未验证假设上,假设一倒调整代码和排期的代价极高。首次验证范围小,但要覆盖关键调用及其后续处理;"真实"=实际的模块、服务和数据参与运行——mock 有助于开发后续逻辑,但无法验证集成;在测试环境用获批的测试数据,不直接上生产;明确本次验证哪些环节,未参与的标记待验证;小范围通过后逐步扩大,**每次结论只对应实际验证过的范围,不随意放大**。
12. **本周沙盘同样适用**:定制开发代码与产品框架的配合虽未对接客户外部系统,但接口契约、运行条件、结果验证的方法一样用——判断会员是否真沉睡要结合新 CRM 和旧 POS 的消费记录;下一讲 ID-Mapping 解决"两系统账户是同一个会员"的确认问题。

## 与青禾沙盘的连接点

- B 组验证就是接口契约思想的作业版:直接入口和运营 Agent 用同一个会员业务模块,相同条件和数据版本下结果要一致——不只是"返回正确",还要"被正确使用",逐项比对。
- 三个客户函数的返回就是契约:身份依据返回"已确认/待核/冲突"如何区分、会员属性字段含义与来源、联系限制的渠道粒度——对应任务书"冲突、缺失和正常值分别表达","未找到"和"执行失败"不能混为一谈。
- "调通了"三问对应第 5 步验证设计:每组预期在运行前写好,来自公开记录或独立 SQL,**预期不能是再调一次被测函数**;A~C 用真实模型运行记录(A 组两问同一会话),D、E 可用直接入口或本地小样本——mock/小样本支持开发,不能支持集成结论。
- 数据版本写进报告:`data_version`/`rules_version` 与 `manifest.json` 一致(自检 `block2_report_version_agreement` 查的就是这个)=契约第④要点"覆盖范围与版本"。
- 尽早验证落进作业顺序:第 4 步 `bind`/`init` 后先试调直接入口,再进第 5 步固定验证——先打通最细真实链路;已核实范围的结果不能冒称全公司结果,未验证环节如实标记。

## 可用于作业的证据 / 判断

- `verification_cases` 按"三问"组织:操作是否成功、返回内容是否正确(与独立确认的预期对照)、调用方是否正确使用结果;`findings` 写判断和失败定位(规则/数据/工具/上下文/输出约束),失败如实保留、同题回归。
- 对账即对照预期:`reconciliation.json` 的账户数与金额守恒=与事先独立确认的预期结果核对;有差异定位到记录和规则,不设容差放过。
- 契约五要点当自查清单:对象与编号体系(统一会员 ID vs 来源账户 ID)、字段含义与单位、结果状态区分、覆盖范围与数据/规则版本、限制与超时处理。
- 结论不超出验证范围:每次结论对应实际检查过的部分;验证范围与账号权限、数据版本一致;发给模型的内容只放当前任务需要的对象和依据片段。
- 系统集成的工时单列并留余量:`time_log` 里把联调、等待、返工按阶段如实记,直接对应本讲"时间和资源预算留余地"的要求。
