# V03 从标准产品到客户解决方案:能力适配与开发取舍

> 视频 33:34(article 1036154,课件 21 页;字幕稿 `transcripts/v03-*.md`)。本周读材料、列缺口、做开发取舍的方法来源——对应作业第 1 步缺口清单,写报告第 6 步也回来看。

## 核心方法与机制

1. **FDE 的核心工作是填差距**:结合客户的数据、业务规则和现有系统情况,把标准产品(含 agent)已有能力组织成能完成整个业务任务的解决方案——差距=需求−已有支持,先组织、再找缺、再定怎么补。
2. **以客户业务流程为主线拆环节,每环节问三个问题**:要完成什么操作?处理哪些业务数据?遵循哪些业务规则?例:筛选会员的购买记录是业务数据,消费金额计算方法和入选条件是业务规则;客户专业人员头脑里的经验(查询顺序、结果解释)也要落实到操作和规则里,不能只存在人脑中。
3. **逐环节核对现有能力**:现有系统功能是否支持所需操作、产品配置能力能否满足;核对输入、返回结果、数据范围、使用条件;拿不准就做针对性功能检查或 POC 验证。核对后仍缺的功能/数据/依据列为**缺口**,每条标明影响范围和后果。
4. **沿业务流程组织初步方案**:每步写清用什么现有功能、配置什么业务要求、谁执行;前一步输出要符合下一步输入(信息齐全、格式一致);**环节之间的衔接缺口也要明确指出**。引入新系统可能精简或改变客户原有流程,这也要写进方案。
5. **青禾例(三环节)**:①准备会员消费信息——先做 ID 映射,数据=新 CRM+旧 POS 的账户与购买记录、迁移和账户核查记录;②筛选沉睡会员——数据=映射后的消费记录+门店归属,规则=消费金额、最近有效购买时间的计算口径、门店范围、沉睡条件;③形成运营建议——数据=筛选结果+会员特点,规则=按特点选运营方式、按联系限制排除。缺口例:部分新旧账户缺迁移或核查记录,无法确认是同一会员→业务数据缺口,影响消费记录归类、筛选和建议生成。
6. **初步方案的样子**:产品查询取账户消费记录→ID 映射把确认的记录归属到人→缺数据无法映射的账户**单独标记**→配置门店范围/消费金额/沉睡条件→计算筛选→输出名单时说明数据覆盖范围及待核影响→生成建议时附上联系限制并遵守,没有确定结论不做判断;方案末尾列出待补齐核实的内容(涉及哪些账户、怎么补、怎么验证)。
7. **缺口三层面各有补法**:操作层面——缺功能补功能,已有的做适配;有查询接口≠有功能,要组织成 agent 可用的工具(使用场景、输入参数、返回含义),必要时把几个底层操作组合成任务工具。数据层面——缺数据先补齐核实(补齐后已有功能直接可用,无需开发);格式/系统间流通不匹配再补数据处理能力;数据不足时选客户提供或自行适配开发。规则层面——规则不明与客户核实、补判断条件和例外,**不让大模型直接猜测推理**;规则明确但产品缺内容,就整理后通过产品知识供给机制接入并验证 agent 能拿到能用;规则明确且配置无误=无缺口;规则明确但功能执行不了,补处理和校验能力。
8. **三层面都要查访问与连接条件**:数据/操作已存在但未授权→去申请权限而非擅自使用;连接方式不支持所需传递调用→补接入能力;只是连接参数问题→属配置工作,写进实施安排。具体接口契约和验证方法留到 V04。
9. **补齐动作映射到交付手段**:补充资料、核实规则、接入知识和系统=实施工作;涉及新增/修改代码的形成开发清单;也可以不做定制、推动标准产品升级。**补不齐的缺口**先找客户可接受的替代方案(人工处理、换数据来源、缩小范围),且必须写明限制和额外工作量;找不到替代方案就与客户讨论调整 SOW;核心因素不可妥协时尽早告知项目无法继续,减少损失。
10. **开发取舍两维度**:通用性(一大类客户共同需要,依据=其他客户需求/相似业务过程/一致性要求)+阻塞性(不解决对当前交付的影响,FDE 自行核对阻塞后果与替代方案;**客户紧急催促≠实际阻塞,没催促也可能是真阻塞**)。四象限:通用且阻塞→优先标品改进并尽快交付;客户特有且阻塞→定制开发,把特有规则与通用功能隔离;通用不阻塞→作为正式需求提交产品团队统一安排(有复用价值,但不借机扩大当前项目范围);特有不阻塞→与客户协商延后或取消,但不能单方面决定不做,要遵守 SOW。四象限是方向指导非硬性规定,还要看实现条件——产品迭代节奏跟不上时,在"临时定制"和"调整交付节奏等标品"之间判断。
11. **三种代码置入方式与维护代价**:负债区=为客户拉独立分支写特有逻辑、不合回主干——需求肯定满足,但客户版本与主干各自演进差距越拉越大,主版本升级要重改重验、合并冲突代价大(故名"负债");隔离区=特有逻辑进统一代码库+配置/功能开关控制启用范围——省了版本合并,但增加标品复杂度,开关与其他配置的相互影响要管理测试;只在界面隐藏选项而底层没隔离≠覆盖实际影响;神策也用 flag 做新功能灰度。资产区=把逻辑做成标品通用功能、供多客户使用——降低后续项目成本,但要走完整开发流程(适用性检查、评审、回归、持续维护),少数客户的需求变成默认行为会增加使用和架构上的复杂度。
12. **agent 的维护不止代码**:即使代码和接口兼容,模型、提示词、工具 schema 一变,agent 行为就变,相关业务要重新验证(工具结果是否符合业务限制)。二次开发要看大模型能否业务上兼容:接口只加一条备注、主流程用不上=没解决问题;agent 能否理解"待核实"这种新状态要验证。绕过正式接口直接依赖产品内部逻辑≠做好隔离;独立扩展方式省了主干合并,代价是接口变化后的适配与升级验证。所有结论都要反馈回解决方案,更新业务流程和交付范围。

## 与青禾沙盘的连接点

- 第 1 步缺口清单的格式(缺口/影响/已有依据/下一步)就是本讲"列缺口并标影响"的落地;缺口清单**不是功能列表**——青禾这轮筛选和查询产品已有,缺的主要是身份依据和客户自己的规则。
- 三环节拆解直接对上沉睡召回流程:ID 映射(新 CRM+旧 POS 账户与购买记录、迁移和核查记录为依据)→筛选(消费金额、最近有效购买口径、门店范围、沉睡条件)→建议(按特点选方式、联系限制排除);业务模型七节按这个骨架写。
- 未决身份=补不齐的缺口也要有处理结论并随结果传递:未决账户单列、名单标待核、`buyer_count` 说明粒度(统计购买财务实体数、自然人数待核)——对应判定标准"可确定的必须算准确,未决对象明确单列";把全部账户丢进待核回避实现、或为凑人数错误合并,都不达标。
- 四象限定位:青禾的账户关联是"客户特有且阻塞"→定制开发,并把客户特有规则与通用功能隔离——本周做法是经预留接口接入、隔离客户逻辑;但业务方案只写"读客户数据、调产品接口"不够具体,必须写明读取内容和调用条件并通过验证(V04 接口契约)。
- "待核实"是本讲的现场例:资料不足以确认两账户是同一会员时保留待核实状态,标品只有是/否不够——`identity_evidence` 的返回设计直接对应。

## 可用于作业的证据 / 判断

- 缺口清单每条写:影响哪个函数(`identity_evidence`/`member_attributes`/`contact_constraints`)或哪个结论、已有依据(文件名+节)、下一步(材料已明确直接引用/向某角色定向询问/保留待核)。
- 规则不明确不让模型猜:消费金额口径、联系限制、运营排除全部从材料引用;接入的知识要验证 agent 检索得到(对应 V07 与 C 组验证)。
- 替代方案必须带限制说明:部分补齐时写明哪些账户可进入后续计算、结果范围受什么限制,不把"部分"说成"全部"。
- 用更新后的方案补齐并通过实际业务任务验证=D 组前后对照证明定义确实被用到;`change_log` 写位置、原因、前后版本、预期影响、前后证据。
- 延后/放弃要与客户协商并遵守 SOW,不能单方面取消承诺——报告里"本期处理/延后"的取舍要能指回依据。
