# V05 ID-Mapping的原理与实现

> 视频 47:30(article 1036156,课件 32 页;字幕稿 `transcripts/v05-*.md`)。本周技术主线第一段,对应作业第 2、3 步:身份依据与离线映射。青禾沙盘用的是其中最基础的一条路——基于明确业务依据的离线 ID Mapping。

## 核心方法与机制

1. **ID Mapping 解决什么问题**:新 CRM 与旧 POS 各有一套会员编号,直接用各自编号统计,同一个人会被算成两个人,消费记录被拆开,会员分析和运营决策跟着错;多端产品同理——网页 Cookie ID、APP 匿名设备 ID、微信 OpenID、登录后的用户 ID 混在同一批日志里。目标是把各种标识关联到同一身份,并保留标识之间的关系(不是只输出一张扁平名单),这样既能按选定口径汇总,又能回到设备等原有粒度分析;而口径本身由业务决定——统计银行真实开户按自然人,发优惠券按登录账号。
2. **FDE 的定位**:不需要从头开发 ID Mapping 平台,职责是明确统计口径与关联依据、判断现有产品功能是否满足(配置还是补充开发)、把关系从数据中提取出来完成映射、并负责验证最终业务结果;交付后还要关注落地效果、定位问题原因,不是把问题转给研发就完事。计算引擎选型(内存/数据库/Hadoop 分布式)属于大数据工程,了解原理即可。
3. **第一步:盘点用户标识**:CRM/POS 用户编号、银行卡号、cookie ID、安卓 ID、IDFA/IDFV、OpenID、登录账号……每个标识的含义与适用范围不同:数据契约里的用户 ID 字段不一定对应自然人;OpenID 按应用隔离,同一微信用户在两个小程序/公众号取值不同,不能把所有 OpenID 当同一标识。
4. **主 ID 两种设计,关联树可多层**:①选业务系统已有的唯一标识(身份证号/登录账号),直接用或转哈希,前提是每个值确实对应独立个体;②重新分配统一 ID(如神策 ID),再建它与登录账号的关联。主 ID 作根节点,树可以多层:主 ID→UnionID→多个 OpenID(同一微信开放平台下)。程序实现不一定用树这种数据结构,树是逻辑表达;业内把构建关联的过程称为实体解析。
5. **明确关系优先,用前先验证**:登录、绑定、系统迁移记录语义无歧义,是首选关联依据,但要验证有效性——迁移是否成功、记录是否被撤销、绑定的有效时间。从有效业务记录中提取对应关系,按主 ID 规则保存;概率匹配只是缺乏明确关系时的辅助,业务有强登录账号体系时不一定需要。
6. **新数据对主 ID 的两种影响**:①增加新关联——匿名 Cookie 首次出现分配主 ID 100,用户注册后登录 ID 关联到 100 下,历史数据归属不变,无需回溯;②合并两个主 ID——设备 B 匿名先分配主 ID 200,用户用同一账号登录后才发现 100/200 是同一人,通常保留先创建的 100,把 200 下标识关联过去,并回溯已归属 200 的历史数据;回溯代价过高且业务可接受部分差异时可不回溯,由业务需求决定,不是技术说了算。
7. **概率匹配四步**(仅作补充手段):①筛候选对——数据里有数百万甚至上千万设备,两两比较不可行,先用规则筛出值得比较的对(如姓名+出生日期相同、或邮箱相同,多条规则互补覆盖字段缺失);②提特征——共现次数、时间分布、网络使用人数、行为关联;单次重合证据弱,长周期反复重合强,但也可能是家庭成员共享设备;③打分——加权规则、标注样本训练、设备关系图均可,区分能力的判据:现象在不同人之间常见则弱,在同一人频繁出现而不同人少见则强;④定门槛——相似度 0.9 不代表 90% 概率,用样本验证不同分数下的误关联/漏关联再定自动关联门槛。IP+UA 不能简单拼接:办公室多人共用出口 IP 且 Chrome 版本相同则 UA 相同;同一人在家和公司 IP 不同、手机和电脑 UA 不同。
8. **筛选规则用召回率和成本双向检验**:100 对已知同人配对保留 95 对,召回率 95%;但保留多少决定后续精细比较是 1000 对还是 100 万对,核心是提高召回率的同时控制计算成本,量太大就缩时间范围、加筛选条件;每次调整重测召回率,样本要覆盖缺字段、录错、网络变化等情况。
9. **关系维护三件事**:①冲突——不能仅凭设备相同就合并登录账号,按建立时间或来源可靠性取舍,或把冲突数据单独记录核实;按时间取舍时要配置清楚是"关系发生的时间"还是"系统接到的时间";②解绑与错误关联分开处理——解绑是从某时间点起关系失效,历史记录不必改;错误关联(两个实体被并到同一 ID)要重新确定归属并检查受影响历史数据,与客户确认生效时间和历史处理标准,删掉一条关系后还要核查其他有效关联;③保留关联依据和变更记录——发现问题才能定位影响范围、确认修正生效。
10. **离线实现两段流水线**:提前确定一批输入(账户资料、绑定记录),记录输入范围与规则版本;先生成映射关系(映射表:各系统标识值→主 ID+关联状态),再用映射处理业务数据(事件、订单、售后工单——ETL 从每条记录找来源标识、查表补主 ID、保留原信息)。规则不变时增量更新,改规则或纠错时重算受影响范围,数据量小可每次全量;更新后检查通过再让下游统一切换,避免同一份结果混入新旧两种口径。另一选择是只存映射表、查询时 join——省 ETL 和回溯,但查询复杂、有版本一致性问题;按更新频率、查询要求和产品能力选。
11. **实时实现三个区别**(知识面,作业不要求):①逐条处理中构建更新映射,关联树放 KV 存储,顺序仍是先更新映射表→取主 ID 写回数据→数据流前进;②新数据与历史协调——200 并入 100 后要另起批量任务回溯,实时流和批量回溯会冲突(事件已查到旧 ID 200 还在队列,关联却已更新,时间窗内遗漏),可行思路是借鉴流处理 barrier 机制在切换时明确边界,边界后用新映射、之前保留旧 ID,确认旧数据写入完成后再回溯、已扫描的补扫交错期数据;③三个时间概念分开——新数据可用时间、历史回溯完成时间、下游画像/统计更新时间;常见折中是新事件实时可用、历史归属离线批量修正。
12. **验证分三层,标准必须独立**:①映射本身——误合并(不同人并到一个 ID)与漏合并(同一人标识分开)分开检查,用独立判断标准,不能拿系统自身结果证明自己正确;指标用准确率(判为同一人的样本中实际同人的比例)与召回率(应判同人的样本中被正确识别的比例),并准备共享设备、资料缺失、关系冲突等代表性样本;②ETL 后业务记录——逐条核对主 ID、无遗漏重复、回溯范围正确;课程做法是同一组数据按正常顺序和乱序各跑一遍,比对最终主 ID、数量与回溯范围;③端到端——用独立口径算指标、圈人群,与系统结果比;明细正确不代表业务结果无误,圈人用了未更新的旧画像,结果照样错。

## 与青禾沙盘的连接点

- 对应作业第 2 步 `identity_evidence`:输入是迁移记录(`migration_records.csv`,状态 success/failed/revoked/unknown)、账户核查(`account_review_records.csv`,same/different)等明确业务依据——正是第 5 条"明确关系优先、验证有效性"的落地;概率匹配与实时实现作业不要求。
- 第 3 步 `prepare` 生成来源映射(`state/mapping.json`)、订单按映射进查询库、`reconciliation.json` 对账,就是第 10 条两段流水线+"更新后检查通过再切换";追溯一组跨系统账户及订单、一条不应采信的依据,对应第 9 条"保留关联依据、可定位影响范围"。
- 未决来源单列、独立财务桶不当自然人,是第 6 条"回溯与否由业务决定"的青禾选择:核实不了的归属不硬合并;全公司精确自然人数保留待核,不靠错误合并凑数。
- 验证三层对应 A~E:第②层落在第 3 步对账与追溯(正序/乱序可用 E 组本地小样本模拟),第③层是 B 组直接入口与 Agent 逐项一致、独立口径核对;防误合并即任务书"不能凭姓名、脱敏手机号或设备相同合并"。

## 可用于作业的证据 / 判断

- `identity_evidence` 返回的 evidence(left/right/relation/evidence_id/source_file/source_row/rule_version)就是"保留关联依据"的工程化:每条关系能回到记录序号,evidence_id 不能重复;findings 承载未采信、失效、导出外引用、缺失和冲突,保留可定位来源与原因。
- relation 只有 same/different/unresolved:失效、撤销的迁移记录和无效核查不进 evidence、进 findings——"验证有效性"直接决定哪些记录可采信;证据不足保留 unresolved(待确认),不能为凑人数升级成 same。
- `verified_singletons` 只放有公开核查依据(开户核查覆盖+例外记录)支持独立开户的账户,不是所有孤立账户;无边来源不能脱离 coverage.json 单独判断;business_basis.csv 是核查依据说明,不是统一会员答案表。
- 自检映射用"独立标准":用独立 SQL 或公开记录核对已核实分组、订单归属与金额守恒,不能拿 prepare 自己的输出证明自己正确;误合并是本周最不能错的点——AI 起草身份规则时最容易凭姓名或手机号相同就合并。
