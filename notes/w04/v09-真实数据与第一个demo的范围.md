# V09 真实数据与第一个demo的范围

> 视频 27:51(article 1031544,课件 23 页;字幕稿 `transcripts/v09-*.md`)。外部案例课:神策的 ETL 实践(前半)+ 投手 Copilot 的第一个 demo(后半),用来印证本周方法。

## 核心方法与机制

1. **方法论核心:从用数需求倒推采集方案**。客户买数据产品是为了完成具体业务任务(看指标、出报表);先访谈业务方,弄清他们要什么判断、看多深,再定要采哪些数据——顺序不能反。
2. **采集方案与验证**:分析师产出方案(所需事件、字段、来源、关联处理、ID 映射);**方案不直接交研发**,先从需求反推验证——把每个需求转成计算口径,确认事件、字段、筛选条件、用户标识真能算出来。方案阶段验证的本质是"需求与数据的对应关系";数据条件不满足就与客户协商调整需求范围。
3. **ETL 与 ELT**:先清洗再入库 vs 先入库再计算,神策两种都支持;方法论不变——每一项采集和处理都要有业务需求对应,并以此作为方案验证依据。
4. **数据 diff 分两层**:原始数据层(总条数、分布)与应用层(指标、报表);底层看似无误,业务结果仍可能有差异——客户关注的是业务结果,不只原始数据。
5. **diff 容忍度是商定的,不是追求 100% 一致**:与客户商定核对范围与可接受比例;SOW 里必须写明比较对象和计算条件,否则必然争议。超出约定(如 3% 变 6%)要查原因——数据遗漏、逻辑问题、口径不一致;不是所有 diff 都是 bug,也不能凭感觉判断。
6. **逐条追踪不因容忍度而放松**:约定了 3% 不等于逐条环节可接受误差——每条数据去向要能解释(接受、隔离、去重);隔离数据单独存放保留再利用,不直接丢弃。生产环境不能频繁全量重导,靠隔离区重处理。
7. **上线策略:并行与分批试跑**:新系统不一次性替换所有数据源,按业务逐步试运行,新旧并行一段时间;试运行除数据准确性外,还要看数据流稳定性、延迟、计算存储资源——线上业务对时效有硬要求,结果对但延迟高也没法用。先观察部分链路,再逐渐扩大范围。
8. **备份与幂等**:每个环节留原始数据备份(按环节设保留窗口:7 天/30 天/一年),出问题从出错点恢复,不必全量重跑;网络重试会产生重复数据,神策用"用户 ID+事件 ID+发生时间"组成联合主键判重,流式处理只能在时间窗口内去重——一定程度的幂等,做到不重不漏。
9. **模板与工具是提效,不替代核实**:行业需求模板、采集方案模板给工作一个起点,指标含义与业务流程差异仍要访谈和方案验证;配套 SDK、可视化埋点、collector、方案流转工作流、数据质量平台(相当于对账)。AI 时代把这套经验整理成数据采集 skill 交给 coding agent,交付团队向 FDE 转型——但**甲方的业务确认环节没有变**,方案是否符合业务、数据可用性仍要客户人工确认。
10. **投手 Copilot 第一版 demo**:核心假设是"投手能在 Copilot 里完成大部分盯盘工作"。第一版做成诊断卡片信息流+IM 通知;用 Claude Code 快速做出可交互 demo(虚拟示例数据)带去客户现场。
11. **反馈推翻假设,且不能浅读反馈**:投手反馈"看完还是担心漏,要回 Meta 后台逐一复查"——时间没省下来,核心假设失败。若浅读成"用户不喜欢卡片 UI",改动就只停在界面层;真实原因是投手最关心**检查的完整性**:信息流只聚合了问题,没说明"没出现的广告是检查过没问题,还是根本没检查"。
12. **调整方向:给用户一个可逐项检查的范围**:按广告资产树展示所有资产,问题标记在对应节点上,节点带查看状态与处理状态——投手能看清哪些看过、哪些处理过,在 Copilot 内完成检查。改版用模拟数据、纯前端演示,先让客户评估交互是否符合工作需求。
13. **具体可交互的 demo 比抽象 PPT 更能揭示理解差距**:最初给 PPT,客户提不出具体反馈;有了真 demo,投手才能实际使用并给出有价值(推翻假设)的反馈。

## 与青禾沙盘的连接点

- 神策方案验证 ↔ 第 3–8 步:从青禾要用数据完成的工作(38 项指标)出发核对数据可用性;对账等式与"每条记录去向"就是 diff 的逐条层;隔离不丢弃、两次导入结果一致,对应备份与幂等纪律。
- diff 容忍度写进 SOW ↔ W03 与王经理的交付约定经验;本周结论也要按"商定的比较对象和条件"来写,不追求与客户口头数字完全一致(数据按真实规模 1/10 缩小)。
- 投手 Copilot ↔ 第 11–12 步:demo 要演客户完整工作流而非单点功能;bad case(看完还要回后台)如实保留;客户反馈要深挖到工作本质需求(检查完整性),demo_plan 的"继续、缩小范围、调整方向"三种条件就来自这类反馈的判断。
- 青禾 demo 的目的同样是暴露理解差距,让沈总/小林指出"不对"的地方——不是为了展示功能完美。

## 可用于作业的证据 / 判断

- 客户关注业务结果而非原始数据:38 项指标跑通后,要抽查数字的业务口径是否符合修订后的定义,不能只看 `status: ok`。
- demo 假设要具体到可证伪:"投手能在 Copilot 完成大部分盯盘"→ 青禾的关键假设也要写成一条可被运行结果支持的判断,写进 demo_plan 的判断说明。
- 阶段性结论按实际运行证据限定范围;模拟数据的交互验证不能替代真实库上的运行(青禾 demo 必须在导入后的 project 上跑)。
