# V03 客户数据的核实与判断

> 视频 30:35(article 1031539,课件 20 页;字幕稿 `transcripts/v03-*.md`)。本周数据工作的方法源头,不讲代码:data_diagnosis.md 的写法来源。

## 核心方法与机制

1. **为什么先核实**:agent 以数据为地基,数据含义错了,agent 设计再好答案也是错的。最危险的是**沉默的失败**——agent 被调教得不愿说"查不到",而是尽力给出一个看似合理的数字:单位和数量级都对,甚至数值相近,但本质是错的,直接用结果的人难以察觉(Anthropic 今年 6 月博客:自助数据分析最难防范的就是这种"答案虽错但看似合理"的沉默错误;真正的问题往往源于资料本身的错误或过时——agent 按错误说明查数据,仍能得出结果并解释得头头是道)。神策查数 agent 的教训:北京存的是汉字还是拼音不先看数据永远不知道;内部数据环境与客户环境准确率差异明显,原因不是模型或检索,而是客户数据未经系统性核实。
2. **字典为什么天然不可信**:数据字典在系统上线时编写,记录的是理想约定;业务变化和录入习惯会让实际数据偏离,而**几乎没有公司能同步迭代数据字典**;有些字典从一开始就没校验过。例子:出海电商客户 robots.txt 写着允许所有 AI 爬虫,防火墙却默认阻止主流 AI 爬虫,老板毫不知情——对客户的每个系统描述都要保持怀疑。正确顺序:拿到数据先看实际数据,再与客户核实细节,而不是按字典直接清洗、导入、算指标。
3. **核实三步法**:①定来源——三类信息互相印证:实际数据本身、描述数据的文档(字典/表格说明/接口文档)、客户业务负责人及同事的说法;还有容易被忽略的第四类:**自己在访谈中积累的认知**(W02/W03 形成的理解,也要与真实数据核对)。②用文档、客户说法和自己的理解去核对数据实际情况。③对不上的地方分类定性,找对的人处理。
4. **数据剖析(data profiling)怎么看**:不必一开始统计所有字段,先挑要用的字段,带着"要确认什么"去查。最常看三个问题:文本字段的实际取值含义;时间字段的真实分布——大量记录集中在凌晨两点或整齐的 0 点 0 分,多半是系统批量同步或后期补录的时间,不是业务实际发生时间;完整性——按来源、时间、地区等维度拆分,找突然减少或缺失的维度。准确性要找可靠参照:财务报表、业务同事维护的 Excel、客户常挂在嘴边的数;先核对关键总数(如一个月订单量是否合理),再随机抽几条记录人工对。
5. **差异分三类,类别决定处理**(字段级):
   - **字典过时**:数据是对的,字典/我们原有认识没跟上(如新增业务值字典没写;小样本上的结论在全量数据上不成立也属此类)。按实际数据理解并写映射,**不要误改数据**,找客户确认。
   - **映射错误**:字段里装的不是字段名说的东西(或对字段的理解错了)。找真正懂该字段的人确认,改映射和清洗规则,确保实际含义与名称一致。
   - **数据暂缺**:这次导出里根本没有。**不能当零**,要写进覆盖说明和待补数据清单,问相关人能否补;无论能否补录,覆盖记录都必须提供给 agent。
6. **远桥小例(先自己判再对答案)**:赵工导出工单数据+字段说明。三处不一致:①工单状态有"待配件",字段说明没提→字典过时,找赵工确认含义和起始时间;②"确认时间"大量集中在傍晚、甚至晚于派工时间——结合小何曾说现场网络不佳、先记备忘录联网再补录→该字段部分记录的是补录时间,属映射错误,抽几条工单与小何核对,并问赵工有无客服通话记录等能还原真实确认时间;**确认前不能拿它算报修到确认的时长**,否则 agent 按字段说明回答就错;③按地区拆分发现某些外地城市几乎没有报修记录——这些地方由合作维修商处理,不在赵工导出范围内→数据暂缺,统计报修量时不能说这些地方没报修,找许经理和赵工确认能否补充。
7. **记录级问题分三类**:①录入错误(设备编号小写、多余空格等格式问题)→清洗统一,原始记录保留,修不了的单独存放注明原因;②业务异常(记录本身无误但事件异常,如设备一月内多次报修、用户一小时访问 3000 次)→**不改不删**,标记后写诊断报告,要不要过滤、怎么过滤与客户按业务需求商量(爬虫访问要不要计入 UV 由客户定);③客户的特殊做法(看似不合理实为有意为之:投手想让广告六点开跑、因系统延迟需提前到四点安排;一线同事把系统字段当便签——远桥工单"故障类型"栏写着"客户要求只在工作日上门",看似录错位置,实为业务约束,**清洗掉就会违反客户要求**)→保留、拆分单独存放、记住来源,并问清业务含义。
8. **核实说明(工作成果,要交给客户确认)**:每条结论标来源——数据看到的写具体事件(如"小何工单中傍晚补录的比例"),访谈听来的写对方理解和行为动机(如"小何因网络问题补录"),推断单列。数据可以支持或反驳某个说法,但不能互相替代;自己的推断不能写成数据上看到的事实,未核实的不能写成已确认。后续 ETL 规则和数据说明都以这份核实说明为依据。
9. **核实的范围边界**:数据治理不可能完全可靠,核实是其中一部分。**不求搞清客户所有数据问题,围绕 SOW 约定的服务范围**,解决 SOW 提到的问题所涉及的数据。
10. **三原则收口**:先核实再动手(不按文档直接清洗导入);先分清再处理(先定类别再决定改什么、找谁;看似错误的记录先了解原因);结论有出处(每条注明数据/访谈/推断,经客户确认后才交给 agent 使用)。
