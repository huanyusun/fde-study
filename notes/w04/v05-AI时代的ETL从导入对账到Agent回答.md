# V05 AI时代的ETL:从导入对账到Agent回答

> 视频 41:17(article 1031541,课件 29 页;字幕稿 `transcripts/v05-*.md`)。技术主线后半段,对应作业第 7、8、12 步:适配器隔离、导入对账、部分覆盖下的回答与调优对照。

## 核心方法与机制

1. **ETL 全程要保留三类信息**:原始记录的位置(来源文件+记录序号)、处理前后对比、数据覆盖范围。"程序跑成功"不等于没问题——这三样是事后检查与验证的依据。前提纪律:可靠地读文件,发现影响整个文件的问题(如表头不符)必须停下核实,不带猜继续;无论这批数据能否处理,**原始文件必须保留**。
2. **每条记录三类去向:接受/隔离/去重**。完全重复的按规则去重保留一条(计数为接受 1+去重 1);隔离的暂无法确认。Databricks 数据质量规则给三种选择(违规入库并统计/直接丢弃/整体失败),工程能力不同,但**怎么处理由业务决定**;要"隔离+其余继续入库"就得自己加标记分流。隔离记录单独按批次保存(不用临时表免覆盖),带来源文件、记录序号、原因、完整原记录——客户补数据或给新规则后能继续处理。
3. **幂等性**:同数据、同规则、同版本下多次执行业务结果一致。网络中断重试、客户补数、FDE 改规则都会触发重跑;不设计好就数据翻倍或报错。手段:稳定标识(多系统时=来源系统+原始编号)+写入方式(upsert 或新分区替换旧分区)。梧桐采用**独立全量重导**:每次在新目录完整处理导入,检查通过再决定是否使用。
4. **验证幂等不只比总数**:同一输入同版规则跑两次,比订单数,还要**追一条原始记录**比较两次的处理去向与字段值。稳定编号同时服务于跨版本追踪。
5. **修改后重点从"有没有变"变成"变化是否符合预期"**:让 AI 改程序时,除告知改什么,还要明确指出哪些结果应该变化,把预期写成检查,重跑后逐项比较。例:客户补发会员信息后,预期=隔离数减少、接受数增加、且新增的正是原来被隔离的孤儿订单。程序运行成功≠业务符合预期。
6. **版本与输入都要记**:每次运行记录所用规则版本、代码版本、输入数据版本(给原始文件算哈希指纹;跨会话交接附哈希)。规则与代码分开版本化。旧库别删:新导入可能失败,保留已检查过的旧数据,新数据完整生成并通过检查后再切换,失败信息也记下来。
7. **对账分两段**:①原始输入→处理结果:等式"读入=接受+隔离+去重"(一条会员拆 3 个标签仍是接受 1 条,标签另按拆分规则查);②处理结果→数据库:总记录数、关键金额汇总,再按业务维度分组核对(每家门店×每月的条数与金额——总数相同但一家少十条一家多十条,分组才能定位),必要时按稳定编号逐条比。比较前先明确比什么、什么口径。
8. **对账程序不能让 AI 从处理代码反推**:要给**独立核实过的业务口径+样本预期**,否则同一个错误被复制到两处,"两边都错也能对上"。
9. **按键追踪两条路径**:接受订单——原始序号→清洗文件(金额/门店/会员号与表结构匹配、主键不重、关联存在)→库内记录;隔离订单——原始→隔离文件(带编号与原文+原因)→确认接收区和订单库里都没有它。两条都通,才能向客户交代:接收了什么、每条去了哪、什么没进库、哪些待核实。很多项目把对账结果作为交付物。
10. **数据不全时 agent 的回答边界**:缺口两种(来源不全:只有门店收银没有线上;收到但被隔离:找不到会员/渠道映射不明)。原则:结论限定在已覆盖范围;未纳入的不能当零,也不能一律拒答——按客户问题检查缺口是否落在涉及的时间段/门店/指标上:隔离 2 条若是其他月份则不影响八月;若是八月但金额未确认,只能报"已统计订单的销售额"并说明不是完整八月;连日期都无法确认就只能说"未核实"。隔离比例小≠影响小(可能金额占比大或集中某门店某月)。
11. **梧桐同比反转案例**:只有门店收银数据时,去年 8 月 909 单、今年 783 单,同比下降成立;补上线上订单(去年 1319、今年 1520)后全渠道其实是增长——来源不全时把"门店下降"说成"收款单数下降"方向就错了。理想回答先说覆盖范围(仅门店、线上未纳入、部分订单隔离)再给数字。整批隔离 40 条不能简单当作"八月少 40 单"或加回八月。
12. **覆盖说明+提示词的对照实验**:同一同比问题每档问两次,三个条件共六次,查询 SQL 结果一致,变的只是回答:①只说"门店收银系统导出"→两次都没提线上缺口;②补"线上订单在另一平台导出"→两次都明确了来源与未纳入;③再调提示词(数值结论限定在实际覆盖范围内,并说明是否支持整体判断)→回答先说范围再给数字。结论:缺的是信息还是回答要求要分开判断——信息缺就补说明,信息有了不会用才调提示词;**不按案例逐条追加提示词,要找共同原因**,否则提示词无限增长;改完用其他问题回归,确认没把原有能力改坏(更多在 W07)。

## 与青禾沙盘的连接点

- 第 7 步(adapt):七张表+quarantine,每条隔离带 reason_code、source_file、source_row、raw_json 完整原记录;record_counts 满足"读入=接受+隔离+去重"。
- 第 8 步(reconcile/load):两次导入(run-01 project-a/project-b)比 row_counts、table_sha256;record_counts.reconciliation 写等式证据;人工追一条合法+一条失败记录写 samples——正是第 9 条的两条追踪路径。
- 第 12 步(调优):定位五层(协议/数据 SQL/工具/提示词上下文/Harness 策略),每次只改一处,同一问题前后各跑一次;实验证明调优对象优先级——先补覆盖说明(数据侧)再动提示词;"只在末尾补一句数据不全、结论仍按全公司下"不算解决。
- 输出确定性:按确定顺序写出,不依赖 set 迭代顺序,否则重复运行不一致(repeat 层预检)。

## 可用于作业的证据 / 判断

- `repeat_import` 要 first/second 的 counts + row_counts_equal;`test_result` 含金额汇总前后一致。
- demo 回答若数据只覆盖部分(如仅门店无线上、部分月份),结论必须限定范围并说明缺口性质(来源缺失/隔离/未核实),bad case 如实记录。
- agent 回答实验的设计可直接借:同一问题多次跑保证稳定、三档对照(只补信息/信息+提示词)、用别的问题回归。
- 覆盖说明(coverage_notes)随补数重导同步更新,manifest 里的 time_range/quarantined 是 agent 回答"适用范围"的依据。
