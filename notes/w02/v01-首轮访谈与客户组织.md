# V01 首轮访谈与客户组织

> 视频 34:11(article 1026349)。字幕稿本地见 `transcripts/v01-首轮访谈与客户组织.md`(不进 Git)。

## 核心方法与机制

**本周诊断三方向**(起点 = W1 立项邮件 + 旧项目结项材料):

1. **了解业务问题**:沈总给出"复购率下滑 + 会员老化明显"的现象与解释,但解释的依据要核实——运营、门店这些角色怎么看,有没有别的原因。
2. **了解实际工作**:小林现在怎样获取信息、选会员、形成建议、执行动作,门店和系统怎样参与——才能判断 agent 进哪个环节、会不会额外增加工作(沈总明确要求"别让他多整理一套表")。
3. **了解进入条件**:哪些能直接用、哪些需要客户配合——核实业务定义、数据/系统条件、谁参与、谁能决定。

**读旧项目结项材料的方法**——材料里的套话要拆成追问:

- "需求持续调整,推动方案逐步完善" → 原来解决什么工作?调整了什么?为什么?调整后效果如何?
- "日常使用继续推进,操作路径需完善" → 找实际使用者:系统用来做什么?哪里不方便?遇到困难时工作最后怎么完成的?
- "继续跟踪使用观察效果" → 希望改善什么?实际结果如何?有没有记录?

**干系人四角色**(虚拟案例:远桥设备售后工单系统):

| 角色 | 案例 | 职责 | 要点 |
| --- | --- | --- | --- |
| 推动者 | 许经理 | 提出问题、组织沟通、协调参与 | 积极推动 ≠ 拥有全部权限 |
| 决策人 | 梁总 | 预算审批 | 只对某一类事项做决定;每类事项各有其决策人 |
| 评估人 | 赵工 | 评估接入条件、核实认证/接口/运维 | 评估"行不行" vs 决策人"定不定",微妙区别 |
| 使用者 | 小何 | 收工单、记录处理结果 | 最懂一线细节;许经理不知道的他们知道 |

一人可兼多角色(许经理同时推动+评估业务效果);不一定四类齐全;小公司一人多角,大公司光 IT 评估就可能牵涉架构师、CIO 审批。

**职位 / 权限 / 影响力三分**(To B 新手最易混淆):

- **职位**:组织内岗位,用来找初步沟通对象;同职位在不同公司职责不同。
- **权限**:对某件事实际能做什么决定——不能从职位名称推出来,必须沟通核实(梁总有审批权 ≠ 已经批了)。
- **影响力**:小何职位不高,但资历深、和梁总熟、最清楚哪个步骤费时间——他的意见值得认真核实。
- 访谈优先级不能按职位高低排;也不能因为某人熟悉业务就认为他对具体事项有决策权。

**部门墙的成因**:不一定是办公室政治,而是不同角色/部门的目标、考核、信息、工作量、风险各不相同。例:工单加必填项——许经理要完整进度,小何多了重复录入,赵工要考虑系统衔接与运维;考核按现场处理速度评价工程师,记录就会失真。FDE 要把变更说具体:增加了谁的工作、谁需要什么帮助、谁承担什么风险;确认存在重复录入就要想办法减少步骤,否则"满足了许经理,但干活的人没法用"。

**组织诉求 ≠ 个人诉求**:组织要减少遗漏、快速处理所有问题;个人在意记录方不方便、对自己的工作有什么影响。诉求只是一句话时不下动机判断(小何说"回公司再补记录"只是提出条件,不能推断他反对系统——贴了标签,后续沟通就会被预设立场带偏)。

**乙方侧的角色与承接**(需求"工单与现有系统互通"如何落地):

- 销售:不能只传话——确认客户原话、上下文、有无承诺。
- 产品负责人:说明当前能力支持到什么程度、有哪些限制。
- 交付/FDE:评估所需环境、条件、资源、排期;把"互通"变成具体需求,与已有能力及实施条件核对,才能给出可靠的方案和承诺。

**现场记录纪律**:写具体的人名。"业务支持 IT 待确认"没用——下一步跟谁讨论?"赵工说可以评估接口"≠ 允许介入——还要记录评估条件与结果。同一个部门、同一个岗位内的差异,不能被"某角色/某部门支持"覆盖;一个人支持业务目标 ≠ 支持你的全部实施方案。

## 与青禾沙盘的连接点

- **本周必访**:老周(IT 负责人,系统和数据协作)、小林(会员运营经理,日常运营)、陈姐(大区门店店长,门店工作);**选访**:王经理(财务经理,预算合同)、增长负责人(项目发起人,可继续核实 W1 遗留问题;同一角色在 W1/W2 访谈里透露的信息不一样)。
- **材料 ↔ 访谈对象的映射**:材料说"操作路径要完善" → 问小林、问陈姐(门店到底怎么弄);系统条件 → 找老周核实;预算合同状态 → 沈总/王经理可以帮着核实。职责只是调查方向,不预设问题一定在哪个环节。
- **本周四个产物**:访谈实时文件(原始记录)、访谈纪要(自己的判断)、本体初稿、干系人地图。
- **访谈切入三件事**:这个问题涉及谁的工作?谁掌握相关信息?谁需要参与决定?对TA权限和职责已有什么依据?
- W1 的立项报告和 GAP 表用来补充具体问题、调整调查重点,**获得新证据后修订判断**——修订本身是课程要求的动作,不是返工。

## 可用于作业的证据 / 判断

- 讲师明确说:本讲的全部内容"已经是一个非常简化版的干系人地图"——流程是:依据公开职责形成初步调查判断 → 找到这些人 → 区分说法与依据 → 找到要核实的地方。干系人地图先按职责起稿,细节靠访谈填。
- **不预填**:不能因为老周是 IT 负责人就预填他拥有全部数据信息;他只是系统和数据协作的入口。
- **"支持"要落成具体事项**:谁决定、谁执行、需要什么前提、现在到哪一步。开会听到"我支持"不等于万事俱备——把客户的支持逐步核实成一件件具体的事,现场推动时才知道哪些已具备条件、哪些还在协调。
- **交叉核实方法**:从每个人不同的方向、岗位、立场顺着他的事情问,一个问题得到不同结果,结果交叉起来核实行。
- 思考题的答案框架(可直接套用到沙盘):角色识别(推动/评估/使用)有依据了,但审批**进度**要另确认——梁总有审批权 ≠ 已批准;数据访问、人员安排也不因"下周试用"自动具备;小何的补记录诉求直接影响上线后的使用方案,不是立场问题;客户侧找业务人员解释场景、系统负责人说明环境接口,己侧销售查需求来源、产品核对能力、交付核对条件。
