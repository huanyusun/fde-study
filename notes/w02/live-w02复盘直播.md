## 一、多角色访谈：围绕实际工作核查说法

核心难点是分清谁说了什么、理解分歧成因、落实待核信息，再把认识转化为业务模型。

| 常见误区 | 改进方式 |
| --- | --- |
| 拿同一个口径问题逐个问所有人 | 问各自在实际工作中的具体用法；公司级口径尚未明确时记为待核实，避免重复消耗访谈次数 |
| 一条消息塞五六个问题 | 一次只问一件事；复杂问题可提前书面发送，让对方准备 |
| 得到笼统回答后原样追问 | 换角度问常规做法、工作卡点、例外处理，或请对方口头讲解一次流程 |
| 开场不讲目的，或问职责外的问题 | 先说明材料用途，再问具体业务；职责外事项转交对应干系人 |

值得保留的三项做法：

- **收尾复述，请对方纠正**：提高记录准确性，真实项目中也能形成留痕；复述确认仍不等于独立核实业务事实。
- **带着上一位角色的说法问下一位**：交叉核对立场与分歧，准确归属原话，不把自己的概括冒充他人表述。
- **具体提出配合请求**：写清核查内容、用途、时间段与所需支持，便于对方对接审批。

## 二、参考答案：保留口径、来源与判断边界

### 会员数如何建模

参考答案没有直接把一个会员数设为确定属性，而是将“口径”单独建成对象，记录说法来源、核算范围与核实进度，避免 Agent 自行挑选答案。

“80 万”和“120 万”是讲评中的不同说法示例。当前任务应记录说法及适用条件、保留疑问，不能越权判定谁对；也不能把提问前提或对方重复的数字当成确认事实。

### 冲突组工具如何使用

工具输出是核查线索，不是结论。概要提到：参考运行前三组混入无关条目，需剔除；第四组实际为一致说法，不构成分歧。该判断针对讲评中的参考输出，不能直接套用到本项目运行。

人工核查应确认：是否针对同一问题，时间、范围、含义是否可比，原文是否真正不一致。相同说法、未涉及事项和共同未知不能为了满足作业要求而列成冲突。

### 方法开发与 Skill 设计

原 Skill 存在按步骤调用工具、人工确认点设计不足等问题；参考答案补充分组核查、模型分层起草等规则。应先明确规则与确认点，再执行，避免 Agent 边跑边改规则。

方法开发不能只改单个文件或路径：需要在固定条件下保留修改前后的实际运行结果。超时、截断、格式错误等失败运行不能计为有效完成。

### 验证业务模型是否生效

- 不以“回答更谨慎”作为有效性的主要依据，要看是否用到客户特有的定义与边界。
- 每一道验证题写清检验模型中的哪几条，以及预期表现。
- 不只检查模型文件是否存在，还要检查实际请求引用的客户事实原文是否正确；错误模型可能放大错误。
- 职权判断要分开记录授权边界、偏好和否决权；否决权以明确表态为依据，不能按职位或态度推定。

### W1 如何接续

W1 快照与编号原样保留，只对新证据真正改变判断的条目追加更新，说明变化依据，保留历史轨迹。概要中的“更新两条”是参考答案的处理数量，本项目应按实际证据决定，不能照搬数量。

## 三、沙盘机制与客户沟通

### 沙盘机制说明

- 老周本周不展开系统清单和取数方式，属于剧情设定；角色信息按周开放。
- 出现“未能可靠回答”提示，概要称其为后台审核拦截，不再消耗次数；不可概括他人说法。具体限制的适用范围仍需以平台当次提示为准。

### 客户沟通的三个难点

| 难点 | 可采取的行动 |
| --- | --- |
| 建立信任 | 换位理解客户处境，坦诚能力边界并兑现承诺；私交只能帮助拉近距离 |
| 看清内部关系 | 在干系人地图中记录每个人在意的利益与风险，识别可能帮忙、拖延或放大项目的人；推断单独标注并寻找验证机会 |
| 听懂话外之音 | 客户以流程推脱时，进一步了解其风险顾虑；提供有范围的核查说明，明确数据范围、用途与责任，让其便于向老板交代 |

## 四、FDE 面试与简历建议

以下为直播提供的准备参考，不代表所有企业统一采用的招聘流程；概要指出国内企业仍在摸索。

| 面试环节 | 准备重点 |
| --- | --- |
| 编码 | 生产级开发能力；能解释最近代码的设计选择与边界条件 |
| 系统设计 | 跨云、跨技术栈的架构取舍，理解具体约束 |
| 问题分解 | 开放场景下如何界定目标、排序优先级并安排验证 |
| 客户模拟 | 承接情绪、深挖需求；该环节的定性判断很关键 |

简历应写清三件事：

1. **完整项目闭环**：如何把客户需求定义为业务结果、做了哪些技术取舍、上线后有什么真实数字。
2. **亲手完成的技术工作**：区分团队协调与自己开发、部署、排障的工作；缺少实践时如实承认短板。
3. **具体沟通场景**：例如如何让持怀疑态度的客户接受方案，用行动和结果证明能力。
